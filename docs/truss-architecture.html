8. 설계 근거 · 트레이드오프

AZ 구성 — 컴퓨트 2AZ, 데이터만 3AZ

항목내용
목표 우선순위현업 수준 HA를 1순위, 비용은 2순위(공유 계정) — 단 AZ 구성만 예외로 비용을 고려
데이터 계층 3AZRDS Multi-AZ DB 클러스터는 3AZ 배포가 하드 제약이라 선택지가 없음
컴퓨트 계층 2AZ 유지NAT·Interface Endpoint·노드그룹은 AZ 수에 비례해 비용 증가(NAT 1개당 약 $43/월) — RDS처럼 강제되지 않는 계층까지 3AZ로 맞출 이유 없음
3번째 AZ가 2c 아닌 2d인 이유AWS CLI(describe-orderable-db-instance-options)로 확인한 결과 RDS 시작 클래스 db.m6gd.large가 Multi-AZ 클러스터 배포 시 2c를 지원하지 않음(2a/2b/2d만 지원)
트레이드오프컴퓨트 계층은 AZ 1개 장애 시 손실 비율 50%(3AZ 대칭이었다면 33%). RDS만 3노드 구조로 보호되고 나머지 계층은 격리 수준이 낮음 — 팀이 인지하고 감수한 결정

인스턴스 클래스 선정 근거

리소스클래스근거
EKS 백엔드 컴퓨트시스템 노드그룹(t3.medium 고정 2대, CoreDNS 등 상주) + Karpenter NodePool(c6i.large, On-Demand 전용, CPU 합산 상한 160)NFR-01/02(초당 1만 건) 측정 대상 자체라 버스터블(t계열) 배제 — 크레딧 고갈 패턴이 아니라 실제 시스템 성능을 측정해야 함. compute-optimized 중 최소 사이즈. Cluster Autoscaler 대신 Karpenter로 전환 완료(11장) — 미리 정한 min/max 대신 실제 파드 리소스 요청 기준으로 노드를 즉시 프로비저닝/정리
RDSdb.m6gd.largeMulti-AZ DB 클러스터는 로컬 NVMe "d" 계열에서만 지원(AWS CLI로 확인) — 애초 검토했던 db.r6g.large는 클러스터 배포 자체를 지원하지 않음. "d" 계열 중 가장 저렴한 클래스로 시작, 부족하면 db.r8gd.large로 상향
ElastiCache Rediscache.t4g.medium20개 마켓 호가창은 데이터량이 작아 메모리 최적화·샤딩 불필요 — 범용 거쳐 버스터블까지 하향. 트레이드오프: 크레딧 소진 시 지연 튈 수 있어 리플레이 고배속 구간에서 CPU 크레딧 사용률을 부하 시험으로 관찰 예정

NAT / VPC 엔드포인트

NAT Gateway는 AZ당 1개(총 2개) — 컴퓨트 계층을 3AZ로 확장하지 않기로 한 결정에 맞춰 2개 유지, 실질 용도는 시세수집기→업비트 아웃바운드뿐이다. S3는 Gateway Endpoint(무료)로 NAT 없이 처리하고, ECR·CloudWatch Logs·STS·Bedrock Runtime·SQS는 Interface Endpoint로 2a/2b에 배치해 NAT 장애가 배포·로그·Job 트리거까지 막지 않게 한다.

9. Job 트리거 상세 — SQS + Lambda

항목내용
문제접수API(Public ALB 뒤 외부 노출, HPA 스케일아웃 가능)가 K8s API를 직접 호출해 Job을 생성 → 노출 컴포넌트가 클러스터 RBAC 권한을 보유, 공격 표면·blast radius 확대
개편접수API에서 Job 생성 권한(RBAC) 제거, SQS 발행 권한만 부여
흐름접수API → SQS(team1-sqs-job-trigger) 발행 → Lambda(team1-lambda-job-trigger, VPC 연결)가 이벤트소스매핑으로 소비 → EKS 프라이빗 엔드포인트 호출해 Job 생성
Job 구분메시지 본문의 job_type으로 AI트레이더 Job / 리플레이 Job 분기 생성
권한 범위Lambda 전용 IAM 역할 → EKS 액세스 엔트리로 매핑, 특정 네임스페이스 create-only(최소 권한)
효과클러스터 변경 권한 보유 주체 = Lambda 단일 지점. 접수API 스케일아웃·침해와 무관하게 Job 생성 권한 없음
SQS를 끼우는 이유세션 시작 요청이 몰릴 때 접수API 응답 시간과 Lambda/EKS API 호출 속도를 분리(버스트 완충), 실패 시 재시도·내구성을 SQS가 대신 보장, 접수API는 Lambda 가용성에 의존하지 않음

10. AI 트레이더 봇 설계 요약

봇LLM 사용판단 기준
마켓메이커규칙 기반항상 매수·매도 동시 호가, 체결되면 즉시 재호가(취소 후 재호가하는 유일한 봇)
노이즈규칙 기반고정 확률로 발동, 방향·가격·수량 모두 무작위 소량
대량주문규칙 기반낮은 확률로 발동, 발동 시 훨씬 큰 수량(부분 체결 검증 목적)
모멘텀추종LLM(Bedrock)"추세인가 아닌가" 정성적 판단 — 최근 가격 변화율·캔들 데이터를 프롬프트에 계산해 전달
평균회귀LLM(Bedrock)"과열인가 아닌가" 정성적 판단 — 이동평균 대비 이격도를 프롬프트에 계산해 전달
  • 판단 주기와 주문 생성 주기는 별개 — 봇은 최신 방향 신호(공유 상태)를 계속 갱신하고, 주문 생성 로직은 그 상태를 자기 루프 주기로 읽어 주문을 만든다. Claude 호출 지연(수 초)이 주문 생성 속도에 영향을 주지 않기 위함
  • 호가창은 AI 트레이더가 아니라 매칭엔진이 만든다 — 접수API가 발행한 주문을 매칭엔진이 체결하며 Redis에 반영, 접수API가 조회 응답으로 돌려준다
  • Bedrock 모델: 기본 claude-sonnet-5, 비용 부담 시 claude-haiku-4-5로 하향. 역할 프로필(persona, 고정)은 프롬프트 캐싱 대상
  • Bedrock 호출 권한(IRSA)은 ai-trader 네임스페이스 서비스 어카운트에만 부여(최소 권한)

11. 남은 결정 사항

항목상태
Bedrock 모델의 ap-northeast-2 가용 여부미확인 — 크로스 리전 추론 프로파일 필요 시 IRSA 정책 ARN도 같이 확정
분산 트레이싱(X-Ray 등)미결 — FR-21 구간별 소요 시간 추적에 AMP/Grafana만으론 부족할 수 있음
Karpenter NodePool CPU 상한, RDS/ElastiCache 최종 클래스1차 부하 시험 결과로 확정 예정(현재는 시작값)
리플레이 엔진 마켓 단위 병렬 실행논의 중 — 매칭엔진 호가창이 마켓별 독립이라 마켓 단위 병렬 Job이 자연스러운 경계. 락 키를 세션 단위에서 세션+마켓 단위로 바꾸는 안 검토 중
주문 기록 파일 병합/분할 책임미정 — 현재는 파드(봇 인스턴스) 단위 시간순 파일. 마켓 단위 병렬 리플레이를 하려면 마켓별 재그룹핑이 필요, 트레이더가 세션 종료 시 할지 리플레이 엔진이 읽을 때 할지 미확정
ACM 인증서 발급/도메인 확정진행 중 — team1-acm-cloudfront(CloudFront용, us-east-1), team1-acm-alb(접수API ALB용, ap-northeast-2) 명명만 확정, 실제 발급·다이어그램 표기는 미완료
