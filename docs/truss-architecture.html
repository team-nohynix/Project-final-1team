8. 실측 인프라 노트

AWS CLI(aws sts/ec2/eks/rds/elasticache/elbv2/cloudfront/route53/wafv2/acm/sqs/lambda/s3/ecr/cloudwatch/sns/secretsmanager/kms)와 kubectl로 직접 조회해 확인한 사실만 적었다. 완전성은 resourcegroupstaggingapi get-resources로 Team=team1 태그가 붙은 리소스 전체(약 40개 서비스·유형, fleet 이력 제외 160여 개)를 한 번에 뽑아 서비스별로 대조하는 방식으로 확인했다 — 개별 서비스 API만 훑어서는 놓쳤던 항목(아래 Secrets Manager, RDS 스냅샷 등)이 이 방법으로 드러났다. 설계 의도·근거가 아니라 지금 이 순간 배포된 상태의 기록이며, 서로 다른 조회 결과가 충돌할 때는 더 최근에 조회한 값을 우선했다(예: MSK 브로커 주소).

RDS 대신 EC2 자체 MySQL — 과거엔 RDS가 있었다

현재 RDS 인스턴스·클러스터는 계정에 team1 리소스로 하나도 없다(describe-db-instances/describe-db-clusters 둘 다 빈 결과). 대신 team1-mysql EC2(m6i.2xlarge, ap-northeast-2a 단일 인스턴스)에 MySQL을 직접 설치해 운영 중이다. Multi-AZ·자동 백업·자동 페일오버 등 RDS의 관리형 기능은 전혀 없다. 다만 team1-rds-final-before-subnet-migration이라는 RDS 스냅샷이 아직 남아 있어(태그 전수조사로 발견) — 이름 그대로 서브넷 마이그레이션 직전에 RDS가 실제로 존재했고, 그 시점에 최종 스냅샷을 뜬 뒤 삭제했다는 걸 보여준다. team1-data-d 서브넷(10.10.52.0/24)이 그 RDS 3번째 노드용이었던 흔적이다.

Secrets Manager — 2026-08-27, K8s Secret에서 다시 전환

처음엔 "미사용"이라고 적었는데, list-secrets 결과만 봐서 그랬다 — 태그 전수조사로 team1/backend/secrets·team1/monitoring/grafana-admin 두 시크릿이 DeletedDate: 2026-07-28로 삭제 처리돼 있는 걸 발견했다(생성 7/22·7/27, 삭제 7/28 — RDS→EC2 MySQL와 같은 시기의 "관리형에서 자체 운영으로" 흐름). 이후 팀 요청으로 Secrets Manager를 다시 도입했다: 현재 DB 접속 문자열을 team1/backend/mysql-db-url 시크릿으로 새로 생성하고, Secrets Store CSI Driver(+ AWS provider)를 설치해 recorder-db-secret K8s Secret을 여기서 자동 동기화하도록 전환했다. team1-sa-recorder IRSA 역할에 secretsmanager:GetSecretValue 정책을 추가했고, recorder Deployment에 CSI 볼륨 마운트를 붙여 두 파드 모두 무중단 롤링 재시작으로 전환 완료했다(재시작 후 0회 재기동, 정상 기동 로그 확인). 앱 코드·env var 이름은 바뀌지 않았다 — K8s Secret이 이제 AWS가 채워주는 것으로 바뀌었을 뿐이다.

파드 단위 오토스케일링(KEDA)

matching-engine(min 2 / max 10)과 recorder(min 2 / max 10, 재확인 시점 기준 — 이전 확인 때는 min 1이었음) 둘 다 KEDA ScaledObject가 붙어 있고 트리거는 Prometheus 쿼리다. orderapi는 KEDA 대상이 아니다.

모니터링 — 관리형 AMP/AMG 아님, EC2 하나에 Prometheus+Grafana 동거

team1-monitoring EC2(t3.medium) 보안그룹 규칙에 "Prometheus"(9090), "Grafana"(80, 3000) 설명이 그대로 박혀 있어 확인했다 — Prometheus와 Grafana가 같은 인스턴스에서 같이 뜬다. monitor.jhyang.click이 이 인스턴스의 공인 IP(43.202.105.104)를 직접 가리킨다. 반면 Route53의 grafana.jhyang.click 레코드는 k8s-team1shared-* ALB를 가리키는데, 그 ALB는 계정에 더 이상 존재하지 않는다 — 예전엔 K8s 위에서 Grafana를 돌리다가 지금의 EC2 방식으로 옮기면서 이 레코드를 정리하지 않은 것으로 보이는, 실질적으로 끊긴 링크다.

시세 전달 경로 — Kafka도 S3도 아니고 HTTP pull

AI트레이더는 시세수집기가 내는 매니페스트/파일 API를 HTTP로 직접 호출해서 시세를 받는다. 시세수집기는 team1-truss-market-data 버킷에도 원본을 쓰지만, 이건 보관용이고 AI트레이더가 실시간으로 읽는 경로가 아니다. 시세수집기는 자체 Public ALB(truss-collector.jhyang.click)로도 노출되며, CloudFront(truss.jhyang.click)가 /v1/* 경로를 여기로 라우팅한다.

진입점 — CloudFront 하나가 경로 기반으로 전부 라우팅

truss.jhyang.click CloudFront 배포 하나가 기본 경로(S3 프론트엔드), /order-api/*·/recorder-api/*(접수API ALB), /v1/*(시세수집기 ALB)를 CloudFront Function으로 접두사를 벗겨가며 라우팅한다. WAF(team1-waf-alb)는 CloudFront가 아니라 두 ALB에 직접 붙어 있다(get-web-acl-for-resource로 확인, CloudFront의 WebACL은 빈 값). ACM 인증서는 "team1-acm-*"라는 별도 이름이 아니라 jhyang.click 와일드카드 인증서 하나를 리전별로 재사용한다.

문서화 안 돼 있던 내부 의존관계

접수API(orderapi) 파드 환경변수에 RECORDER_URL=http://recorder:8082가 있다 — Kafka(orders/executions) 경로와 별개로 접수API가 기록기를 K8s 내부 서비스로 직접 HTTP 호출한다. 같은 환경변수 목록에 ORDER_RECORDS_BUCKET·PROMETHEUS_URL도 있는데 정확한 용도(주문 기록을 접수API도 쓰는지, Prometheus를 왜 아웃바운드로 호출하는지)는 코드까지 보지 않고는 단정할 수 없어 사실관계만 남겨둔다.
