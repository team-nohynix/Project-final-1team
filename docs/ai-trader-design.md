## 1. 개요

**목적**: Truss의 목표는 매칭 엔진의 처리량·정합성·확장성을 검증하는 것이며, 이를 위해서는 실제 시장과 유사한 주문 패턴이 필요하다. AI 트레이더는 이러한 패턴을 생성하는 부하 생성기이다. **투자 수익률은 설계 목표가 아니다.** 봇의 판단이 타당한 방향성을 가지며, 그 결과 매칭 엔진이 처리할 수 있는 수준의 호가창이 형성되면 충분하다.

**범위**: 본 문서는 판단 로직(봇 5종), 주문 생성 로직, 트레이딩 기간 선택 이후의 시세 소비, 주문 기록(S3 저장)까지를 다룬다. 리플레이 엔진과 접수 API·매칭 엔진 자체 구현은 범위에서 제외한다.

파란색(모멘텀 추종 봇, 평균회귀 봇)이 Claude를 호출하는 봇이고, 나머지 3종 봇은 규칙 기반이라 Bedrock과 연결되지 않는다. 시세 수신 모듈은 5개 봇 모두에게 시세를 전달하고, 각 봇의 방향 신호는 주문 생성 로직으로 모인다. **호가창은 AI 트레이더가 아니라 매칭 엔진이 만든다** — 접수 API가 발행한 주문을 매칭 엔진이 소비해 체결하면서 호가창을 갱신하고, 그 결과를 Redis에 반영하면 접수 API가 조회 응답으로 돌려준다(회색 점선 박스는 매칭 엔진 내부 구현이라 범위 밖이며, 참고용으로만 표시했다).

### 2.2 봇별 LLM 사용 여부

| 봇 | LLM 사용 | 이유 |
|---|---|---|
| 마켓메이커 봇 | ❌ 규칙 기반 | 항상 양방향 호가라는 결정적 규칙이라 판단이 필요 없음 |
| 노이즈 봇 | ❌ 규칙 기반 | 무작위성 자체가 목적이라 판단이 필요 없음 |
| 대량 주문 봇 | ❌ 규칙 기반 | 발동 조건이 단순 확률/주기라 판단이 필요 없음 |
| 모멘텀 추종 봇 | ✅ Claude(AWS Bedrock) | "추세인가 아닌가"라는 정성적 판단이 필요 |
| 평균회귀 봇 | ✅ Claude(AWS Bedrock) | "과열인가 아닌가"라는 정성적 판단이 필요 |

**판단 로직은 봇 5종 그 자체를 의미한다.** 규칙 기반 3종은 자체 로직으로 즉시 판단하고, LLM 기반 2종은 역할 프로필(persona)과 최근 판단 이력(메모리)을 프롬프트로 구성해 Bedrock 경유로 Claude를 호출한다(구체적인 프롬프트 구성은 뒤에서 다룬다). 다섯 봇이 만든 신호를 모은 것이 판단 로직 전체의 출력이며, 주문 생성 로직은 봇 종류나 LLM 사용 여부와 무관하게 방향 신호를 입력받아 실제 주문(가격·수량)으로 변환하는 공통 모듈이다.

이렇게 판단(봇 로직)과 주문 생성을 분리하는 이유는, Claude 호출에 수백 ms~수 초의 지연이 있더라도 주문 생성 속도(부하량)에는 영향을 주지 않도록 하기 위함이다. 규칙 기반 봇은 이 지연이 아예 없으므로 더 빠른 주기로 반복될 수 있다.

### 판단 주기와 주문 생성 주기는 별개다

판단 로직은 매 갱신마다 주문 생성 로직에 "전달"하는 게 아니라, 봇마다 **최신 방향 신호(공유 상태)를 계속 갱신**해두는 방식이다. 주문 생성 로직은 그 상태를 자신의 루프 주기로 읽어서 주문을 만들며, 두 주기는 서로 독립적이다.

| 구분 | 주기 |
|---|---|
| LLM 기반 봇(모멘텀 추종 봇·평균회귀 봇)의 방향 신호 갱신 | 수 초(Claude 호출 지연에 좌우됨) |
| 규칙 기반 봇(마켓메이커 봇·노이즈 봇·대량 주문 봇)의 방향 신호 갱신 | LLM 호출이 없어 훨씬 빠르게 가능 |
| 주문 생성 로직의 반복 주기 | 판단 주기와 무관하게 더 짧게 설정 가능 |

즉 하나의 방향 신호로 여러 건의 주문이 나올 수 있다 — 모멘텀 추종 봇이 5초에 한 번 "BUY, strength 0.6"을 갱신해도, 주문 생성 로직은 그 5초 동안 가격·수량을 조금씩 바꿔가며 여러 번 주문을 낼 수 있다. 정확한 숫자(판단 몇 초, 주문 생성 몇 ms)는 아직 확정되지 않았으며, 목표 부하와 성능 시험 결과를 보고 튜닝한다(향후 검토 사항 참고).

### 2.3 데이터 흐름 (단계별)

1. 사용자가 트레이딩 기간(과거 시점)을 선택한다(FR-26)
2. 시세 수집기(C)가 업비트에서 해당 기간의 20개 마켓 시세를 수신해 원본을 S3에 저장한다(FR-14)
3. AI 트레이더의 시세 수신 모듈이 시세 수집기의 매니페스트/파일 API를 HTTP로 호출한다(Kafka 아님 — 과거 데이터·소비자 1개뿐이라 pull 방식). 최초 1회 큰 단위(일/주/월/년 단위 가격·거래량, batch 파일)를 일괄 수신해 판단 기준선을 설정하고, 이후 실시간으로 작은 단위(초/분 단위 가격·거래량, 개별 체결 내역, stream 파일)를 이벤트 타임스탬프 간격에 맞춰 순차 수신해 판단을 갱신한다
4. 판단 로직의 각 봇이 시세와 함께 접수 API의 호가창 조회(`GET /v1/markets/{market}/orderbook`) 결과를 참고해 판단한다(FR-16: "시세와 호가창을 참고")
   - 규칙 기반 3종(마켓메이커 봇·노이즈 봇·대량 주문 봇)은 자체 로직으로 즉시 방향 신호를 만든다
   - LLM 기반 2종(모멘텀 추종 봇·평균회귀 봇)은 프롬프트를 구성해 AWS Bedrock의 Claude를 호출하고, 구조화된 방향 신호를 응답받는다
5. 주문 생성 로직이 방향 신호를 모아 마켓별 호가 단위에 맞춘 실제 주문(가격·수량)으로 변환한다
6. 주문 생성 로직이 접수 API에 실시간으로 제출한다(`POST /v1/orders`). 접수 API는 검증 후 Kafka `orders` 토픽에 발행한다
7. 매칭 엔진(B)이 `orders` 토픽을 소비해 체결을 수행하고, 갱신된 호가창 상태를 Redis(ElastiCache)에 반영한다. 4단계에서 각 봇이 참고하는 호가창은 이 데이터를 접수 API가 조회 응답으로 돌려준 것이다 — **AI 트레이더는 호가창을 직접 만들지 않는다**
8. 접수 API에 제출한 것과 같은 주문을 주문 기록 모듈이 시간순으로 파일에 남긴다(FR-17)
9. 트레이딩 세션 종료 시 기록 파일을 S3에 업로드한다. 이 파일이 리플레이 엔진(FR-18)의 입력이 된다

### 2.4 왜 페이퍼 트레이딩도 접수 API에 실시간 제출하는가

주문을 파일에 기록만 해두고 접수는 리플레이 모드에서만 하는 방식은 쓰지 않는다. 봇 판단에는 실시간 호가창이 필요한데, 호가창은 매칭 엔진이 실제 주문을 받아야만 존재하는 상태이기 때문이다 — 주문을 보내지 않으면 봇이 참고할 시장 자체가 없다.

페이퍼 트레이딩은 실시간 제출과 파일 기록을 동시에 수행하고, 리플레이는 그 기록을 나중에 배속으로 재생하는 구조다.

## 3. 판단 로직: 봇 5종

각 봇은 시세를 참고해 아래 형태의 **방향 신호**를 생성한다.

```json
{
  "botId": "momentum-01",
  "botType": "MOMENTUM",
  "market": "KRW-BTC",
  "direction": "BUY",
  "strength": 0.6,
  "generatedAt": "2026-08-03T09:00:03.000Z"
}
```

| 봇 | 판단 기준 | 신호 예시 |
|---|---|---|
| 마켓메이커 봇 (전체 주문 50%+) | 항상 매수·매도 동시 호가. 체결되면 즉시 재호가 | `direction: BOTH`, 매수·매도 동시 발생 |
| 모멘텀 추종 봇 | 최근 가격이 상승 추세일 때 매수 | `direction: BUY`, 추세 없으면 신호 없음 |
| 평균회귀 봇 | 가격이 기준선 대비 일정 폭 이상 이격되면 매도 | `direction: SELL`, 이격도에 비례한 strength |
| 노이즈 봇 | 무작위 소량 주문 | `direction`·`strength` 모두 무작위 |
| 대량 주문 봇 | 간헐적으로 큰 수량 1건 | 발동 시에만 `strength: 1.0`급 신호 |

마켓메이커 봇은 매수·매도 두 방향 신호를 동시에 생성해야 하므로 스키마가 다르다.
```json
{
  "botId": "mm-01",
  "botType": "MARKET_MAKER",
  "market": "KRW-BTC",
  "bid": { "direction": "BUY", "strength": 0.9 },
  "ask": { "direction": "SELL", "strength": 0.9 },
  "generatedAt": "2026-08-03T09:00:00.000Z"
}
```

가격이 이동해 기존 호가가 스프레드 밖으로 벗어나면, 마켓메이커 봇은 기존 주문을 취소(`DELETE /v1/orders/{orderId}`)하고 새 가격에 재호가한다 — 다이어그램의 `POST/DELETE 주문`에서 `DELETE`가 쓰이는 경우는 이것이 유일하다. 나머지 4종 봇은 취소를 사용하지 않는다.

비중(마켓메이커 50% 이상 등 FR-16 검증 기준)은 봇 유형별 인스턴스 수와 판단 주기로 조절하며, 실제 비율은 모니터링 화면(FR-25)에서 확인한다.

### 규칙 기반 3종의 알고리즘

LLM을 쓰지 않는 봇은 매 판단 주기마다 아래 규칙을 그대로 계산해 방향 신호를 만든다.

**마켓메이커 봇**
1. 시세 수신 모듈이 가진 최우선 매수호가(best bid)·매도호가(best ask)의 중간값(mid price)을 계산한다. 호가창이 비어 있으면(세션 시작 직후) 최근 체결가를 대신 쓴다.
2. 중간값에서 고정 스프레드만큼 떨어진 두 지점을 매수·매도 호가로 낸다(스프레드 폭은 향후 검토 사항 참고 — 좁을수록 체결은 잘 되지만 봇 손실 위험이 커진다).
3. 기존 호가가 체결되거나 가격 이동으로 스프레드 밖에 놓이면 취소 후 재호가한다(위 문단).

**노이즈 봇**
1. 매 판단 주기마다 고정 확률로 "발동" 여부를 뽑는다. 발동하지 않으면 이번 주기는 신호 없음.
2. 발동 시 방향은 50/50 무작위, 가격은 최우선호가 근처에서 무작위 오프셋, 수량은 소량 범위 내 무작위로 정한다.
3. 어떤 마켓에 낼지도 무작위로 뽑는다 — 봇 인스턴스 하나가 여러 마켓을 순회할지, 마켓마다 전담 인스턴스를 둘지는 향후 검토 사항 참고.

**대량 주문 봇**
1. 매 판단 주기마다 노이즈 봇보다 훨씬 낮은 확률로 발동 여부를 뽑는다.
2. 발동 시에만 방향(무작위 또는 직전 추세 방향)과, 평상시 대비 훨씬 큰 수량을 정한다 — 호가 여러 단계를 관통(sweep)해 부분 체결(FR-07) 검증에 기여하는 게 목적이다.

### LLM 기반 2종에 넣는 판단 데이터

모멘텀 추종 봇·평균회귀 봇은 "추세인가 아닌가", "과열인가 아닌가"라는 정성적 판단이 목적이라 규칙으로 고정하지 않고 Claude에게 맡긴다(2.2절). 대신 판단에 필요한 데이터를 프롬프트에 미리 계산해 넣는다 — Claude가 매번 원시 데이터부터 지표를 계산하게 하면 느리고 일관성도 떨어지기 때문이다.

| 데이터 | 용도 |
|---|---|
| 최근 N개 캔들의 시가·고가·저가·종가·거래량 | 추세·변동성 파악 |
| 최근 가격 변화율(예: 1분·5분·15분 구간) | 모멘텀 추종 봇의 추세 판단 |
| 이동평균 대비 현재가 이격도(%) | 평균회귀 봇의 과열 판단 — 이동평균 계산은 트레이더 쪽에서 미리 해서 전달 |
| 현재 호가창 스프레드, 최우선 매수·매도 잔량 | 유동성 상태 파악 |
| 최근 판단 이력(메모리) | EconAgent 방식의 맥락 유지 |

정확한 캔들 개수·구간·이격도 임계치는 실제 프롬프트 설계·튜닝 단계에서 정한다(향후 검토 사항 참고).

### 설계 근거

모멘텀 추종 봇·평균회귀 봇의 판단 로직은 두 편의 CS 탑티어 논문을 참고해 설계한다.

- **[EconAgent](https://aclanthology.org/2024.acl-long.829/)**(ACL 2024): 이질적인 LLM 에이전트 각각에게 역할(페르소나)과 과거 경험(메모리)을 부여해 하나의 시뮬레이션 시장을 만드는 구조. 봇별 프롬프트를 "역할 프로필 + 최근 판단 이력"으로 구성하는 근거가 된다
- **FinCon**(NeurIPS 2024): 에이전트가 자기 판단을 자연어로 되돌아보고 다음 판단에 반영하는 Conceptual Verbal Reinforcement. 세션 중 자기 피드백(선택 기능)의 근거가 된다

### Claude 연동 (AWS Bedrock)

판단 로직은 Claude를 호출해 방향 신호를 만든다. 팀이 이미 AWS 인프라(EKS·S3·RDS·ElastiCache)를 사용 중이므로, Anthropic에 별도로 결제하는 대신 **AWS Bedrock**을 경유해 호출한다.

- EKS 파드에 IRSA(IAM Roles for Service Accounts)로 부여된 역할로 인증하며, API 키를 코드나 설정 파일에 남기지 않는다(NFR-18). 파드 단위로 권한을 부여하므로 EC2 인스턴스 프로필보다 최소 권한 원칙에 가깝다
- 기본 모델은 `claude-sonnet-5`(Bedrock 모델 ID: `anthropic.claude-sonnet-5`)이며, 호출량 대비 비용이 부담되면 `claude-haiku-4-5`로 낮춘다
- 프롬프트는 역할 프로필(persona, 고정)과 메모리(최근 판단 이력, 매 호출 갱신)로 구성하고, tool_choice로 위 방향 신호 스키마 출력을 강제한다
- 역할 프로필은 매 호출 동일하므로 프롬프트 캐싱 대상이다

```python
from anthropic import AnthropicBedrockMantle
client = AnthropicBedrockMantle(aws_region="us-east-1")
```

## 4. 주문 생성 로직

주문 생성 로직은 판단 로직과 별도의 루프로 동작한다. 매 반복(iteration)마다 활성 상태인 모든 (봇 인스턴스, 마켓) 방향 신호를 순회하며, 신호 하나당 주문 1건을 만들어 접수 API로 보낸다. 새로 판단하지 않고, 3장에서 각 봇이 이미 갱신해둔 신호를 "주문 파라미터로 번역"만 한다.

### 4.1 가격 결정

기준값은 판단 로직이 이미 조회해둔 호가창 스냅샷(최우선 매수·매도호가)을 재사용한다. 주문마다 호가창을 새로 조회하면 접수 API에 불필요한 부하가 생기기 때문이다.

| 신호 | 가격 결정 규칙 |
|---|---|
| 방향성 봇(모멘텀 추종·평균회귀·노이즈·대량 주문)의 BUY | 최우선 매도호가(best ask) 이하에서 결정. strength가 높을수록 best ask에 더 가깝게(공격적으로) |
| 방향성 봇의 SELL | 최우선 매수호가(best bid) 이상에서 결정. strength가 높을수록 best bid에 더 가깝게 |
| 마켓메이커 봇 | 중간가(mid price) 기준 매수·매도 각각 일정 스프레드만큼 떨어뜨려 결정. 스프레드가 좁을수록 체결 확률은 높고 봇의 손실 위험은 커짐 |

모든 가격은 마켓별 호가 단위(tick size)의 배수로 반올림한다(`INVALID_PRICE_UNIT` 방지, [API 명세서](api-specification.md) 4장).

### 4.2 수량 결정

마켓·봇 유형별 기준 수량 범위 안에서 무작위로 뽑고, strength에 비례해 조정한다. 노이즈 봇은 기준 범위를 좁게, 대량 주문 봇은 발동 시에만 범위를 훨씬 크게 잡는다. 정확한 기준값은 마켓별 평균 체결 수량을 참고해 튜닝 단계에서 정한다(향후 검토 사항 참고).

### 4.3 같은 신호로 여러 주문을 내는 방식

판단 주기와 주문 생성 주기는 별개다(앞서 설명). 신호가 갱신되지 않은 채로 다음 반복이 와도, 주문 생성 로직은 같은 신호를 다시 읽어 새 주문을 만든다. 이때 4.1·4.2의 가격·수량 계산에 매번 소폭의 무작위 지터를 더해, 같은 방향이라도 매 주문의 가격·수량이 조금씩 달라지게 한다 — 완전히 동일한 주문이 반복 제출되는 것을 피하기 위함이다.

방향 신호가 얼마나 오래 유효한지(다음 판단 갱신 전까지 계속 쓰는지, 일정 시간이 지나면 무효 처리하는지)는 아직 정해지지 않았다(향후 검토 사항 참고).

### 4.4 접수 API 연동

```json
{
  "market": "KRW-BTC",
  "side": "BUY",
  "price": "71500000",
  "quantity": "0.015"
}
```

- `Idempotency-Key`는 봇 인스턴스 ID와 시퀀스 번호를 조합해 발급한다
- `429`(컨슈머 랙 초과) 응답 시에는 즉시 재시도하지 않고 다음 판단 주기까지 대기한다. 즉시 재시도는 NFR-13(지연 대신 즉시 거절)의 취지를 무력화하므로 지양한다
- `400`(유효성 오류) 응답은 로그만 남기고 해당 주문은 폐기한다
- `DELETE /v1/orders/{orderId}`는 마켓메이커 봇이 기존 호가를 취소하고 재호가할 때만 호출한다. 나머지 4종 봇은 취소를 사용하지 않는다

## 5. 주문 기록 (FR-17)

접수 API에 제출한 주문 전량을 시간순으로 파일에 기록해 트레이딩 세션 종료 시 S3에 저장한다(제출 시각, 마켓, 방향, 가격, 수량, 봇 ID, 주문 번호). 이 파일이 리플레이 엔진(FR-18)의 유일한 입력이므로, 판단 과정의 중간값(방향 신호)은 포함하지 않고 최종 주문 파라미터만 남긴다. 정확한 파일 포맷은 API 규격과 마찬가지로 별도 규격 문서에서 확정한다(FR-22).

**봇 인스턴스가 여러 파드로 분산될 때**: 봇 유형별로 여러 인스턴스(파드)를 띄우면 각 파드가 독립적으로 주문을 생성·기록한다. 파드마다 별도 파일로 기록해 S3에 저장하며(파일명에 파드 ID 포함), 한 파일에 여러 파드가 동시에 쓰지는 않는다 — S3는 여러 writer의 동시 append를 지원하지 않기 때문이다. 각 레코드에는 정확한 제출 시각이 남아 있으므로, 파드 하나 안에서는 자연히 시간순이 보장되고, 파드 간 전체 시간순은 세션 종료 후 여러 파일을 제출 시각 기준으로 병합(merge)해 복원한다. 이 병합을 트레이더가 세션 종료 시 수행해 단일 파일로 올릴지, 여러 파일을 그대로 두고 리플레이 엔진이 읽을 때 병합할지는 리플레이 엔진과의 접점이므로 별도 설계 문서에서 확정한다(향후 검토 사항 참고).

## 6. 기타 고려사항

| 항목 | 내용 |
|---|---|
| 인프라 | 전용 EKS 클러스터에서 Kubernetes Job으로 실행한다(전체 아키텍처는 [architecture.md](architecture.md) 참고). 백엔드(접수 API·매칭 엔진)와는 별도 클러스터다 — 리플레이 엔진이 매칭 엔진에 부하를 주는 성능 시험과 AI 트레이더 세션이 동시에 실행돼도 자원 경합으로 측정값이 왜곡되지 않게 하기 위함이다. 트레이딩 세션 단위로 시작·종료되는 워크로드라 상시 기동되는 EC2보다 Job 모델이 적합하다. 봇 유형별로 컨테이너를 분리하면 장애 격리와 비중 조절(레플리카 수 조정)이 용이하다 |
| 환경 분리 | 접수 API 엔드포인트를 설정값으로 분리해 Mock으로도 독립 시험이 가능해야 한다(FR-23) |
| 모니터링 | 봇 유형·인스턴스별 주문 생성 수를 지표로 노출하고(FR-25), 요청에 `X-Request-Id`를 포함한다(FR-21) |
| 성능 | AI 트레이더 자체는 NFR-01/02(초당 1만 건) 목표를 직접 만들 필요가 없다. 모든 성능 측정은 리플레이 모드(FR-18) 기준이며, 페이퍼 트레이딩이 만든 주문을 배속 재생해 목표 처리량을 낸다. AI 트레이더는 현실적인 패턴만 만들면 된다 |
| 장애 시 | 페이퍼 트레이딩은 실행마다 판단이 달라지는 것이 정상이므로 판단 상태 복구는 불필요하다. 다만 주문 기록 파일의 이어쓰기 여부는 별도 결정이 필요하다(향후 검토 사항 참고) |

## 7. 구현 개요

- **스택**: Python(비동기) — 시세 수집기 API 호출, Claude 호출, 접수 API 전송을 모두 비동기로 처리
- **핵심 라이브러리**: `anthropic`(Bedrock 클라이언트 포함), `httpx`, `pydantic`, `boto3`
- **구현 순서**: ① 규칙 기반 3종 봇(마켓메이커 봇·노이즈 봇·대량 주문 봇) + 목업 접수 API로 기본 파이프라인 완성 → ② 시세 수집기 연동(매니페스트/파일 API, HTTP) → ③ Claude 기반 2종 봇(모멘텀 추종 봇·평균회귀 봇) 추가 → ④ 주문 기록·S3 업로드 → ⑤ 오류 처리·모니터링 훅 → ⑥ 컨테이너화 후 EKS 배포(Kubernetes Job)
- 매칭 엔진 구현을 기다리지 않고 독립적으로 개발·시험하기 위해(FR-23) 목업 접수 API로 1단계부터 시작한다

## 8. 향후 검토 사항
- 봇별 비중(인스턴스 수, 판단 주기)을 코드 상수와 설정 파일 중 어느 방식으로 관리할지
- 판단 주기·봇 인스턴스 수에 따른 실제 Bedrock 호출 비용 산정
- 주문 기록 파일의 정확한 필드·포맷 확정(FR-22)
- 트레이딩 기간 시세가 부분 수집된 상태에서 트레이더가 소비를 시작할 수 있는지
- 재시작 시 주문 기록 파일 이어쓰기 여부
- 여러 파드가 만든 주문 기록 파일을 시간순으로 병합하는 책임을 트레이더와 리플레이 엔진 중 어디에 둘지
- 봇·마켓별 기준 수량 범위, 마켓메이커 봇의 스프레드 폭 등 주문 생성 로직의 실제 수치
- 방향 신호의 유효 기간(TTL) — 다음 판단 갱신 전까지 계속 쓸지, 일정 시간 후 무효 처리할지
- 노이즈 봇 인스턴스가 여러 마켓을 순회할지, 마켓마다 전담 인스턴스를 둘지
- LLM 프롬프트에 넣을 캔들 개수·구간·이격도 임계치 등 실제 지표 설계
- 리플레이 엔진과의 인터페이스는 별도 설계 문서에서 확정
