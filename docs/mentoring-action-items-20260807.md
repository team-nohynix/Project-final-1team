# 멘토링 액션 아이템 대응 (2026-08-07)

정리: 양지훈 / 대상 멘토링: 2026-08-07 (현업 AWS MSP 이사님) / 다음 멘토링까지 준비할 답변

## 문서의 목적

2026-08-07 멘토링에서 나온 액션 아이템에 대해 **"왜 그렇게 했는가"를 멘토가 되물었을 때 한 번에 답할 수 있는 수준**으로 근거를 정리한 문서다. 멘토가 반복해서 강조한 원칙은 세 가지였다.

1. **의뢰받은 시스템이라면 고객 요구사항부터 정리하고, 거기서 솔루션을 끌어내야 한다** — 기술을 먼저 고르고 이유를 붙이는 건 순서가 거꾸로다.
2. **모든 기술 선택에는 당위성이 있어야 한다** — "이걸로도 되는데 왜 그것이냐"에 답할 수 없으면 그 선택은 근거가 없는 것이다.
3. **비용을 이펙티브하게 쓰는 것(FinOps)이 클라우드의 핵심 역량이다** — AWS 네이티브 서비스를 쓰는 것 자체가 답이 아니다.

그래서 이 문서는 **1장에서 고객의 현재 환경(AS-IS)과 핵심 요구사항 5개(RQ-01~05)를 정의하고, 2장 이후의 모든 기술 결정을 그 RQ 번호에서 끌어낸다.**

요구사항은 **쿠버네티스 강제력 순으로 정렬**했고, **RQ-01은 멘토가 결정적 근거로 지목한 "24시간 무중단 + 잦은 배포"**다. 각 요구사항은 `현재 겪는 문제 → 고객의 요구 → 정량 기준 → 요구되는 능력 → 적용 기술 → 이 요구가 잘라내는 것` 순으로 쓴다.

> **답변을 2단 관문으로 나눈 이유**: "컨테이너 오케스트레이터가 필요하다"와 "쿠버네티스여야 한다"는 **다른 명제**다. 앞의 것만 논증해놓고 쿠버네티스를 결론으로 내면 *"그럼 ECS는요? AWS 쓰면서 굳이 K8s를 얹는 이유는요?"*에서 막힌다. 멘토가 물은 것은 **"딱 쿠버네티스만 되는 이유"**이므로, 5개 요구사항 각각에 **① EC2 직접 운영·Lambda를 자르는 부분**과 **② ECS까지 자르는 부분**을 함께 적었다.

## 1. 고객 요구사항 — 가상 고객사 의뢰 (액션 아이템 ①)

> "이 거래소를 운영할 거예요? 아니면 만들어달라는 걸 의뢰받았어요? … 의뢰를 받았다면 사용자의 요구사항이 있을 거예요. 이 요구사항을 정리를 해야죠. 그래서 어떻게 솔루션을 풀어갈 거냐. 이런 고객의 니즈들을 여러분들 스스로가 만들고 그걸로 솔루션에 반영을 하는 거예요."

### 1.1 고객과 현재 환경 (AS-IS)

**고객**: 국내 가상자산 거래소 **A거래소** (가칭)
**의뢰 내용**: **대량 주문에도 강건한 가상화폐 거래 시스템 구축**

A거래소는 **이미 AWS(서울 리전)를 쓰고 있다.** 다만 수년 전 자체 IDC에서 리프트 앤 시프트로 옮긴 뒤 구조를 바꾸지 않아, **"AWS 위에서 온프레미스처럼 운영"**하는 상태다.

| 항목 | 현재 상태 (AS-IS) |
|---|---|
| **실행 방식** | EC2 인스턴스에 애플리케이션 바이너리를 **직접 설치**(컨테이너 미사용). systemd 유닛으로 기동 |
| **종목 배치** | **인스턴스에 종목을 고정 할당.** `matching-01` 인스턴스가 BTC·ETH를 맡는 식이고, 할당표는 설정 파일에 하드코딩 |
| **배포** | Ansible로 아티팩트를 각 인스턴스에 밀어 넣고 프로세스 재시작 → **점검 공지 후 새벽에 배포** |
| **확장** | 웹 계층만 ASG(**CPU 기준**). 매칭 계층은 종목 고정 할당 때문에 **대수 고정**이고, 증설은 담당자가 인스턴스를 수동 추가한 뒤 할당표를 다시 작성 |
| **신규 컴포넌트 추가** | 컴포넌트가 하나 늘면 **EC2 인스턴스 그룹을 새로 띄운다.** 기존 인스턴스에 같이 올리면 ① CPU·메모리를 서로 잠식하고 ② 인스턴스 프로파일이 하나뿐이라 IAM 권한까지 섞이기 때문. 그래서 관행적으로 **1 컴포넌트 = 1 인스턴스 그룹**이고, 대부분 유휴 상태로 **상시 과금**(일부는 RI로 선구매까지 해둔 상태) |
| **권한** | **인스턴스 프로파일 1개를 그 인스턴스의 모든 프로세스가 공유** |
| **관측** | CloudWatch 기본 지표 + 인스턴스마다 에이전트를 수동 설치. 새 인스턴스에 설치를 빠뜨려 못 보고 지나간 장애가 있었음 |
| **배치 작업** | 검증·정산 배치는 별도 EC2에서 cron으로 실행. 배포 스크립트·권한·모니터링 체계가 서비스 계층과 **완전히 별개** |

|---|---|---|---|---|
| **RQ-01** | **24시간 무중단 운영과 잦은 배포** ★ | 점검 창 0분, 당일 패치, 무인 자가 복구, 즉시 롤백, AZ 장애 지속 | **O** | — |

#### 1.2.1 RQ-01 — 24시간 무중단 운영과 잦은 배포 ★

**현재 겪는 문제 (AS-IS)**

- 배포가 곧 **인스턴스 위 프로세스 재시작**이다. Ansible로 아티팩트를 밀어 넣고 systemd를 재기동하는 동안 그 인스턴스가 담당하는 종목은 **주문을 받지 못한다.** 그래서 배포 때마다 **새벽 점검 공지**를 내야 한다.
- 그런데 **가상자산은 장 마감이 없다.** 새벽에도 거래량이 적지 않아 "점검해도 되는 시간"이 실제로는 존재하지 않는다. 그 결과 **급한 버그 수정도 다음 점검 창까지 며칠씩 밀린다.**
- **롤백은 더 느리다.** 문제가 나면 이전 아티팩트를 다시 빌드해 다시 밀어 넣어야 해서 수 분이 걸린다. 그 사이 장애가 이어진다.
- 새벽에 프로세스가 죽으면 **당직자가 깨서 수동으로 재기동**한다. 기동 중인 인스턴스로 주문이 들어가 실패한 사례도 있었다 — ELB 헬스체크가 "포트가 열렸는가"만 보기 때문에, 호가창 복구가 끝나기 전에 트래픽이 들어왔다.
- 인스턴스가 어느 AZ에 몰려 있는지는 **사람이 엑셀로 관리**하는데, 실제로 한 번 틀려서 같은 역할 프로세스가 한 AZ에 몰려 있었다.

**고객의 요구**

> "경쟁사가 신규 코인이랑 주문 유형을 계속 낸다. 우리도 **기능을 수시로 내고 버그는 당일 패치**해야 한다. 그런데 **가상자산은 24시간 장이라 점검 창이 없다.** 배포한다고 서비스를 멈출 수는 없다."
> "문제를 발견하면 **1분 안에 되돌아가야** 한다. 되돌리려고 다시 빌드하는 건 말이 안 된다."
> "새벽 3시에 프로세스가 죽어도 **사람 없이** 살아나야 하고, **'살아 있음'과 '주문 받을 준비가 됐음'을 구분**해달라."
> "데이터센터 한 곳이 나가도 거래는 계속돼야 하고, **같은 역할 프로세스가 한 곳에 몰리지 않게 알아서 흩어놔달라.**"

**합의한 정량 기준**

- **일 단위 배포**를 전제로 하는 배포 체계, 계획 점검 시간 **0분**
- **거래 중 배포 시 실패 주문 비율 0.1% 이하**
- 롤백 **1분 이내**, 재빌드 없이 직전 정상 버전으로 복귀
- 프로세스 강제 종료 후 **60초 이내 처리 재개**, 무인. 기동 중인 인스턴스에 트래픽 유입 **0건**
- AZ 1개 장애에도 거래 지속, **동일 역할 프로세스의 AZ 분산이 자동 유지**

**요구되는 능력**

- 배포 단위가 **분 단위로 교체 가능할 만큼 가벼울 것** (아티팩트를 서버에 밀어 넣고 재시작하는 방식이 아닐 것)
- 무중단 순차 교체 + 헬스 판정 + 최소 가용성 보장이 **플랫폼 기본 기능**일 것
- 배포 이력이 **선언적 리비전**으로 남아 되돌리기가 "이전 리비전 재적용"으로 끝날 것
- 생존 판정(liveness)과 트래픽 수용 판정(readiness)이 **분리**되고, 후자 통과 시에만 라우팅에 편입될 것
- 배치 제약(같은 역할은 다른 장애 도메인에)을 **선언하면 플랫폼이 매 배치마다 강제**할 것

**적용 기술** — **컨테이너 이미지 = 배포 단위 + 롤링 업데이트 + PDB + probe 3종 + topologySpread + GitHub Actions CI/CD**

- `maxUnavailable: 0` 롤링 업데이트로 새 파드가 **readiness 통과 후에만** 트래픽을 받고 그때 구 파드를 내림 → 배포 중 실패 주문이 원천적으로 발생하지 않음
- `PodDisruptionBudget`으로 종목별 최소 가용성 유지
- 롤백은 이전 ReplicaSet이 스케일 0으로 남아 있어 **`rollout undo` / `helm rollback` = 이전 리비전 재활성화** (재빌드 없음)
- `livenessProbe`는 프로세스 생존만, **`readinessProbe`는 호가창 복구 완료 + Kafka 파티션 할당 완료일 때만 통과** → 복구 중인 파드는 Service 엔드포인트에서 제외돼 주문이 유입되지 않음. `startupProbe`로 초기 복구 시간 확보
- `topologySpreadConstraints`(`maxSkew: 1`, `whenUnsatisfiable: DoNotSchedule`)로 AZ 균등 배치를 스케줄러가 강제 — 엑셀 관리가 사라짐
- 파이프라인: push → 테스트(실패 시 병합 차단) → 이미지 빌드 → ECR(커밋 SHA 태그) → `helm upgrade` (상세 2.6절)

**이 요구가 잘라내는 것**

- **EC2 직접 운영 X** — AMI 재빌드(수십 분) 또는 인스턴스 순차 교체(OS 부팅부터, 수 분). 점검 창 0분 + 실패 주문 0.1% 이하를 맞출 수 없고, 60초 내 재개도 어렵다. ASG는 인스턴스를 AZ에 분산할 뿐 **그 위 프로세스 배치에는 관여하지 않는다**
- **ECS O** — ECS도 롤링 업데이트·태스크 정의 리비전 롤백·헬스체크·AZ spread를 제공한다. **이 요구만으로는 쿠버네티스가 확정되지 않는다**

> **이 항목이 1순위인 이유**: 멘토가 "딱 쿠버네티스만 되는 이유"를 물었을 때 시작점이 되는 흐름이 이것이다 — **빈번한 배포 → CI/CD 필수 → 컨테이너가 배포 단위 → 오케스트레이터.** 나머지 요구를 다 만족시켜도 이것 하나가 남으면 현재 방식(EC2 + Ansible)으로는 갈 수 없다.

#### 1.2.2 RQ-02 — 하나의 인프라·하나의 운영 체계

**현재 겪는 문제 (AS-IS)**

- **컴포넌트가 하나 늘 때마다 EC2 인스턴스 그룹이 하나 는다.** 기존 인스턴스에 같이 올릴 수 없는 이유가 두 가지다 — ① CPU·메모리를 서로 잠식해 거래 처리 성능이 흔들리고 ② **인스턴스 프로파일이 하나뿐이라 IAM 권한까지 합쳐진다.**
- 그 결과 대부분의 인스턴스가 **유휴 상태로 상시 과금**되고, 일부는 RI로 선구매까지 해둬 줄이지도 못한다.
- 권한 문제는 감사에서 실제로 지적받았다 — **시세 수집 프로세스가 같은 서버에 있다는 이유만으로 거래 DB 자격 증명에 접근할 수 있는 구조**였다.
- **검증·정산 배치는 별도 EC2에서 cron으로 하루 종일 떠 있다.** 실제로 도는 시간은 하루 몇 분인데 인스턴스는 24시간 과금된다.
- 그리고 **서비스 / 배치 / 모니터링 에이전트가 각각 다른 방식으로 관리된다.** 배포 스크립트도 따로, 권한 설정도 따로, 모니터링도 따로다. 새 인스턴스에 모니터링 에이전트 설치를 빠뜨려 **못 보고 지나간 장애**가 있었다.

**고객의 요구**

> "컴포넌트를 붙일 때마다 **인스턴스 그룹을 새로 띄우는 걸 멈추고 싶다.** 그런데 같이 올리면 서로 CPU를 잡아먹고 권한도 섞인다. **한 서버에 여러 컴포넌트를 올리되 서로 침범하지 않게** 해달라."
> "**같은 서버에 있다는 이유로 권한을 같이 쓰면 안 된다.** 감사 지적 사항이다."
> "검증용 부하 생성기와 분석 배치가 **거래 처리 성능을 절대 건드리면 안 된다.** 그렇다고 용도별로 인프라를 따로 잡아주진 못한다."
> "운영자가 버튼을 누르면 검증 작업이 **그때 떠서 끝나면 사라져야** 한다. 하루 종일 떠 있는 건 그만하고 싶다."
> "그리고 **서비스든 배치든 에이전트든 하나의 방식으로 통일**해달라. 운영 인력이 몇 명 안 되는데 체계가 세 갈래면 감당이 안 된다. **새 컴포넌트가 모니터링에 자동으로 잡혀야** 하고."

**합의한 정량 기준**

- 컴포넌트 수 증가가 **인스턴스 그룹 증가로 직결되지 않을 것**, 평상시 컴퓨트 사용량 **피크 대비 25% 이하**
- 검증·분석 워크로드가 도는 동안에도 거래 처리 지표에 **측정 가능한 영향 0**
- 자격 증명 하드코딩 **0건**, **프로세스 단위 최소 권한** (같은 서버라도 프로세스마다 권한이 다를 것)
- 일회성 작업은 **온디맨드 실행 + 완료 후 자원 자동 회수**, 재시도·실행 시간 상한 설정 가능
- 상시 서비스·일회성 작업·노드 에이전트를 **하나의 배포 파이프라인, 하나의 권한 모델, 하나의 관측 체계**로 관리. 새 유형 추가 시 **신규 관리 도구 도입 0건**
- **신규 컴포넌트가 사람 개입 없이 모니터링 대상에 자동 편입**

**요구되는 능력**

- **자원 할당 단위와 격리 단위가 분리**되어 있을 것 — 여러 워크로드를 한 서버에 모으면서(집적), 워크로드마다 **자원 상한·전용 노드·우선순위를 선언하면 플랫폼이 강제**할 것(격리)
- IAM 권한 부여 단위가 **서버가 아니라 프로세스**일 것
- **완료 상태를 갖는 일회성 작업**을 표준 리소스로 다룰 것
- 성격이 다른 워크로드(장기 실행 / 완료형 / 노드 상주)를 **같은 API·같은 배포 단위·같은 권한 모델**로 다룰 것
- 플랫폼이 워크로드 목록을 **API로 제공**해 모니터링이 자동 발견할 수 있을 것

**적용 기술** — **파드 `requests` 기반 bin packing + 네임스페이스·taint·ResourceQuota·PriorityClass + IRSA + Job + 단일 K8s API**

- **집적**: 컴포넌트는 `resources.requests`만 선언하고 **배치는 스케줄러가 남는 자리를 찾아 결정** → 컴포넌트가 늘어도 인스턴스 그룹이 늘지 않음. Karpenter Consolidation이 피크 후 파편화된 노드를 압축(4.2절 ②)
- **격리는 인스턴스를 나누는 게 아니라 선언으로**: 측정 대상(`backend`)은 `workload=backend:NoSchedule` taint가 걸린 전용 노드그룹에만, 부하 생성기(`replay`)·AI 트레이더·수집기는 각각 전용 Fargate Profile(파드 1개 = microVM 1개), 네임스페이스별 `ResourceQuota`, `backend`에 높은 `PriorityClass`
- **권한**: OIDC provider 1개를 공유하되 신뢰 정책의 `sub` 조건(`system:serviceaccount:<ns>:<sa>`)으로 **파드별 권한 분리** → 같은 노드에 있어도 `sa-collector`는 RDS 접근 권한 자체가 없음. MSK는 SASL/IAM이라 관리할 시크릿 0개
- **일회성 작업**: **Job**의 `backoffLimit`·`activeDeadlineSeconds`·`ttlSecondsAfterFinished`가 고객 요구 조항과 1:1 대응 (상세 3장)
- **운영 체계 단일화**: Deployment / StatefulSet / **Job** / CronJob / **DaemonSet**이 모두 **같은 API 서버·같은 RBAC·같은 스케줄러** 아래 있다. Helm chart 하나에 함께 들어가고, 권한은 전부 ServiceAccount + IRSA 한 모델
- **관측 자동 편입**: `ServiceMonitor`/`PodMonitor` 라벨 셀렉터에 걸리면 신규 파드가 자동 스크레이프 대상 — **에이전트 설치 작업 자체가 사라짐** (상세 7.3절)

**이 요구가 잘라내는 것**

- **EC2 직접 운영 X** — **집적과 격리가 동시에 성립하지 않는다.** EC2에서 격리 수단은 "인스턴스를 나누는 것"뿐이라, 격리하면 비용 요구를 어기고 집적하면 격리 요구를 어긴다. 한 인스턴스에서 cgroup·systemd 슬라이스로 상한을 직접 관리할 수는 있으나 그건 **스케줄러를 직접 만드는 일**이다. 인스턴스 프로파일이 서버 단위라 권한 요구도 불가
- **ECS △ → 부분적으로 X** — 집적(bin packing 배치 전략)·격리(태스크 단위 예약)·프로세스 단위 권한(Task Role)까지는 ECS도 된다. 그러나 **"하나의 운영 체계"는 성립하지 않는다.** ECS에서 이질 워크로드를 다루면 **상시 서비스는 ECS Service, 본격 배치는 AWS Batch(별도 서비스), 노드 에이전트는 daemon 전략**으로 갈라진다 — 상세는 2.5절 ③

#### 1.2.3 RQ-03 — 거래 정합성과 처리기 단일 소유권

**현재 겪는 문제 (AS-IS)**

- 종목을 **인스턴스에 고정 할당**하고, 그 할당표를 **설정 파일에 하드코딩**해 관리한다. 대수를 늘리거나 줄이려면 담당자가 할당표를 다시 쓰고 배포해야 한다.
- 문제는 **대수가 바뀌는 그 순간**이다. 이전 인스턴스가 아직 해당 종목을 처리하고 있는데 새 인스턴스가 같은 종목을 잡아버려 **두 프로세스가 같은 호가창을 동시에 만졌고, 중복 체결 사고**가 났다.
- 자체적으로 분산 락과 재할당 로직을 짜서 넣었지만 **그 로직이 틀렸다.** 정상 종료 경로에서는 소유권을 반납하는데, 비정상 종료나 배포 중 겹치는 구간에서는 반납이 누락됐다.
- 결과적으로 **"대수를 바꾸는 것" 자체가 위험한 작업**이 되어, 부하가 몰려도 매칭 계층은 대수를 건드리지 못하고 고정 운영 중이다.

**고객의 요구**

> "돈이 걸린 일이다. **한 종목은 반드시 처리기 한 대만** 담당해야 한다. 그런데 우리는 처리기를 늘리고 줄이는 **바로 그 순간에** 두 대가 같은 종목을 잡아서 **중복 체결 사고**가 났다. 종목 재할당을 우리가 직접 짠 로직으로 하고 있었는데, 그게 틀렸다."
> "**대수가 바뀌는 도중에도 이중 소유가 0이어야** 한다. 이번엔 우리가 짜는 게 아니라 **플랫폼이 보장**하게 해달라."

**합의한 정량 기준**

- 순서 역전 **0건**, 접수 응답한 주문의 유실 **0건**, 중복 체결 **0건**
- 매수·매도 총량 정확히 일치
- **처리기 증감 중 동일 종목 이중 소유 구간 0초**

**요구되는 능력**

- 처리기마다 **플랫폼이 부여하는 안정적인 고유 신원**이 있을 것 (설정 파일에 사람이 적는 방식이 아닐 것)
- 대수 변경 시 **플랫폼이 순차적으로**(한 번에 한 대씩, **이전 것이 완전히 종료된 것을 확인한 뒤** 다음 것) 교체해 줄 것

**적용 기술** — **Kafka 파티션 키 고정 + StatefulSet 순번 신원 + `OrderedReady` + `preStop` 소유권 반납**

- ① 파티션 키 = **종목명** → 같은 종목은 항상 같은 파티션, 파티션 내 순서 보장
- ② 매칭 엔진을 **StatefulSet**으로 배포해 `matching-0…19` **순번 신원**을 플랫폼이 부여 → 종목 할당을 순번에서 결정적으로 계산 (**사람이 관리하는 할당표가 사라짐**)
- ③ `podManagementPolicy: OrderedReady`로 **이전 파드가 완전히 종료된 뒤** 다음 파드 시작
- ④ `preStop` 훅에서 컨슈머 그룹 leave + 소유권 반납 후 종료
- ⑤ PDB로 동시 중단 상한 1
- **자체 분산 락을 짜지 않는다** — 고객이 실패한 지점이 정확히 거기이므로

**이 요구가 잘라내는 것**

- **EC2 직접 운영 X** — 리더 선출·임대 갱신·소유권 반납·순차 교체를 처음부터 직접 구현해야 한다. **고객은 이미 그걸 만들었다가 사고를 냈다**
- **Lambda X** — 동시 실행 인스턴스 수를 제어할 수 없어 소유권 자체를 표현할 수단이 없다
- **ECS X** — ECS 서비스의 태스크에는 **순번 신원(ordinal identity)이 없다.** 태스크 ID는 매번 새로 발급되는 임의 값이라 "몇 번째인지"를 플랫폼이 보장하지 않는다. 배포 시 `minimumHealthyPercent`/`maximumPercent`로 **비율**은 제어해도 **"이전 것이 완전히 죽은 뒤 다음 것"이라는 순서 보장은 없다.** 결국 고객이 실패했던 자체 구현으로 되돌아간다
- **K8s O** — StatefulSet이 이 두 가지(순번 신원 + 순차 교체)를 정확히 표준 기능으로 제공한다

#### 1.2.4 RQ-04 — 대량 주문 대응과 한계 동작

**현재 겪는 문제 (AS-IS)**

- 시세 급변 구간에 주문이 폭증하면 **체결이 수 초 이상 밀린다.** 사용자는 주문이 들어갔는지도 알 수 없다.
- 자동 확장이 있긴 한데 **웹 계층만, 그것도 CPU 기준**이다. 그런데 실제로 겪은 건 **"CPU는 멀쩡한데 주문만 밀리는"** 상황이었다 — 병목이 CPU가 아니라 처리 대기 중인 메시지 양이기 때문이다. CPU 기준 ASG는 아무것도 하지 않았다.
- 매칭 계층은 RQ-03의 이중 소유 위험 때문에 **대수를 아예 못 늘린다.** 결국 증설은 담당자가 새벽에 깨서 수동으로 한다.
- 감당 못 할 부하가 들어왔을 때 **정해진 동작이 없다.** 요청이 그냥 쌓이고 응답이 늘어지다가, 클라이언트 재시도가 겹쳐 상황이 더 나빠진다.
- 그리고 **성능을 숫자로 증명한 적이 없다.** "이 시스템이 몇 건까지 버티는가"에 대한 답이 없어서 용량 계획도 감으로 한다.

**고객의 요구**

> "주문이 평소의 수십 배로 몰려도 밀리지 않아야 한다. 그리고 **CPU 보고 늘리지 마라.** **실제로 밀려 있는 주문량**을 보고 늘려야 한다. 사람이 새벽에 깨서 늘리는 것도 안 된다."
> "주문 넣고 결과가 바로 떠야 한다. 호가창은 실시간처럼 보여야 하고."
> "감당 못 할 만큼 몰리면 어떻게 되는지 **미리 정해달라.** 다만 **주문을 조용히 버리는 건 절대 안 된다.**"
> "말로만 버틴다고 하지 말고 **실제로 버티는지 인수 시험으로 증명**해달라. 같은 조건으로 몇 번이든 재현할 수 있어야 한다."

**합의한 정량 기준**

- 주문 접수·체결 각 **초당 1만 건** (= 동시 주문 사용자 **1,250명**, 산출 근거는 1.3절)
- **처리 대기량(메시지 백로그) 기준** 자동 증설, 임계 초과 감지 후 **2분 이내 증설 완료**, 사람 개입 0회
- 주문 제출 → 체결 결과 **p99 0.5초**, 접수 응답 p99 0.1초, 호가창 조회 p95 0.05초
- 수용 한도 초과 시 동작을 **계약서에 명문화**. 접수 응답을 준 주문은 어떤 상황에서도 **유실 없음**
- 목표 부하를 **재현 가능한 형태로 생성**해 위 기준을 실측 증명. 동일 입력 재생 시 결과 동일

**요구되는 능력**

- **메시징 시스템의 대기량을 직접 읽어** 스케일 기준으로 삼을 것 (지표를 다른 시스템에 옮겨 적는 경로를 거치지 않을 것)
- 처리 단위 증설이 **초 단위**일 것
- 주문 응답 경로에 디스크 왕복이 없을 것 (= 처리기가 상태를 메모리에 들고 오래 살 것)
- 과부하를 감지해 유입을 스스로 차단하는 백프레셔 경로
- 측정 중 **플랫폼이 임의로 자원을 재배치하지 않도록 통제**할 수 있을 것

**적용 기술** — **KEDA + Karpenter 2단 스케일 + 인메모리 호가창 + 3계층 오버플로우 + 리플레이 엔진**

- **증설**: `KEDA ScaledObject`(kafka scaler)가 **브로커를 직접 폴링**해 컨슈머 랙을 읽고 매칭 엔진 **파드**를 늘림(기존 노드 위 수 초) → 노드가 모자라면 `Karpenter NodePool`이 EC2 Fleet API를 직접 호출(45~60초). CPU 지표는 배제. 파드 상한은 종목 수와 같은 **20**
- **응답 속도**: 매칭 엔진이 호가창을 **프로세스 메모리**에 유지, 조회는 Redis 사본. RDS 쓰기는 Kafka `executions` 뒤 **비동기 경로**로 분리해 응답 경로에서 완전히 제외 (상세 5.3절 ①)
- **한계 동작**: L1 정상 / L2 Kafka 적재 후 **순차 처리**(202, 체결 지연 허용) / L3 랙 임계 초과 시 `429 + Retry-After` **즉시** 반환. **드랍 경로 없음** — 스케일아웃 트리거와 거절 트리거가 **같은 랙 지표** (상세 6.2절)
- **재현성**: 기록된 주문 파일을 **판단 로직 재실행 없이 그대로 재생**해 입력 고정. 측정 구간에는 Karpenter `budgets: nodes "0"`과 PDB로 **자발적 재배치를 차단** (상세 4.2절 ⑤·6.3절)

**이 요구가 잘라내는 것**

- **EC2 직접 운영 X** — 커스텀 지표 퍼블리셔를 직접 만들어야 하고, 증설 단위가 인스턴스라 OS 부팅부터 시작해 2분을 못 맞춘다
- **Lambda X** — 인메모리 호가창을 유지할 수 없어 p99 0.5초를 지킬 수 없다
- **ECS △→X** — ECS Application Auto Scaling은 **CloudWatch 지표 기반**이다. Kafka 랙으로 스케일하려면 ① 우리가 랙을 CloudWatch에 퍼블리시하고 ② 지표 해상도를 거쳐 ③ 알람이 평가되는 경로를 지나야 한다. 2분 예산에서 이 왕복은 부담이 크고, **우리가 만들어 유지할 컴포넌트가 하나 는다.** KEDA는 브로커 직접 폴링이라 중간 경로가 없다

#### 1.2.5 RQ-05 — 환경 재현성과 클라우드 비종속

**현재 겪는 문제 (AS-IS)**

- 개발·검증·운영 환경이 **각각 다른 Ansible 플레이북**으로 만들어져 있다. 시간이 지나면서 갈라져서 지금은 구성이 서로 다르다.
- 그래서 **"개발에선 됐는데 운영에서 안 된다"**가 반복된다. 원인 파악에 시간이 걸리고, 결국 운영에서 직접 고치면서 격차가 더 벌어진다.
- 한편 경영진 차원에서 **자체 IDC 회귀를 검토 중**이다. 규제 대응(자산 관련 데이터의 물리적 통제)과 비용 양쪽 이유다. 그런데 **현재 구성은 ASG·시작 템플릿·CloudWatch 알람에 묶여 있어 AWS 밖으로 가져갈 수 없다.**
- 즉 지금 새 시스템을 AWS 전용 기술로 다시 만들면 **3년 뒤에 또 처음부터 만들어야 한다.**

**고객의 요구**

> "개발·검증·운영 환경을 **같은 정의로** 만들어달라. 지금은 환경마다 플레이북이 갈라져서 '개발에선 됐는데'가 반복된다."
> "그리고 **3년 내 자체 IDC 회귀를 검토 중**이다. 규제 대응과 비용 양쪽 이유다. **특정 클라우드 사업자 없이는 못 도는 구조는 피해달라.**"

**합의한 정량 기준**

- 세 환경을 **동일한 배포 정의 + 환경별 값 분리**로 구성
- 애플리케이션 실행 계층이 **클라우드 사업자 계정·API 없이도 기동 가능**할 것

**요구되는 능력**

- 워크로드 정의가 **인프라 사업자와 분리된 선언적 표준 형식**일 것
- 그 정의를 해석해 실행하는 **컨트롤 플레인 자체를 자체 인프라에서 돌릴 수 있을 것**

**적용 기술** — **단일 Helm chart + 환경별 values, 표준 K8s API만 사용, 엔드포인트는 ExternalName/Route53으로 추상화**

- dev/staging/prod가 **같은 chart**를 쓰고 `values-*.yaml`만 다름 → 플레이북이 갈라질 여지가 없음
- 파드는 항상 `kafka.truss.local`을 바라보고 **ExternalName Service + Route53 Private Hosted Zone**이 환경별 실제 엔드포인트로 연결 → 파드 스펙 불변
- **dev가 파드 카프카 + 인클러스터 Prometheus로 도는 것 자체가 "관리형 서비스 없이도 동작함"의 상시 검증** (상세 7.5절)

**이 요구가 잘라내는 것**

- **EC2 직접 운영 X** — ASG·시작 템플릿·CloudWatch 알람은 AWS 전용이다. 지금 겪는 문제 그대로다
- **ECS X (결정적)** — ECS는 **컨트롤 플레인이 AWS 리전에 상주**한다. ECS Anywhere로 온프레미스 서버를 등록할 수 있지만, 그 서버들은 여전히 **AWS 리전의 ECS 컨트롤 플레인에 상시 연결**되어 지시를 받고 AWS 계정·IAM이 있어야 동작한다. **"AWS 없이 자체 IDC에서 돈다"가 성립하지 않는다**
- **K8s O** — 컨트롤 플레인 자체를 자체 IDC에 세울 수 있고, 우리가 쓴 매니페스트가 그대로 동작한다

> **정직하게 남길 트레이드오프**: 우리는 MSK·AMP·AMG 같은 AWS 네이티브 서비스도 쓴다(7장). 즉 **완전한 이식성은 아니다.** 다만 경계가 다르다 — 애플리케이션 실행 계층(파드·배포·Job·스케일 정의)은 그대로 옮겨가고 **교체 대상은 주변 관리형 서비스로 한정**된다. Kafka는 Strimzi로, AMP/AMG는 자체 Prometheus/Grafana로 대체 가능하며, 그 전환 지점을 Helm values 한 곳에 모아둔다. ECS였다면 실행 계층의 정의 형식(태스크 정의·서비스)부터 통째로 다시 만들어야 한다.

고객은 **"평소의 수십 배"**라고만 말했다. 이걸 계약 가능한 숫자로 바꾸는 것이 우리 일이었다.

| 단계 | 내용 |
|---|---|
| ① 대상 범위 합의 | A거래소 원화마켓 중 **거래대금 상위 20개 종목**으로 한정 (전 종목은 1차 범위 밖) |

| ⑤ 전체 목표 산출 | 20종목 × 500건 = **초당 1만 건** → RQ-04 |
| ⑥ 사용자 수 환산 | 거래소 Open API의 통상적인 계정당 주문 한도 **초당 8건**을 사용자 1명의 최대 속도로 놓으면, 10,000 ÷ 8 = **동시 주문 사용자 1,250명** |

**이 사슬이 중요한 이유**: 나중에 멘토가 "몇 명까지 버티냐"고 물었을 때(6장), 1,250명이 임의로 정한 값이 아니라 **① 대상 종목 수 → ② 실측 → ③ 고객 발언 → ④ 합의 → ⑤ 처리량 → ⑥ 사용자 수**로 이어지는 근거를 갖는다.

## 2. 왜 쿠버네티스인가 (액션 아이템 ②)

### 2.1 멘토의 질문과 답변 구조

> "이 서비스 AWS EC2로는 안 되나요? EC2 쓰고 Lambda 써서 이벤트 처리할 수 있지 않을까요? 오토스케일링, 이건 EC2 안 돼요? 그러면 이런 이유가 아니라 **딱 Kubernetes만 되는 이유**를 되셨어야지."

우리가 처음 든 근거는 **오토스케일링**이었는데, 이건 EC2 Auto Scaling Group으로도 되므로 K8s를 선택할 이유가 되지 못한다. 멘토 지적이 맞다.

그리고 여기서 한 걸음 더 나가야 한다. **"컨테이너 오케스트레이터가 필요하다"와 "쿠버네티스여야 한다"는 다른 명제다.** 앞의 것만 논증해놓고 쿠버네티스를 결론으로 내면, "그럼 ECS는요? AWS 쓰면서 굳이 K8s를 얹는 이유는요?"라는 후속 질문에 답이 없다. 그래서 관문을 두 단계로 나눈다.

```
후보: EC2 직접 운영 / Lambda / ECS / EKS(Kubernetes)
   │
   ├─ 1단계 관문 (RQ-01~05 전부) ──▶ EC2 직접 운영 탈락, Lambda 탈락
   │                                 "컨테이너 오케스트레이션이 필요하다"
   │                                 남은 후보: ECS, EKS
   │
   └─ 2단계 관문 (RQ-05 · RQ-03 · RQ-02) ──▶ ECS 탈락
                                             "그중에서도 쿠버네티스여야 한다"
                                             결론: EKS
```

### 2.2 요구사항별 대체 가능성 (한눈에)

**O = 그대로 됨, △ = 되지만 직접 만들어야 함, X = 구조적으로 불가**

| 고객 요구 | 핵심 능력 | EC2 직접 운영 | Lambda | ECS | **EKS** |
|---|---|---|---|---|---|
| **RQ-01** 무중단 잦은 배포 | 가벼운 배포 단위 + 무중단 순차 교체 + probe 분리 + 즉시 롤백 | **X** | O | O | **O** |
| **RQ-02** 하나의 인프라·운영 체계 | 집적 + 격리 + 프로세스 단위 권한 + **이질 워크로드 단일 API** | **X** | △ | **△→X** | **O** |
| **RQ-03** 정합성·단일 소유권 | **순번 신원 + 순차 교체** (이중 소유 0초) | **X** | **X** | **X** | **O** |
| **RQ-04** 대량 주문·한계 동작 | **대기량 직접 기준** 2분 증설 + 인메모리 상태 + 백프레셔 | **X** | **X** | **△→X** | **O** |
| **RQ-05** 재현성·클라우드 비종속 | 사업자 중립 선언적 정의 + **컨트롤 플레인 자체 호스팅** | **X** | **X** | **X** | **O** |

**읽는 법**: EC2 직접 운영은 5개 전부에서 X → 1단계 탈락. Lambda도 3개에서 X. **ECS는 RQ-01만 온전히 통과하고 나머지 넷에서 걸린다** → 2단계 탈락.

### 2.3 1단계 — EC2 직접 운영이 탈락하는 지점

각 요구의 "현재 겪는 문제"가 곧 근거다. 고객은 지금 EC2로 운영 중이고, **그 방식으로는 안 되니까 우리를 부른 것**이다.

| 요구 | EC2에서 불가한 이유 |
|---|---|
| **RQ-01** | 배포 = 아티팩트를 밀어 넣고 프로세스 재시작. 무중단으로 하려면 인스턴스 순차 교체인데 OS 부팅부터라 수 분. 점검 창 0분 + 실패 주문 0.1% 이하를 맞출 수 없고, 롤백 1분·재개 60초도 불가. ASG는 인스턴스를 AZ에 분산할 뿐 **프로세스 배치에는 관여하지 않는다** |
| **RQ-02** | **집적과 격리가 동시에 성립하지 않는다.** 격리 수단이 "인스턴스를 나누는 것"뿐이라 격리하면 비용을, 집적하면 격리를 어긴다. 인스턴스 프로파일이 서버 단위라 프로세스별 권한도 불가. cgroup으로 직접 관리하는 건 **스케줄러를 직접 만드는 일** |
| **RQ-03** | 리더 선출·임대 갱신·소유권 반납·순차 교체를 직접 구현해야 한다. **고객이 이미 만들었다가 사고를 냈다** |
| **RQ-04** | 커스텀 지표 퍼블리셔를 직접 만들어야 하고, 증설 단위가 인스턴스라 2분을 못 맞춘다 |
| **RQ-05** | ASG·시작 템플릿·CloudWatch 알람은 AWS 전용. IDC로 못 가져간다 |

**1단계 결론**: 컨테이너 오케스트레이터가 필요하다. 다만 ECS도 이 관문을 통과하므로 **여기까지로는 쿠버네티스가 확정되지 않는다.**

### 2.4 Lambda가 매칭 엔진을 만들 수 없는 이유

RQ-04(0.5초 응답)와 RQ-03(순서 역전·중복 체결 0)를 동시에 만족시키려면 매칭 엔진의 설계가 하나로 좁혀진다.

**설계 결론**: 호가창을 **프로세스 메모리에 유지**하고, **한 종목은 정확히 한 프로세스만** 담당한다.

| 설계 요구 | Lambda에서 성립하지 않는 이유 |
|---|---|
| 호가창을 프로세스 메모리에 유지 (RQ-04) | 실행 간 상태를 보장하지 않는다. 매 호출마다 복원하면 인메모리로 두는 의미가 사라진다 |
| 한 종목 = 한 프로세스 (RQ-03) | 동시 실행 인스턴스를 런타임이 자동으로 늘린다. 소유권을 표현할 수단이 없다. 예약 동시성을 1로 묶으면 처리량이 무너진다 |
| 60초 내 무인 재개 (RQ-01) | 복구 대상이 되는 "프로세스의 수명"이라는 개념 자체가 없다 |
| 장시간 세션·부하 재생 (RQ-02·04) | 최대 실행 시간 15분 |

반대로 **"버튼을 눌렀을 때 작업을 하나 띄우는" 짧은 제어 로직은 Lambda로도 된다.** 그 선택지는 3장에서 실제로 비교하고, 다른 이유로 채택하지 않는다.

### 2.5 2단계 — ECS가 아니라 쿠버네티스인 이유

여기가 멘토가 물은 **"딱 쿠버네티스만 되는 이유"**의 답이다. 세 가지가 ECS를 잘라낸다.

**① RQ-05 — ECS는 컨트롤 플레인이 AWS를 벗어나지 못한다 (가장 결정적)**

고객이 *"3년 내 자체 IDC 회귀를 검토 중이고, 특정 클라우드 사업자 없이는 못 도는 구조는 피해달라"*고 명시했다.

ECS의 컨트롤 플레인은 **AWS 리전에 상주하는 관리형 서비스**다. ECS Anywhere로 온프레미스 서버를 등록할 수 있지만, 그 서버들은 여전히 **AWS 리전의 ECS 컨트롤 플레인과 상시 연결**되어 지시를 받고, AWS 계정과 IAM이 있어야 동작한다. 즉 **"AWS 없이 자체 IDC에서 돈다"가 성립하지 않는다.**

쿠버네티스는 컨트롤 플레인 자체를 자체 IDC에 세울 수 있고, 우리가 쓴 매니페스트가 그대로 동작한다. **이 요구 하나만으로 ECS는 탈락한다.**

**② RQ-03 — ECS 태스크에는 순번 신원이 없다**

고객이 겪은 사고는 **자체 구현한 종목 재할당 로직의 실패**다. 따라서 이번에는 **플랫폼이 보장**해야 하고, 필요한 것은 두 가지다.

- **순번 신원**: "이 프로세스가 몇 번째인지"를 플랫폼이 안정적으로 부여 → 종목 할당을 순번에서 결정적으로 계산할 수 있고, 사람이 관리하는 할당표가 사라진다
- **순차 교체**: "이전 것이 완전히 종료된 것을 확인한 뒤 다음 것" — 이게 이중 소유 0초의 직접적 보장

**ECS는 둘 다 제공하지 않는다.** ECS 서비스의 태스크는 매번 새로 발급되는 임의 ID를 갖고, 배포 시 `minimumHealthyPercent`/`maximumPercent`로 **비율**은 제어해도 **순서**는 보장하지 않는다. 결국 고객이 실패했던 자체 구현으로 되돌아간다.

**K8s의 StatefulSet은 이 두 가지가 정확히 그 리소스의 정의**다 — `matching-0 … matching-19`라는 안정적 순번, `podManagementPolicy: OrderedReady`라는 순차 보장.

**③ RQ-02 — ECS는 워크로드 유형마다 운영 체계가 갈라진다**

우리 시스템에는 세 성격이 섞여 있다.

| 성격 | 우리 워크로드 | K8s | ECS 계열 |
|---|---|---|---|
| 상시 서비스 | 접수 API, 매칭 엔진, 기록기, 시세 수집기 | Deployment / StatefulSet | ECS Service |
| 완료형 일회성 작업 | AI 트레이더 세션, 리플레이 엔진 | **Job** | ECS RunTask 또는 **AWS Batch** |
| 노드 상주 에이전트 | 로그 수집 | **DaemonSet** | daemon 배치 전략 |

**K8s는 셋이 같은 API 서버·같은 RBAC·같은 스케줄러 아래 있다.** Helm chart 하나에 함께 들어가고, 권한은 전부 ServiceAccount + IRSA 한 모델이며, 관측은 같은 service discovery로 자동 편입된다.

우리는 이걸 **실제로 검증했다** — AI 트레이더/리플레이 엔진을 AWS Batch로 뺄지 검토했을 때 나온 결론이 이렇다.

> IAM이 두 벌(Task Role vs Batch Job Role), 네트워킹이 두 벌(별도 Compute Environment의 서브넷·SG), IaC 코드가 두 벌, 배포 절차가 두 갈래(`helm upgrade` vs `submit-job`), 그리고 **모니터링이 분리된다** — Prometheus의 K8s service discovery가 Batch/ECS 태스크를 보지 못해 CloudWatch를 따로 붙여야 한다.

이건 **고객이 RQ-02에서 "하나의 방식으로 통일해달라"고 명시적으로 거부한 구조**이고, 동시에 **3인 팀이 감당할 표면적이 아니다.**

**④ RQ-04 — ECS 오토스케일은 CloudWatch를 경유한다 (보조 근거)**

고객은 *"CPU 말고 실제로 밀린 주문량을 봐라"* + *"2분 이내"*를 요구했다. ECS Application Auto Scaling은 **CloudWatch 지표 기반**이라 랙을 퍼블리시하고 지표 해상도를 거쳐 알람이 평가되는 왕복이 필요하다. KEDA는 브로커를 직접 폴링해 중간 경로가 없다. 그리고 노드 축의 Karpenter(4장) 역시 K8s 스케줄러의 pending 파드를 보고 동작하는 K8s 생태계 컴포넌트다.

**2단계 결론**: RQ-05 하나만으로도 ECS는 탈락하고, RQ-03·02가 각각 독립적으로 같은 결론을 뒷받침한다. **EKS(Kubernetes) 확정.**

### 2.6 그럼에도 한 문장으로 답해야 한다면 RQ-01이다

> "신속한 배포. 그쵸? 빠른 패치, 코드 수정이 빠르다는 거예요. 그래서 나중에 CI/CD로 연결하는 이런 맥락의 흐름이 있어야 된다는 거예요. … CI/CD 파이프라인이 무조건 필요한가요? 빈번한 배포가 필요하다는 것. 1년에 한두 번 배포할 거면 그거 필요 없어요."

2.5절이 "쿠버네티스여야 하는 이유"라면, **발표에서 먼저 말할 것은 RQ-01이다.** 나머지는 "이렇게 하면 어렵다"인 반면 이건 **"이 요구를 받아들인 순간 배포 체계 전체가 결정된다"**이기 때문이다.

| RQ-01이 요구하는 것 | 필요한 능력 |
|---|---|
| 기능을 **수시로** 낸다 | 배포가 일 단위로 일어난다 → **CI/CD 파이프라인이 없으면 성립 불가** |
| 버그를 **당일 패치**한다 | 코드 수정 → 배포까지 분 단위 → **배포 단위가 가벼워야 함(= 컨테이너 이미지)** |
| **점검 창 0분** | 배포 중에도 거래 지속 → **무중단 순차 교체 + 헬스 게이트 + 최소 가용성 보장이 플랫폼 기본 기능** |

```
RQ-01 (24시간 장 · 당일 패치 · 점검 창 0분)
  → 배포가 빈번하다
  → CI/CD 파이프라인이 필수다
  → 배포 단위가 "컨테이너 이미지"여야 파이프라인이 분 단위로 돈다
  → 그 이미지를 무중단으로 굴려줄 오케스트레이터가 필요하다
  → (2.5절의 2단계 관문) → Kubernetes
```

> **멘토가 지적한 핵심을 한 줄로**: "1년에 몇 번 배포할 시스템이면 CI/CD도 K8s도 필요 없다." 우리 고객은 **24시간 장에서 당일 패치를 요구했다.** 정확히 정반대 케이스다.

### 2.7 CI/CD 파이프라인과의 연결 (멘토가 요구한 "맥락의 흐름")

RQ-01은 K8s만으로는 충족되지 않는다. **"컨테이너 이미지가 배포 단위"라는 점을 파이프라인이 끝까지 이어받아야** 비로소 당일 패치가 성립한다.

```
개발자 push
  → GitHub Actions: 자동 테스트 → 실패 시 병합 차단
  → 컨테이너 이미지 빌드 → ECR push (커밋 SHA를 태그로)
  → Helm values의 image.tag 갱신 → helm upgrade
  → K8s 롤링 업데이트 (maxUnavailable=0, readiness 게이트, PDB로 종목별 최소 가용성) ← RQ-01
  → 문제 발생 시 helm rollback / kubectl rollout undo (재빌드 없음)                  ← RQ-01
  → 인수 시험(리플레이) 재실행 → 대시보드에서 이전 배포와 동일 시간축 비교              ← RQ-04
```

마지막 줄이 중요하다. **RQ-04(인수 시험으로 증명)와 RQ-01(잦은 배포)이 만나면 "배포할 때마다 성능이 나빠지지 않았는지 자동으로 확인하는" 회귀 검증 루프**가 된다. 이게 이 프로젝트에서 CI/CD가 존재하는 진짜 이유다.

### 2.8 발표용 결론 (4문장)

1. 한 문장으로 답해야 한다면 **RQ-01** — **24시간 장, 점검 창 0분, 당일 패치**. 그래서 CI/CD가 필수이고, 그래서 배포 단위가 컨테이너이며, 그래서 오케스트레이터가 필요하다.
2. **5개 요구 전부가 EC2 직접 운영을 배제**한다 — 고객이 지금 그 방식으로 운영 중이고, 각 요구의 "현재 겪는 문제"가 곧 그 근거다.
3. **RQ-04·03이 Lambda를 배제**한다 — 매칭 엔진은 상태를 들고 오래 사는, 종목당 하나뿐인 프로세스여야 한다.
4. **여기까지는 ECS도 통과한다. ECS를 자르는 것은 RQ-05·03·02다** — 컨트롤 플레인이 AWS를 못 벗어남(IDC 회귀 불가), 태스크에 순번 신원·순차 교체 보장 없음(이중 소유 재발), 이질 워크로드가 Service/Batch/daemon으로 갈라져 운영 체계가 이원화됨.

## 3. Kubernetes Job 트리거 메커니즘 (액션 아이템 ③)

### 3.1 먼저: "왜 굳이 Job이어야 하는가"에 대한 답

> "굳이 잡을 써야 되는 이유, 잡의 역할, 잡이어야 되는 이유. 이게 조금 애매해서. … 근데 그 일회성으로 뜨는데 얘가 이벤트를 받으면 계속 실행이 돼야 되잖아요."

**출발점은 RQ-02다.** 고객이 *"운영자가 버튼을 누르면 그때 떠서, 끝나면 사라져야 한다. 지금은 배치 전용 EC2가 하루 종일 떠 있다"*라고 요구했고, 여기에 실패 재시도 횟수와 최대 실행 시간 상한까지 명시했다. **이건 Job의 기능 명세와 그대로 겹친다.**

멘토의 우려는 **"Job은 일회성인데, 이 워크로드는 이벤트를 계속 받으며 돌아야 하지 않느냐"**였다. 답은 이렇다.

**Job은 "짧은 작업"에 쓰는 리소스가 아니라 "완료 조건이 있는 작업"에 쓰는 리소스다.**

| | AI 트레이더 | 리플레이 엔진 | 시세 수집기 (비교군) |
|---|---|---|---|
| 시작 조건 | 운영자가 기간을 선택해 세션 시작 | 운영자가 재생할 기록·구간 선택 | 상시 |
| **종료 조건** | **선택한 기간의 시세를 모두 소진하면 종료** | **지정 구간을 모두 재생하면 종료** | 없음 |
| 실행 시간 | 수 분 ~ 수십 분 | 배속에 따라 수 분 | 무한 |
| 채택 리소스 | **Job** | **Job** | **Deployment (replicas=1)** |

세션 내부에서는 시세를 계속 구독하며 오래 돌지만, **세션 자체에는 명확한 끝이 있다.** Job의 정의에 정확히 부합한다.

**Deployment로 하면 안 되는 이유**: `restartPolicy: Always`라 세션이 끝나 프로세스가 종료돼도 파드가 무한 재시작한다. 세션 종료를 표현할 방법이 없고 사람이 `replicas: 0`으로 내려야 한다 — RQ-02의 "끝나면 사라져야 한다"를 위반한다.

**Job이 RQ-02의 각 조항에 그대로 대응한다**

| 고객 요구 (RQ-02) | Job 기능 |
|---|---|
| 버튼을 누르면 그때 뜬다 | 접수 API가 Job 객체를 생성 (3.3절) |
| 끝나면 사라진다 | `ttlSecondsAfterFinished` — 완료 후 파드·객체 자동 회수 |
| 실패 시 재시도 횟수 상한 | `backoffLimit` (무한 재시도로 LLM 호출 비용이 새는 것 방지) |
| 최대 실행 시간 상한 | `activeDeadlineSeconds` — 무한 루프도 자동 종료 |
| (RQ-04) 분산 부하 생성 | `completions` / `parallelism` (Indexed Job)로 종목 단위 4대 병렬 재생 |
| (RQ-02) 실행 이력 관측 | Job status(`succeeded`/`failed`)가 곧 세션 상태 — 별도 저장소 불필요 |

**AWS Batch가 아니라 K8s Job인 이유도 RQ-02다** — 2.5절 ③에서 정리한 대로, Batch로 빼면 IAM·네트워킹·IaC·배포 절차·모니터링이 전부 이원화된다. **Lambda로 대체 불가한 이유**는 최대 실행 15분 제한이다.

### 3.2 트리거 방식 3안 비교

| | **안 A. SQS + Lambda → EKS API** | **안 B. 접수 API(인클러스터) + RBAC** | **안 C. KEDA ScaledJob + SQS** |
|---|---|---|---|
| 흐름 | 프론트 → API GW → SQS → Lambda → EKS API로 Job 생성 | 프론트 → ALB → 접수 API 파드 → (in-cluster) K8s API로 Job 생성 | 프론트 → 접수 API → SQS → KEDA가 큐 depth 보고 Job 생성 |
| 인증 경로 | Lambda IAM 역할을 **EKS Access Entry**로 클러스터에 등록 + Lambda를 VPC에 붙여 프라이빗 엔드포인트 접근 | ServiceAccount 토큰 (클러스터 내부, **추가 IAM 0개**) | KEDA가 SQS 접근용 IRSA 필요 |
| 신규 컴포넌트 | API GW, SQS, Lambda, VPC ENI = **4개** | **0개** (접수 API는 이미 존재) | SQS, ScaledJob = 2개 (KEDA는 이미 도입 예정) |
| 지연 | Lambda 콜드스타트(VPC ENI 포함) + Job 생성 | 동기 호출, 수십 ms | 폴링 주기만큼 지연 |
| 버퍼링·재시도 | SQS가 담당 | 클라이언트가 재시도 (동기 응답이라 실패를 즉시 알림) | SQS가 담당 |
| 세션 우선순위·대기열 | 가능 | 불가 | 가능 |

### 3.3 결정: 안 B (접수 API + RBAC) 채택

**근거**

1. **인증 경로가 가장 짧다.** Lambda는 클러스터 **외부**라 ① IAM 역할을 EKS Access Entry(또는 aws-auth ConfigMap)로 클러스터에 등록하고 ② 프라이빗 API 엔드포인트를 치려면 Lambda를 VPC에 붙여야 하며(ENI 생성 → 콜드스타트 증가) ③ IAM 인증 토큰으로 kubeconfig를 조립해야 한다. 접수 API는 이미 클러스터 **안**에 있어 마운트된 ServiceAccount 토큰만으로 API 서버를 호출한다 — **새로 만들 인증·네트워크 경로가 0개다.** RQ-02(운영 체계 단일화·권한 접점 최소화)에 정확히 맞는다.
2. **SQS의 가치가 이 시나리오에 없다.** 멘토가 정확히 짚은 대로 SQS의 목적은 "Lambda가 일방향이라 실패 시 재전송·버퍼링"이다. 그런데 안 B는 **동기 요청-응답**이라 실패를 즉시 HTTP 상태 코드로 알릴 수 있고 재시도 주체가 명확하다. 세션 시작은 **사람이 버튼을 누르는 초당 1건 미만의 이벤트**라 버퍼링해야 할 유량 자체가 없다. 없는 문제를 위해 컴포넌트 3개를 추가하는 건 RQ-02(비용)에도 어긋난다.
3. **주문 트래픽과 제어 트래픽을 혼동하지 않는다.** 대량 처리가 필요한 건 주문 경로(초당 1만 건)이고 그건 메시징 계층이 담당한다. 세션 제어까지 큐를 태우면 아키텍처가 대칭적으로 보일 뿐 실익이 없다.

**단, 되돌릴 조건을 명시해둔다** — 아래 중 하나라도 발생하면 안 C(KEDA ScaledJob + SQS)로 전환한다.
- 동시 세션이 Fargate 동시 실행 쿼터에 근접해 **대기열**이 필요해질 때
- 세션에 **우선순위**(예: 시연용 세션 우선)가 필요해질 때
- 세션 요청 유실이 실제로 관측될 때

> 이 전환 조건은 앞서 AWS Batch vs K8s Job을 검토할 때 세운 기준과 같은 형식이다 — "지금은 필요 없다"로 끝내지 않고 **"이 조건이 되면 바꾼다"**로 남긴다.

### 3.4 구현 상세

**(1) Job 매니페스트는 코드가 아니라 ConfigMap 템플릿으로 둔다**

멘토가 "코드에다가 Job YAML을 넣어놔도 되겠네요"라고 한 것의 개선판이다. 템플릿을 코드에 하드코딩하면 리소스 요청량·이미지 태그·타임아웃을 바꿀 때마다 접수 API를 재배포해야 한다. ConfigMap에 두면 **재배포 없이 매니페스트만 갱신**된다 — RQ-01의 "빠른 변경" 원칙과 같은 방향이다.

```yaml
# configmap: job-templates (namespace: backend)
ai-trader-job.yaml: |
  apiVersion: batch/v1
  kind: Job
  metadata:
    name: trader-{{ .SessionID }}
    namespace: ai-trader
    labels:
      truss.io/session-id: "{{ .SessionID }}"
      truss.io/workload: ai-trader
  spec:
    backoffLimit: 2                    # RQ-02 재시도 상한
    activeDeadlineSeconds: 5400        # RQ-02 최대 실행 90분
    ttlSecondsAfterFinished: 3600      # RQ-02 완료 후 자동 회수
    template:
      spec:
        serviceAccountName: sa-ai-trader   # RQ-02 프로세스 단위 IAM(IRSA)
        restartPolicy: Never
        containers:
          - name: trader
            image: {{ .ECRRepo }}:{{ .ImageTag }}
            env:
              - { name: SESSION_ID,   value: "{{ .SessionID }}" }
              - { name: PERIOD_START, value: "{{ .PeriodStart }}" }
              - { name: PERIOD_END,   value: "{{ .PeriodEnd }}" }
              - { name: BOT_CONFIG,   value: "{{ .BotConfig }}" }
```

**(2) RBAC은 네임스페이스를 넘는 최소 권한으로 준다 (RQ-02)**

접수 API의 ServiceAccount는 `backend` 네임스페이스에 있고, Job은 `ai-trader`·`replay` 네임스페이스에 만들어야 한다. 따라서 **Role은 대상 네임스페이스에**, **RoleBinding의 subject는 backend의 SA를** 가리킨다. ClusterRole을 쓰면 클러스터 전체 권한이 되므로 쓰지 않는다.

```yaml
kind: Role
metadata: { name: job-creator, namespace: ai-trader }
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["create", "get", "list", "watch", "delete"]
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]     # 세션 로그 조회용
---
kind: RoleBinding
metadata: { name: backend-can-create-jobs, namespace: ai-trader }
subjects:
  - kind: ServiceAccount
    name: sa-ingest-api
    namespace: backend                   # 다른 네임스페이스의 SA를 지정
roleRef: { kind: Role, name: job-creator, apiGroup: rbac.authorization.k8s.io }
```

`update`·`patch` 권한은 주지 않는다 — 접수 API가 하는 일은 "만들고, 상태를 읽고, 취소하면 지우는 것"까지다.

**(3) 세션 상태 반영**

```
접수 API가 Job 생성 → DB session 테이블에 PENDING 기록 → 즉시 HTTP 202 + session_id 반환
접수 API의 워처가 Job status를 watch → RUNNING / SUCCEEDED / FAILED로 갱신
프론트는 session_id로 상태 조회
```

즉시 202를 돌려주는 설계가 **8장의 Fargate 기동 지연을 사용자 경험에서 흡수하는 장치**이기도 하다.

**(4) 남는 리스크**: 접수 API는 주문 처리(초당 1만 건)의 핫패스이기도 하다. Job 생성 로직이 여기 붙으면 관심사가 섞인다. 세션 제어 엔드포인트를 **별도 Deployment(`session-controller`)로 분리**하고 같은 ALB의 다른 경로로 붙이는 방안을 함께 검토한다 — 인클러스터의 장점은 유지하면서 핫패스를 오염시키지 않는다.

## 4. Karpenter vs Cluster Autoscaler (액션 아이템 ④)

> "카펜터를 권장을 해요. 근데 왜 카펜터를 쓰는 게 단순히 빨라서만 일까? 아닌 게 또 있어요."

### 4.1 결정적 근거: RQ-04의 "2분 이내 증설"을 CA로는 구조적으로 못 지킨다

| | Cluster Autoscaler | Karpenter |
|---|---|---|
| 동작 | 10초 주기 폴링 → 스케줄링 시뮬레이션 → **ASG의 desired capacity 변경** → ASG가 인스턴스 기동 | pending 파드를 감지 → **EC2 Fleet API 직접 호출** |
| 계층 | Pod → CA → **ASG** → EC2 (한 단계 더 있음) | Pod → Karpenter → EC2 |
| 노드 준비 시간 | **약 3~4분** | **약 45~60초** |
| RQ-04(2분) 충족 | **미달** | 충족 (여유 약 60초) |

CA가 느린 건 구현이 나빠서가 아니라 **ASG를 거치는 구조** 때문이다. 튜닝으로 좁힐 수 있는 차이가 아니다.

> 파드 증설(KEDA)은 이미 떠 있는 노드 위에서 수 초 만에 끝난다. 2분 예산을 실제로 소모하는 건 **노드가 부족할 때**이고, 그래서 노드 오토스케일러 선택이 RQ-04의 성패를 가른다.

### 4.2 속도 외의 근거 5가지 (멘토가 찾아보라고 한 부분)

**① 노드그룹(ASG)을 사전 정의하지 않아도 된다**

CA는 "이미 정의된 노드그룹"의 크기만 조절한다. 인스턴스 타입을 바꾸려면 노드그룹을 새로 만들어야 하고, AZ마다 별도 ASG를 두는 게 관행이다(우리도 `ng-backend-a`/`ng-backend-b`로 나눠뒀는데, 이건 **CA의 AZ 불균형 문제를 우회하려는 구성이기도 하다**). Karpenter는 pending 파드의 `requests`·nodeSelector·topology constraint를 읽어 **그 자리에서 적합한 인스턴스 타입과 AZ를 고른다.** RQ-01의 AZ 자동 분산 제약을 스케줄러가 직접 반영한다는 뜻이기도 하다.

**② Consolidation — 실행 중인 파드를 재배치해 노드를 줄인다 (RQ-02 직결)**

CA의 스케일 다운은 사실상 "비어 있는 노드 제거"에 가깝다. 실행 중인 파드를 옮겨 노드 수를 줄이지는 않으므로 시간이 지나면 **파편화된 노드가 남는다.** Karpenter는 세 가지로 능동적으로 압축한다.
- 빈 노드 삭제
- **single-node consolidation**: `c6i.4xlarge`에 4 vCPU어치 파드만 돌면 `c6i.xlarge`로 교체
- **multi-node consolidation**: 여러 노드를 더 저렴한 노드 1대로 통합

**우리 시나리오에 직접 걸린다**: 피크가 지나면 매칭 엔진 파드가 20 → 2로 줄어든다. CA는 파편화된 노드가 남지만 Karpenter는 압축한다. 업계 보고로는 CA → Karpenter 전환 시 **노드 비용 20~40% 절감** 사례가 흔하다. **RQ-02(평시 피크 대비 25% 이하)를 지키는 실질 수단이 이것이다.**

**③ Spot 혼합과 중단 처리를 하나의 NodePool 안에서 한다**

CA로 스팟을 쓰려면 스팟 ASG와 온디맨드 ASG를 따로 만들고 우선순위를 조합해야 한다. Karpenter는 하나의 NodePool에 `capacity-type: [spot, on-demand]`와 다수 인스턴스 타입을 나열해두면 capacity-optimized 전략으로 알아서 고르고, **스팟 중단 경고(2분 전)를 받아 미리 taint·drain**한다. 7장의 dev 환경 스팟 전략과 직결된다.

**④ Drift 감지 — 노드 스펙이 바뀌면 자동 교체**

EC2NodeClass의 AMI나 보안 그룹이 바뀌면 Karpenter가 기존 노드를 "drifted"로 표시하고 순차 교체한다. CA는 AMI 갱신을 노드그룹 롤링으로 사람이 수행해야 한다. RQ-01(잦은 변경)·RQ-02(보안 패치) 양쪽에서 손이 덜 간다.

**⑤ Disruption Budget — 인수 시험 중 자발적 중단을 0으로 묶을 수 있다 (RQ-04 재현성 직결)**

**우리 프로젝트에 특히 중요한 이유**다. 인수 시험 도중 Karpenter가 consolidation으로 노드를 교체해버리면 그 순간의 측정값이 오염되고, **RQ-04가 요구한 "재현 가능한 시험"이 성립하지 않는다.** Karpenter는 스케줄 기반 disruption budget을 지원하므로 시험 구간에는 자발적 중단을 막고, 끝난 뒤에 압축이 돌게 할 수 있다.

```yaml
# NodePool 발췌 — 인수 시험 시간대에는 자발적 중단 금지
disruption:
  consolidationPolicy: WhenEmptyOrUnderutilized
  budgets:
    - nodes: "0"
      schedule: "0 13 * * *"   # 13:00부터
      duration: 4h             # 4시간 동안 중단 없음
    - nodes: "10%"             # 그 외 시간
```

CA에는 이에 상응하는 세밀한 제어가 없다.

### 4.3 트레이드오프와 전환 계획

- **Karpenter도 어딘가에서 돌아야 한다**: Karpenter 컨트롤러와 `kube-system`(CoreDNS 등)은 관리형 노드그룹 위에 있어야 한다. **관리형 노드그룹은 시스템 컴포넌트용 최소 2대로 축소**하고 워크로드 노드를 NodePool로 넘기는 구조가 된다.
- **현재 Terraform은 CA 전제**다(각 노드그룹 min 2 / max 8, [Truss 인프라 아키텍처](truss-architecture.html) 8장). Karpenter 전환 시 min/max 재조정 필요 — 미착수.
- **학습·운영 부담**: NodePool/EC2NodeClass라는 새 CRD를 익혀야 한다. 4주 제약에 걸리면 EKS Auto Mode(관리형 Karpenter)로 우회할 수 있다.
- **RQ-05(이식성) 관점**: Karpenter는 AWS 전용이다. 다만 이건 **노드 공급 계층**이라 IDC 회귀 시 교체 대상이 이 계층 하나로 한정된다 — 파드·Deployment·StatefulSet·Job 정의는 그대로 간다. 온프레미스에서는 Cluster API로 대체하거나 물리 노드 고정 구성으로 간다.
- **Fargate와의 관계**: Karpenter는 EC2 노드를 만드는 오토스케일러이고 Fargate는 노드 개념이 없는 실행 환경이다. **대체 관계가 아니라, 워크로드마다 "Fargate Profile에 올릴지, Karpenter가 띄운 노드에 올릴지"를 고르는 배치 선택이다**(8장).

## 5. RDS 부하 처리 — 정합성 트레이드오프와 5단 방어 (액션 아이템 ⑤)

### 5.1 왜 DB는 무작정 오토스케일링할 수 없는가

> "디비를 오토스케일링에 한계가 있는 이유가? 정합성 이슈 때문이라는 거예요. 잘못된 그림 중에 하나가 앞에 로드밸런서를 그려놓고 뒤에 디비 이렇게 쓰는 거. 말이 안 돼요."

파드는 **무상태**라 복제본을 늘리면 그만이지만, DB는 **상태를 가진다.** 노드를 늘리면 노드 간 데이터를 일치시켜야 하고, 그 일치를 어느 수준으로 보장할지가 곧 **정합성(consistency) 모델**이다.

| 모델 | 보장 | 대가 | 적합한 데이터 |
|---|---|---|---|
| **Strong Consistency** | 쓰기 직후 모든 읽기가 최신값 | 노드 간 합의 비용 → 지연 증가, 확장 제한 | **가상자산 거래·체결·잔고** |
| **Eventual Consistency** | 시간이 지나면 수렴 | 일시적 불일치 허용 | SNS 팔로우 수, 조회 통계 |

**RQ-03(유실 0 / 중복 체결 0 / 순서 역전 0)은 명백히 Strong Consistency 요구**이고, RQ-04는 0.5초 응답을 요구한다. 둘 다 만족시키려면 비용이 급격히 오른다(멘토: "돈을 왕창 쏟아부으면 되지만 그게 ROI인가"). 그래서 **데이터마다 등급을 나누는 것**이 설계다.

### 5.2 우리 시스템의 데이터 정합성 등급

| 데이터 | 등급 | 저장소 | 근거 |
|---|---|---|---|
| 체결 결과·주문 이력 | **Strong** | RDS PostgreSQL **단일 라이터** (Multi-AZ DB 클러스터) | RQ-03. 샤딩·멀티라이터를 **하지 않는다** |
| 호가창 현재 상태 | Strong (단, DB 아님) | **매칭 엔진 인메모리**가 원본, Redis는 조회용 사본 | 1종목 = 1엔진이라 원본이 애초에 한 곳뿐 → 분산 정합성 문제가 발생하지 않는 구조 |
| 호가창 조회 응답 | Eventual 허용 | Redis | 수십 ms 지연된 호가는 거래소에서도 정상 (RQ-04는 지연 상한만 요구) |
| 거래 내역 조회 | Eventual 허용 | RDS **reader endpoint** (읽기 가능 스탠바이 2대) | 조회 트래픽을 라이터에서 분리 |

**핵심**: 우리는 **DB를 분산시키지 않는 것**을 선택했다. 대신 DB에 도달하는 부하 자체를 구조로 줄인다.

### 5.3 5단 방어 구조

> 멘토가 박수친 지점: "RDS에서 쓰는 컴포넌트는 기록기가 하나뿐이고 매칭 자체는 Redis 기반이라 RDS를 안 거친다. 그런데 기록기가 못 따라갈 때 속도를 늦추는 로직이 없어서 랙이 계속 쌓이다 터지는 구조라고 이해했고, 그래서 MSK 컨슈머 랙 기반으로 기록기를 스케일하겠다."

**① 핫패스에서 DB를 제거한다 (이미 반영됨 — RQ-04)**

```
주문 접수 → Kafka(orders) → 매칭 엔진 → 인메모리 호가창 + Redis
                                          ↓
                              Kafka(executions) → 기록기 → RDS
```

주문 접수·매칭·체결 응답 경로(0.5초를 지켜야 하는 구간)에 **RDS가 한 번도 등장하지 않는다.** RDS를 쓰는 유일한 컴포넌트는 기록기이고, 기록기는 응답 경로 밖에 있다. "로드밸런서 뒤에 바로 DB"라는 잘못된 그림을 애초에 피한 구조다.

**② 메시징 계층이 쓰기 부하를 시간축으로 펼친다 (이미 반영됨)**

체결이 초당 1만 건 몰려도 기록기가 그 속도로 쓸 필요는 없다. Kafka가 버퍼 역할을 해 순간 피크를 평탄화한다.

**③ 컨슈머 랙 기반으로 기록기를 스케일한다 (신규 — RQ-04의 "대기량 기준" 원칙을 그대로 적용)**

②의 한계는 **버퍼가 무한하지 않다**는 것이다. 기록기 처리량 < 유입량이 지속되면 랙이 단조 증가하고 결국 RQ-03(유실 0)이 깨진다. 고객이 RQ-04에서 *"CPU 말고 실제로 밀린 양을 봐라"*라고 한 원칙이 접수 경로뿐 아니라 기록 경로에도 똑같이 적용된다.

```yaml
# KEDA ScaledObject — 기록기
triggers:
  - type: kafka
    metadata:
      topic: executions
      consumerGroup: recorder-group
      lagThreshold: "5000"            # 레플리카당 허용 백로그
spec:
  minReplicaCount: 1
  maxReplicaCount: 12                 # executions 파티션 수를 상한으로 (그 이상은 유휴)
```

**상한이 파티션 수인 이유**: Kafka는 파티션 하나를 컨슈머 그룹 내 한 컨슈머만 읽으므로, 파티션 수보다 많은 기록기 파드는 아무 일도 하지 않는다. **"오토스케일링에도 max가 있다"는 멘토 지적이 여기에도 정확히 적용된다.**

**④ 쓰기 자체를 최적화한다 (신규)**

| 기법 | 적용 | 근거 |
|---|---|---|
| **배치 쓰기 (COPY)** | 건별 `INSERT` → 체결을 N건 또는 M밀리초 단위로 모아 `COPY`로 적재 | 체결 기록은 append-only라 COPY에 이상적이다. PostgreSQL에서 COPY는 개별 INSERT·배치 INSERT 대비 압도적으로 빠르다 |
| **시각 기준 range 파티셔닝** | `executions` 테이블을 시각으로 파티션 | 인덱스가 파티션 단위로 작아져 삽입 시 유지 비용이 감소. 시험 회차별 데이터 분리·삭제도 쉬워진다(RQ-04 재현성) |
| **인덱스 최소화** | 쓰기 경로 테이블은 조회에 꼭 필요한 인덱스만 | 인덱스 하나당 삽입 비용이 붙는다 |
| **커넥션 풀** | 기록기 파드 내부 풀 우선. 파드 수 증가로 커넥션이 한계에 닿으면 **RDS Proxy** 검토 | 파드가 12개로 늘면 커넥션도 선형 증가. 단, 클라이언트 풀이 이미 효율적이면 RDS Proxy의 추가 이득이 작다는 점도 함께 기록 |

**⑤ 그래도 못 버티면 접수단에서 거절한다 (RQ-04)**

랙이 기준치를 넘으면 접수 API가 신규 요청을 **HTTP 429로 즉시 거절**한다. 지연 응답은 클라이언트 재시도를 유발해 부하를 가중시키기 때문이다. **고객이 "조용히 버리지 마라"고 한 것을 지키는 방식이 이것이다** — 버리는 게 아니라 접수하지 않았음을 명시적으로 알린다.

> **주목할 점**: ③의 스케일아웃 트리거와 ⑤의 거절 트리거가 **같은 지표(컨슈머 랙)**다. 랙 하나로 "늘려서 버틴다 → 그래도 안 되면 막는다"가 연속적으로 이어진다.

### 5.4 왜 Aurora로 가지 않는가 (ROI)

> "RDS 쓰다가 이거를 좀 더 해결하기 위해서 오로라로 바꿔요? 그렇게 하긴 좀 무리가 있어요. 왜냐면 돈이 많이 드니까."

RQ-02(비용 억제)가 걸려 있으므로 **단계적 상향 원칙**을 세운다. 각 단계를 인수 시험으로 검증하고, 실패했을 때만 다음 단계로 간다.

```
1단계 (현재)  db.m6gd.large + COPY 배치 + 파티셔닝
   ↓ 미달 시
2단계          db.r8gd.large (메모리 최적화)
   ↓ 미달 시
3단계          reader endpoint로 조회 완전 분리 + 기록기 파티션 수 증설
   ↓ 미달 시
4단계          Aurora PostgreSQL (또는 시계열 저장소 분리)
```

"처음부터 Aurora"는 돈으로 문제를 덮는 것이고, 우리가 어느 단계에서 왜 막혔는지 설명할 수 없게 만든다. **ROI 관점에서는 단계적 상향이 정답이고, 각 단계의 실패 근거를 지표로 남기는 것 자체가 RQ-04(증명)에 대한 답이 된다.**

### 5.5 인수 시험에서 확인할 지표

| 지표 | 임계 | 초과 시 의미 |
|---|---|---|
| `executions` 컨슈머 랙 | 단조 증가하지 않을 것 | 기록기가 유입을 못 따라감 → ③④ 재검토 |
| RDS `WriteIOPS` / `CommitLatency` | CommitLatency 급등 없을 것 | 스토리지/인스턴스 한계 → 2단계 |
| RDS `DatabaseConnections` | max_connections의 70% 이하 | 커넥션 고갈 → RDS Proxy |
| 기록기 파드 수 | max(12) 도달 여부 | 도달했는데도 랙이 쌓이면 파티션 수 증설 필요 |
| 접수 API 429 비율 | 초당 1만 건 이하 구간에서 0 | 한도 내에서 발생하면 RQ-04 위반 |

## 6. 수용 한도와 오버플로우 정책 (액션 아이템 ⑥)

> "무조건 대량의 요구사항을 견딜 수 있는 내구성이 중요한 게 아니라, 몇 명의 유저까지 버틸 수 있는 숫자가 들어가야 된다는 거예요. … 시스템을 설계할 때는 이 시스템은 몇 명까지 붙일 수 있게 만들어주겠다, 그게 중요해요."

### 6.1 "몇 명까지"를 숫자로 선언한다

| 시나리오 | 사용자당 주문 속도 | 수용 사용자 수 |
|---|---|---|
| **최악 가정** — 모든 사용자가 API 한도까지 주문 | 8 TPS | **10,000 ÷ 8 = 1,250명** |
| 현실 가정 — 활성 사용자가 초당 1건 주문 | 1 TPS | 10,000명 |
| 조회만 하는 사용자 | 접수 경로 미사용 | 별도 산정 (Redis 조회 경로) |

**계약 문구 (제안)**

> 본 시스템은 **동시 주문 사용자 1,250명(계정당 8 TPS 상한 기준), 초당 주문 1만 건**까지를 응답 목표(체결 p99 0.5초) 내에서 처리한다. 조회 전용 트래픽은 접수 경로와 분리되어 별도로 산정한다.

**이 숫자가 임의가 아니라는 것을 보여주는 사슬**

```
대상 종목 20개 × 종목당 초당 500건 (동종업계 실측 × 고객이 말한 "수십 배")
  = 초당 1만 건                        ← RQ-04 목표
  = 매칭 엔진 최대 20대 (RQ-03: 1종목 = 1엔진)  ← 오토스케일링 max가 여기서 나온다
  ÷ 계정당 8 TPS
  = 동시 주문 사용자 1,250명            ← 고객에게 약속하는 숫자
```

즉 **오토스케일링의 max, 처리량 목표, 수용 사용자 수가 하나의 사슬로 연결된다.** 멘토가 지적한 "오토스케일링도 무한이 아니라 max가 있다"에 대한 정량적 답이 이 사슬이다. 종목이 20개라 매칭 엔진을 21대로 늘려도 아무 의미가 없고, 그 지점이 곧 시스템의 물리적 상한이다.

### 6.2 오버플로우 정책 — 3계층 (RQ-04)

> "그게 벗어나면 순차 처리를 할 건지 드롭을 할 건지는 고객의 요구사항에 따라서. … 금융 도메인은 순차 처리를 하는 것으로 알고 있어요. 주문을 해놨는데 성사되지 않았다가 시간이 지나고 나서 성사되는 경우가 왕왕 있어요."

| 계층 | 조건 | 동작 | 클라이언트 응답 |
|---|---|---|---|
| **L1 정상** | ≤ 1만 TPS, 대기량 정상 | 정상 처리 | `202 Accepted` + 주문 번호, 체결 p99 0.5초 |
| **L2 순차 처리** | 1만 TPS 초과, 대기량 < 임계 | 메시징 계층에 적재해 **지연 처리**. 주문은 유실되지 않고 순서대로 처리됨 | `202 Accepted` + 주문 번호 (체결 지연 가능) |
| **L3 즉시 거절** | 컨슈머 랙 ≥ 임계 | **신규 접수만 거절**. 이미 접수된 주문은 계속 처리 | `429 Too Many Requests` + `Retry-After` |

**드랍을 택하지 않은 이유**: RQ-04("조용히 버리지 마라")·RQ-03(유실 0)에 정면으로 어긋난다. 반면 **거절(429)은 유실이 아니다** — 접수 자체를 하지 않았다고 명시적으로 알리므로 클라이언트가 재시도 여부를 판단할 수 있다.

**L2를 기본으로 두는 도메인 근거**: 금융에서는 낸 주문이 즉시 체결되지 않고 시간이 지나 체결되는 것이 정상 동작이다(멘토 언급). 따라서 "지연 체결"은 장애가 아니라 허용된 상태이며, 계약서에 명시하면 고객도 그렇게 이해한다.

**추가 검토 항목**: 실제 거래소는 L3 상황에서도 **취소 요청은 우선 처리**한다(사용자가 주문을 빼고 싶을 때 막으면 손실이 커지므로). 취소 전용 토픽 또는 우선순위 큐 도입을 검토한다.

### 6.3 인수 시험 부하는 목표가 아니라 검증 수단이다 (RQ-04)

리플레이 엔진은 초당 3만 건을 발생시킨다. **이 숫자는 목표 처리량이 아니라 L1 → L2 → L3 전이가 설계대로 일어나는지 증명하기 위한 값**이다. 발표 시 반드시 구분해서 설명한다.

| 부하 구간 | 확인 대상 |
|---|---|
| ~1만 TPS | L1에서 체결 p99 0.5초 유지 (RQ-04) |
| 1만~2만 TPS | L2 진입, 대기량 증가에 따른 자동 증설이 **2분 내** 완료되는지 (RQ-04) |
| 2만~3만 TPS | L3 진입, 429가 **즉시** 반환되는지 · **기존 주문의 유실이 0인지** (RQ-03·04) |
| 매칭 엔진 증감 중 | 동일 종목 **이중 소유 구간 0초** (RQ-03) |
| 배포 중 | 실패 주문 비율 **0.1% 이하** (RQ-01) |
| 전 구간 재실행 | 동일 입력 재생 시 총 주문 수·종목별 비율이 동일한지 (RQ-04 재현성) |

## 7. MSK / AMP / AMG 채택 근거와 환경 분리 (액션 아이템 ⑦)

> "MSK를 시스템 구성도에 그린 건 좋아요. 근데 이것도 그냥 카프카 파드로 처리해도 되잖아요. … MSK를 쓴 이유와 AMP, AMG같이 AWS 네이티브 서비스를 쓰시려고 하는 이유. 고민 좀 해볼게요."

### 7.1 판단 원칙 — "편해서"가 아니라 "측정 격리"

고객이 RQ-04에서 요구한 것은 **"실제로 버티는지 증명하고, 같은 조건으로 재현할 수 있을 것"**이고, RQ-02에서는 **"검증용 워크로드가 거래 처리 성능을 건드리면 안 된다"**고 했다. 그런데 우리가 증명해야 할 대상은 **접수 API·매칭 엔진·기록기 세 컴포넌트뿐**이다. 따라서 AWS 네이티브 서비스를 쓸지 말지는 이 질문으로 판단한다.

> **"이 컴포넌트가 측정 대상과 같은 자원(CPU·네트워크·디스크)을 나눠 쓰면 인수 시험 값이 오염되는가?"**

오염된다면 클러스터 밖으로 뺀다. 오염되지 않는다면 클러스터 안에서 파드로 돌린다. **이것이 "관리형이 편하니까"보다 훨씬 강한 당위성이고, RQ-02·04에서 직접 나온 기준이다.**

### 7.2 MSK를 쓰는 이유

| # | 근거 | 상세 |
|---|---|---|
| 1 | **측정 격리 (최우선, RQ-02·04)** | 클러스터 안에 Kafka 파드를 띄우면 브로커가 매칭 엔진과 같은 노드·네트워크를 놓고 경합한다. 3만 TPS 구간에서 브로커가 CPU를 가져가면 우리가 재는 건 "매칭 엔진 성능"이 아니라 "Kafka + 매칭 엔진 합산 성능"이 된다 |
| 2 | **데이터 유실 0 (RQ-01·03)** | 셀프 호스팅이면 복제 팩터·ISR·min.insync.replicas·PV 재바인딩을 우리가 운영해야 한다. 파드가 재스케줄될 때 PV가 따라오지 않으면 데이터가 날아간다 |
| 3 | **자격 증명 하드코딩 0건 (RQ-02)** | MSK는 **SASL/IAM 인증**을 지원해 EKS의 IRSA 자격 증명을 그대로 재사용한다. 셀프 호스팅이면 SASL/SCRAM 시크릿을 별도 관리해야 한다 — 관리할 시크릿이 0개인 것과 여러 개인 것의 차이 |
| 4 | **납기 4주 / 3인 (제약)** | 브로커 운영에 쓸 인력이 없다. 우리가 증명할 것은 "Kafka를 운영할 수 있다"가 아니라 "대량 주문을 처리하는 시스템을 설계할 수 있다"이다 |

### 7.3 AMP(Managed Prometheus)를 쓰는 이유

| # | 근거 | 상세 |
|---|---|---|
| 1 | **부하가 가장 큰 순간에 모니터링이 먼저 죽으면 안 된다 (최우선, RQ-02·04)** | 인클러스터 Prometheus는 측정 대상 클러스터 **안에서** 돈다. 3만 TPS 구간에서 스크레이프·TSDB 압축이 CPU·디스크를 먹고, 최악의 경우 OOM으로 죽어 **가장 중요한 순간의 지표를 잃는다.** 그러면 RQ-02("5분 안에 원인 특정")도 RQ-04("증명")도 성립하지 않는다 |
| 2 | **15초 간격 / 15일 보관 (RQ-02)** | 인클러스터는 PV 용량을 미리 계산하고 retention을 관리해야 한다. AMP는 스토리지를 자동 확장하고 기본 보관 기간이 150일이다 |
| 3 | **가용성 (RQ-01과 같은 기준)** | AMP는 Cortex 기반으로 다중 AZ에서 동작한다. 인클러스터로 같은 수준을 만들려면 Thanos/Cortex를 직접 얹어야 한다 |
| 4 | **트레이드오프 (명시)** | AMP는 **인제스트 샘플·스토리지·쿼리 단위 과금**이라 고카디널리티 지표를 무분별하게 remote_write하면 비용이 튄다(RQ-02 위반). → relabel 규칙으로 필요한 시리즈만 전송하고, dev는 인클러스터 Prometheus를 쓴다 |

> **RQ-02의 "신규 컴포넌트 자동 편입"은 AMP가 아니라 K8s가 해준다** — Prometheus의 Kubernetes service discovery가 새 파드를 자동으로 스크레이프 대상에 올리고, AMP는 그 데이터를 받아 저장할 뿐이다. 즉 이 요구는 2장의 K8s 근거이기도 하다(2.5절 ③에서 AWS Batch를 배제한 이유이기도 하다).

### 7.4 AMG(Managed Grafana)를 쓰는 이유

| # | 근거 | 상세 |
|---|---|---|
| 1 | **단일 화면·동일 시간축 (RQ-02)** | 지표가 두 곳에 나뉜다 — **AMP**(앱·K8s 지표)와 **CloudWatch**(MSK·RDS·Fargate 지표, 로그). AMG는 둘 다 네이티브 데이터소스로 붙어 하나의 대시보드에서 같은 시간축으로 본다. 고객이 지적한 "담당자마다 다른 화면을 본다"를 해소하는 지점이다 |
| 2 | **자격 증명 (RQ-02)** | 셀프 호스팅 Grafana로 CloudWatch를 붙이려면 IAM 액세스 키를 데이터소스 설정에 넣게 되기 쉽다. AMG는 **서비스 역할**로 붙어 키가 존재하지 않는다 |
| 3 | **접근 제어** | IAM Identity Center 기반으로 고객사 담당자·심사위원에게 뷰어 권한을 부여한다 |
| 4 | **트레이드오프 (명시)** | AMG는 **활성 사용자당 과금**(에디터/뷰어 요금이 다름)이라 뷰어 계정이 늘면 비용을 확인해야 한다 |

### 7.5 환경별 구성 매트릭스 — FinOps와 이식성 (RQ-02·05)

> "개발 환경에서는 굳이 이런 서비스를 쓸 필요가 없고 그냥 파드로 카프카 생성해서 쓰다가, 프로덕션에 배포하겠다고 하면 비용도 효율적으로 사용했다고 할 수 있거든요." / "개발 환경은 스팟 인스턴스를 돌렸다든지 이런 것도 되게 좋을 수 있어요. 요새는 핀옵스도 되게 중요하거든요."

멘토가 명시적으로 칭찬한 부분이므로 표로 못 박아둔다. 7.1절의 판단 원칙을 뒤집어 적용한 결과이기도 하다 — **dev 환경은 측정 대상이 아니므로 측정 격리가 필요 없고, 따라서 네이티브 서비스를 쓸 이유도 없다.**

| 구성 요소 | **dev** (기능 개발) | **staging** (prod 동형 검증) | **prod** (인수 시험·운영) |
|---|---|---|---|
| Kafka | **파드로 자체 기동** (Strimzi/Bitnami) | MSK Serverless | MSK Serverless |
| 지표 저장 | **인클러스터 Prometheus** | AMP | AMP |
| 대시보드 | 인클러스터 Grafana | AMG | AMG |
| 노드 | **스팟 인스턴스** (Karpenter NodePool) | 온디맨드 (prod 동형) | 온디맨드 |
| DB | RDS 단일 AZ 소형 | Multi-AZ DB 클러스터 | Multi-AZ DB 클러스터 |
| 캐시 | 파드 또는 단일 노드 | ElastiCache | ElastiCache |
| 목적 | **기능 개발**에 집중 | 성능·장애 시나리오 검증 | 인수 시험, 실서비스 |

**RQ-05(같은 정의로 세 환경 + IDC 회귀 대비)를 어떻게 충족하는가** (멘토: "연결 고리만 잘 가져가면 되는 거죠. 카프카에 연결하기 위한 엔드포인트가 달라지는 부분만 해결하면 되잖아요.")

1. **매니페스트는 동일, values만 분리**: 세 환경이 **같은 Helm chart**를 쓰고 `values-dev/staging/prod.yaml`만 다르다. 애플리케이션 코드는 `KAFKA_BOOTSTRAP_SERVERS` 환경 변수만 읽는다. **AS-IS에서 플레이북이 갈라졌던 문제가 구조적으로 재발하지 않는다.**
2. **인증 방식 차이 흡수**: dev(PLAINTEXT) ↔ prod(SASL/IAM) 차이는 Kafka 클라이언트 설정 프로파일로 분리한다.
3. **ExternalName Service + Route53 Private Hosted Zone**: 이전 회차 멘토링([2026-08-05 피드백](mentoring-feedback-20260805.md) 2.2절)에서 권장받은 패턴을 적용한다. 파드는 항상 `kafka.truss.local`을 바라보고, 환경별로 그 이름이 가리키는 실제 엔드포인트만 바꾼다 — **환경이 달라져도 파드 스펙과 재배포가 필요 없다.**
4. **IDC 회귀 시 교체 범위가 명확해진다**: dev 환경이 이미 "파드 카프카 + 인클러스터 Prometheus"로 돌고 있다는 것은, **AWS 관리형 서비스 없이도 이 시스템이 동작한다는 것을 매일 증명하고 있다는 뜻**이다. RQ-05에 대한 가장 실질적인 답이 여기 있다. (반대로 ECS였다면 dev 환경조차 AWS 계정 없이는 못 띄운다 — 2.5절 ①)
5. **staging = prod 동형**: 멘토 지침대로 dev에서 기능을 개발하고, **staging은 prod와 동일하게 구성**해 검증한 뒤 prod에 배포한다.

## 8. Fargate 채택 근거와 지연 완화 (액션 아이템 ⑧)

> "파게이트를 왜 쓰셨어요? 이 워크로드가 어떤 워크로드인데 파게이트가 적절하다는 거죠? … 카펜터를 가지고 쓴다고 했을 때 얘한테 적합한 건 어떻게 할 건지, 지연이 생기는 문제는 어떻게 개선할 건지."

### 8.1 먼저: EKS의 노드 구성 3가지와 우리 선택

| 방식 | 특징 | 과금 | 우리 채택 여부 |
|---|---|---|---|
| **관리형 노드그룹** | AWS 제공 AMI로 노드 구성. 노드가 항상 러닝 | **노드 단위** | **채택** — 백엔드(측정 대상) |
| **셀프 관리형 노드그룹** | 내가 만든 커스텀 AMI로 노드 구성 (예: GPU + CUDA) | 노드 단위 | **미채택** — 커스텀 AMI가 필요한 워크로드가 없다. LLM 추론은 Bedrock(관리형)에 위임하므로 GPU 노드 자체가 불필요 |
| **Fargate** | 서버리스. 요청이 있을 때 파드 단위로 microVM 생성 | **파드 단위** | **채택** — 세션 워크로드 3종 |

셀프 관리형을 **왜 안 쓰는지까지 답해야** 3가지 중 2가지를 고른 이유가 완성된다.

### 8.2 Fargate가 적합한 워크로드의 조건 3가지

1. **간헐적으로 뜨고 지는가** (유휴 시간이 실행 시간보다 압도적으로 긴가) — RQ-02
2. **기동 지연 수십 초를 사용자 경험이 감내하는가**
3. **노드 단위가 아니라 파드 단위 과금이 유리한가** — RQ-02

### 8.3 워크로드별 판정

| 워크로드 | 실행 패턴 | 지연 민감도 | 판정 | 이유 |
|---|---|---|---|---|
| 접수 API·매칭 엔진 | **상시** | RQ-04(0.1초/0.5초), **인수 시험 측정 대상 그 자체** | **EC2 노드그룹** | ① 측정 대상이라 예측 가능한 CPU·네트워크가 필요(RQ-04) ② Fargate는 **DaemonSet 미지원**이라 로그 수집 에이전트를 사이드카로 바꿔야 함(RQ-02) ③ **RQ-04의 2분 증설**에 microVM 부팅 30~60초 + 매번 발생하는 이미지 풀을 얹을 여유가 없다 |
| 시세 수집기 | 상시, `replicas: 1` | 재스케줄이 빠를수록 좋음 | **Fargate** | 단일 파드가 EC2 노드 1대를 통째로 점유하는 건 낭비(RQ-02). 특정 노드에 종속되지 않아 AZ 장애 시 재배치가 단순(RQ-01) |
| AI 트레이더 Job | **세션당 1회, 하루 수 회** | 시작 버튼 → 수십 초 대기 허용 | **Fargate** | 조건 1·2·3 모두 충족. RQ-02의 "끝나면 사라져야 한다"를 과금까지 포함해 만족 |
| 리플레이 엔진 Job | **인수 시험할 때만** | 시험 시작 지연 허용 | **Fargate** (단, 8.5 참고) | 부하 생성 주체라 측정 대상과 완전 분리(RQ-02) |

**Fargate의 진짜 장점을 우리 문맥에서 말하면**: 세션 워크로드는 **하루 대부분 아무것도 실행되지 않는다.** EC2 노드그룹이면 유휴 시간에도 노드 요금이 나간다 — 고객이 AS-IS에서 겪던 **"검증 배치 EC2가 하루 종일 떠 있는" 문제 그대로**다. Fargate는 파드가 뜬 시간만 과금하므로 **RQ-02에 직접 답한다.**

**"써보고 싶어서"도 근거가 된다** (멘토가 인정한 부분): "이 프로젝트가 아니면 EKS의 세 가지 노드 구성을 모두 경험할 기회가 없어서, **워크로드 성격상 정당화되는 지점에 의도적으로 Fargate를 배치했다"**고 말할 수 있다. 단, 위 표처럼 워크로드 특성이 먼저 오고 이건 부가 근거다.

### 8.4 지연 문제 — 원인 분해와 완화책

**지연의 구성**

| 단계 | 소요 | 비고 |
|---|---|---|
| ① microVM 프로비저닝 | **약 30~60초** | Fargate의 구조적 특성. 우리가 줄일 수 없다 |
| ② 이미지 풀 | 이미지 크기에 비례 | **Fargate는 노드 이미지 캐시가 없어 파드마다 매번 풀한다.** 여기가 우리가 줄일 수 있는 지점 |
| ③ 컨테이너 시작 | 앱 기동 시간 | |

AWS 측정에 따르면 **컨테이너 이미지 다운로드가 컨테이너 시작 시간의 약 76%**를 차지한다. 즉 **②가 최대 공략 지점**이다.

**완화책 5가지**

| # | 방안 | 기대 효과 | 상태 |
|---|---|---|---|
| 1 | **이미지 최소화** — 멀티스테이지 빌드 + distroless/`scratch` 베이스 | 백엔드는 **Go**라 정적 바이너리 + distroless로 수십 MB까지 줄일 수 있다. AI 트레이더(Python)는 slim 베이스 + 불필요 의존성 제거 | 미착수 |
| 2 | **zstd 압축 이미지** | AWS 내부 테스트 기준 Fargate 시작 시간 **최대 27% 단축**. ECR이 zstd를 지원한다 | 미착수 |
| 3 | **ECR Interface Endpoint + S3 Gateway Endpoint** | 이미지 메타데이터는 ECR API, **레이어 실체는 S3**에서 받으므로 둘 다 필요하다. NAT를 거치지 않아 풀이 빨라지고 데이터 전송 비용도 준다(RQ-02) | ✅ **이미 `infra/network/endpoints.tf`에 구성됨** |
| 4 | **비동기 상태 설계로 지연을 UX에서 흡수** | 세션 시작 요청에 즉시 `202 + session_id`를 반환하고 프론트는 "준비 중" 상태를 표시, Job status watch로 갱신(3.4절). **지연을 숨기는 게 아니라 상태로 드러내 사용자가 기다릴 수 있게 한다** | 설계 반영 |
| 5 | **지연이 문제가 되면 Karpenter 노드로 이동** | 리플레이 엔진처럼 **시험 중 반복 기동이 잦은** 워크로드는 Karpenter NodePool(스팟)로 옮기면 노드를 재사용하므로 **두 번째 실행부터는 이미지가 캐시돼 훨씬 빠르다** | 조건부 |

**중요 — pause 파드 오버프로비저닝은 Fargate에서 효과가 없다**

노드 스케일링 지연 완화의 표준 기법은 저우선순위 **pause 파드**로 여유 노드를 미리 띄워두고 실제 파드가 이를 선점(preempt)하게 하는 것이다. **그런데 이건 EC2 노드(Cluster Autoscaler/Karpenter) 전용 기법이다.** Fargate는 **파드 1개 = microVM 1개**라 pause 파드를 띄워도 다른 파드가 그 자원을 물려받을 수 없다. 흔한 오해라 문서에 명시해둔다.

Fargate에서 굳이 프리워밍을 하려면 **애플리케이션 레벨**밖에 없다 — 사용자가 세션 설정 페이지에 진입한 시점에 Job을 미리 만들어두고 실제 시작 신호를 기다리게 하는 방식(비용과 맞바꾼다).

### 8.5 Fargate vs Karpenter — 선택 기준 정리

멘토도 발화 중 잠시 혼동했던 부분("아 파게이트? 제가 스팟이랑 헷갈렸는데")이라 명확히 정리한다.

> **지연이 있는 건 Fargate이고, Karpenter는 노드 오토스케일러다. 둘은 대체 관계가 아니다.** 워크로드마다 "Fargate Profile에 올릴지, Karpenter가 띄운 EC2 노드에 올릴지"를 고르는 **배치 선택**이다.

| 기준 | Fargate가 유리 | Karpenter(EC2)가 유리 |
|---|---|---|
| 기동 빈도 | **가끔** 뜬다 (하루 수 회) | **자주** 뜨고 진다 (노드 재사용 + 이미지 캐시 이득) |
| 유휴 시간 | 압도적으로 길다 | 짧다 |
| 기동 지연 허용 | 수십 초 허용 | 초 단위 필요 |
| DaemonSet 필요 | 불필요 | **필요** (로그 수집 등) |
| 스팟 활용 | 불가 | **가능** (dev 비용 절감) |
| 우리 배치 | 시세 수집기, AI 트레이더, 리플레이 | 백엔드(측정 대상), dev 환경 전반 |

### 8.6 측정 계획

인수 시험에서 **Job 생성 시각 → 파드 Ready 시각**을 지표로 수집한다(`kube_job_status_start_time` vs 파드 Ready 조건). 목표치를 다음과 같이 설정하고, 미달 시 8.4의 완화책을 순서대로 적용한다.

| 워크로드 | 목표 기동 시간 |
|---|---|
| AI 트레이더 세션 | **90초 이내** |
| 리플레이 엔진 (분산 4대) | **120초 이내** (전 파드 Ready 기준) |

|---|---|
| 이 시스템, 누가 시켜서 만드는 거예요? | A거래소로부터 의뢰받았습니다. 고객은 **이미 AWS를 쓰고 있지만 IDC 시절 구조 그대로**(EC2에 바이너리 직접 설치, Ansible 배포, 종목을 인스턴스에 고정 할당) 운영 중이고, **거기서 실제로 터진 문제들**을 RQ-01~05로 정리했습니다. |
| 그럼 한 문장으로 왜 K8s죠? | **RQ-01** — 24시간 장이라 점검 창이 0분인데 당일 패치를 해야 합니다. 그래서 CI/CD가 필수이고, 배포 단위가 컨테이너여야 하고, 무중단 롤링이 플랫폼 기본 기능이어야 합니다. |
| CI/CD는 왜 필요하죠? | 고객이 **당일 패치와 점검 창 0분**을 요구했기 때문입니다. 1년에 몇 번 배포하는 시스템이면 필요 없습니다. |
| 지금 EC2 쓰고 있다면서요, 그대로 개선하면 안 되나요? | **5개 요구 전부가 지금 방식으로는 불가**합니다. 대표적으로 **RQ-02** — 고객이 "컴포넌트 늘 때마다 인스턴스 그룹을 새로 띄우는 걸 멈춰달라(집적)"와 "그래도 서로 성능·권한을 건드리면 안 된다(격리)"를 동시에 요구했는데, EC2는 격리 수단이 인스턴스 분리뿐이라 둘이 충돌합니다. |
| **그럼 ECS는요? AWS 쓰면서 굳이 K8s를 얹는 이유는?** | 여기가 핵심입니다. **RQ-01은 ECS도 통과합니다.** ECS를 자르는 건 **RQ-05·03·02**입니다 — ① **RQ-05**: 고객이 3년 내 IDC 회귀를 검토 중인데 **ECS는 컨트롤 플레인이 AWS 리전에 상주**해서 AWS 없이는 못 돕니다(ECS Anywhere도 AWS 연결 필수) ② **RQ-03**: ECS 태스크에는 **순번 신원이 없고 순차 교체 보장도 없어** 고객이 겪은 중복 체결이 재발합니다 ③ **RQ-02**: ECS면 상시/배치/에이전트가 Service·Batch·daemon으로 갈라져 IAM·IaC·배포·모니터링이 이원화됩니다. |
| Lambda로는요? | **RQ-04(0.5초)+RQ-03(순서 역전 0)**이 매칭 엔진을 "상태를 들고 오래 사는, 종목당 하나뿐인 프로세스"로 확정합니다. Lambda는 상태도 없고 동시 실행 수도 제어할 수 없습니다. |
| 오토스케일링은 EC2도 되잖아요? | 맞습니다. 그래서 오토스케일링 자체는 근거로 쓰지 않습니다. 다만 고객은 **"CPU 말고 밀린 주문량 기준으로 2분 이내"**(RQ-04)를 요구했고, 인스턴스 단위 증설로는 그 시간을 못 맞춥니다. 실제로 고객의 현재 CPU 기준 ASG가 무용지물이었습니다. |
| 왜 Job이어야 하죠? | **RQ-02**가 "버튼 누르면 그때 뜨고, 끝나면 사라지고, 재시도·실행시간 상한을 걸어달라"인데 Job의 기능 명세와 그대로 겹칩니다. AWS Batch로 안 뺀 이유도 RQ-02(운영 체계 이원화)입니다. |
| SQS는 왜 필요한가요? | **지금은 필요 없습니다.** 세션 시작은 초당 1건 미만의 제어 이벤트라 버퍼링 대상이 아니고, 접수 API가 동기 응답으로 실패를 즉시 알립니다. 대기열이나 우선순위가 필요해지면 KEDA ScaledJob + SQS로 전환합니다. |
| Cluster Autoscaler가 아니라 Karpenter인 이유는? | 속도만이 아닙니다. CA는 ASG를 거쳐 **3~4분**이라 **RQ-04(2분)을 구조적으로 못 지킵니다.** 추가로 Consolidation(RQ-02 비용 20~40% 절감), Spot 중단 처리, Drift 감지, **인수 시험 중 자발적 중단을 0으로 묶는 Disruption Budget**(RQ-04 재현성)이 있습니다. |
| DB는 왜 오토스케일링이 안 되나요? | 파드는 무상태지만 DB는 상태를 가져 분산 시 **정합성**을 맞춰야 합니다. RQ-03은 Strong Consistency 요구라 분산 대신 **단일 라이터를 유지하고 DB에 도달하는 부하 자체를 구조로 줄이는** 방향을 택했습니다. |
| RDS 병목은 어떻게 푸나요? | 5단입니다 — ① 응답 경로에서 DB 제거 ② 메시징 버퍼 ③ **컨슈머 랙 기반 기록기 스케일**(상한은 파티션 수) ④ COPY 배치 쓰기 + 파티셔닝 ⑤ 랙 임계 초과 시 429. 스케일 트리거와 거절 트리거가 **같은 지표**입니다. |
| 몇 명까지 버티나요? | **동시 주문 사용자 1,250명 / 초당 1만 건**입니다. 대상 종목 20개 × 500 TPS = 1만 TPS이고, 계정당 8 TPS 기준으로 환산했습니다. 매칭 엔진 최대 20대라는 오토스케일 max와 같은 사슬에서 나옵니다. |
| 초과하면 드랍인가요 순차 처리인가요? | 3계층입니다 — 한도 내는 정상, 초과 시 메시징 계층에 적재해 **순차 처리**, 대기량 임계 초과 시 **드랍이 아니라 429 명시적 거절**입니다. 고객이 "조용히 버리지 말라"고 했기 때문입니다. |
| MSK를 왜 쓰나요? 파드로 하면 되잖아요? | **측정 격리** 때문입니다. 클러스터 안에 브로커를 두면 3만 TPS 구간에서 매칭 엔진과 CPU를 경합해 합산 성능을 측정하게 됩니다. **dev 환경은 실제로 파드 카프카 + 스팟**입니다. |
| AMP/AMG는요? | 인클러스터 Prometheus는 **부하가 가장 큰 순간에 먼저 죽어 그때의 지표를 잃습니다.** AMG는 AMP + CloudWatch를 한 시간축에서 보기 위함이고, 고객이 지적한 "담당자마다 다른 화면" 문제를 해소합니다. |
| AWS에 너무 종속되는 것 아닌가요? | RQ-05 때문에 **경계를 나눴습니다** — 실행 계층(파드·배포·StatefulSet·Job 정의)은 표준 K8s라 IDC로 그대로 옮겨가고, 교체 대상은 주변 관리형 서비스로 한정됩니다. **dev 환경이 이미 파드 카프카로 돌고 있어서 그게 가능하다는 걸 매일 증명하고 있습니다.** |
| Fargate를 왜 썼죠? | 세션 워크로드는 **하루 대부분 유휴**라 파드 단위 과금이 RQ-02에 맞습니다. 고객이 AS-IS에서 겪던 "검증 배치 EC2가 하루 종일 떠 있는" 문제를 그대로 해소합니다. 반대로 측정 대상인 백엔드는 예측 가능한 성능과 DaemonSet이 필요해 **EC2 노드그룹**에 뒀습니다. |
| Fargate 지연은 어떻게 해결하나요? | 지연의 76%가 이미지 풀이라 ① 이미지 최소화(Go distroless) ② zstd 압축(최대 27% 단축) ③ ECR/S3 엔드포인트(**이미 구성됨**) ④ 202 즉시 응답으로 UX 흡수. **pause 파드 워밍은 Fargate에서 효과가 없다**는 점도 확인했습니다(1파드 = 1microVM). |

## 10. 남은 미결 사항

- [ ] 1장의 가상 고객사 AS-IS·요구사항(RQ-01~05)을 발표 자료 인트로와 기존 문서 도입부에 반영
- [ ] **ECS 배제 근거 재확인** — 2.5절 ②의 "ECS 태스크에 순번 신원이 없다"와 ④의 "ECS 오토스케일은 CloudWatch 경유"는 AWS 공식 문서로 한 번 더 검증할 것. 발표에서 정면으로 반박당하면 2단계 관문 논증 전체가 흔들리는 지점이다
- [ ] RQ-03(이중 소유 0초)을 실제로 어떻게 구현할지 확정 — StatefulSet 순번에서 종목 할당을 계산하는 방식 + `preStop` 훅 상세 설계, 그리고 이를 인수 시험에서 어떻게 측정할지
- [ ] RQ-01의 "배포 중 실패 주문 0.1% 이하"를 인수 시험 항목으로 편입 — 부하가 걸린 상태에서 `helm upgrade`를 실행하고 실패율을 측정하는 시나리오 추가
- [ ] Karpenter 도입에 따른 Terraform 리팩터링 — 관리형 노드그룹을 시스템 컴포넌트용 최소 구성으로 축소하고 NodePool/EC2NodeClass 추가 (현재 min 2 / max 8, [Truss 인프라 아키텍처](truss-architecture.html) 8장 기준 재조정 필요)
- [ ] RQ-02의 "영향 0" 검증 방법 확정 — 부하 생성기가 도는 동안과 안 도는 동안의 거래 처리 지표 차이를 어떻게 측정할지
- [ ] 세션 제어를 접수 API에 붙일지 별도 `session-controller` Deployment로 분리할지 확정 (3.4절 (4))
- [ ] `executions` 토픽 파티션 수 확정 — 기록기 최대 레플리카 수의 상한이 되므로 인수 시험 전에 결정 (5.3절 ③)
- [ ] L3(429) 진입 임계값이 될 **구체적 컨슈머 랙 수치** 확정 — 1차 부하 시험 결과로 산정
- [ ] 취소 요청 우선 처리(별도 토픽 또는 우선순위 큐) 도입 여부 (6.2절)
- [ ] 이전 회차 액션 아이템 중 미완: ExternalName Service + Route53 Private Hosted Zone 패턴 도입 ([2026-08-05 피드백](mentoring-feedback-20260805.md) 2.2절) — 7.5절의 환경 분리 전략과 함께 진행하면 한 번에 해결됨
