## 1.1 개요

### 1.1.1 시스템 개요
Truss는 대량 주문 상황에서 분산 주문 처리 시스템의 성능과 안정성을 검증하는 시뮬레이션 플랫폼이다. 거래소 자체를 구현하는 것이 아니라 암호화폐 거래소의 주문 처리 구조를 단순화해 재현하며, AI 트레이더가 생성한 주문을 매칭 엔진이 체결한다. AI 트레이더는 사용자가 선택한 과거 기간의 업비트 시세를 판단 근거로 삼아 매매 방향을 결정하며, 이렇게 만들어진 주문이라야 실제 시장과 유사한 패턴으로 매칭 엔진에 현실적인 부하를 줄 수 있다(FR-16).

주문은 실제 거래소로 전송되지 않으며, 접수·매칭·체결·저장은 모두 내부에서 처리한다.

프로젝트의 목적은 주문 집중 상황에서의 처리량, 순서 보장·데이터 정합성 유지, 부하 증가에 따른 확장 안정성을 측정하는 데 있으며, 거래 기능 자체를 구현하는 것은 목적이 아니다. 이를 위해 동일 주문 패턴을 반복 재생할 수 있는 부하 생성 환경과 성능 측정 체계를 구축한다. 실험 대상은 업비트 원화 마켓 20개로 제한한다(선정 기준 및 종목 목록은 1.1.4 참고).

실제 시장은 시세 급변 시 주문량이 순간적으로 수십 배 증가하며, 이때 주문 유실·순서 역전·중복 체결이 발생하면 서비스 신뢰성이 크게 훼손된다. Truss는 이 상황을 인위적으로 재현해 시스템의 성능과 안정성을 정량적으로 검증한다.

### 1.1.2 용어
| 용어 | 설명 |
|---|---|
| 호가창 | 미체결 주문을 가격순으로 정렬한 목록. 매수·매도를 각각 별도로 관리 |
| 접수 API | 마켓명·수량·가격 등 주문 내용의 유효성을 검증해 접수하고 Kafka에 발행하는 API |
| 주문 제출 | AI 트레이더나 리플레이 엔진이 접수 API로 주문을 보내는 행위 |
| 주문 매칭 | 매칭 엔진이 가격-시간 우선 원칙에 따라 매수·매도 주문을 대조해 체결 여부를 판단하는 과정 |
| 주문 체결 | 매칭된 매수·매도 주문의 가격이 일치해 거래가 성사되는 것 |
| 가격-시간 우선 원칙 | 거래소의 주문 순서 결정 규칙. 유리한 가격이 우선이며, 가격이 같으면 먼저 도착한 주문이 우선 |
| 파티션 | Kafka에서 메시지를 나누어 담는 단위. 파티션 내부의 순서는 보장됨 |
| 컨슈머 랙 | 처리되지 않고 쌓여 있는 메시지 수. 값이 증가하면 처리 속도가 부하를 따라가지 못한다는 의미 |

| p99 | 요청의 99%가 해당 시간 내에 처리됨을 의미하는 지표. 평균보다 엄격한 기준 |
| 마켓메이커 | 매수·매도 주문을 상시 양방향으로 제출하는 참여자. 호가창을 채워 거래가 성립되게 하는 역할 |
| 페이퍼 트레이딩(Paper Trading) | AI 트레이더 봇이 선택한 기간의 시세와 호가창을 보고 새로 판단해 매수·매도 주문을 생성하는 모드 |
| 리플레이(Replay) | 이미 생성된 페이퍼 트레이딩 주문 기록을 판단 로직 재실행 없이 그대로 꺼내 재생하는 모드 |

### 1.1.3 실행 모드
**페이퍼 트레이딩 모드**: AI 트레이더가 선택한 기간의 시세와 호가창을 참고해 주문을 생성한다. 목적은 투자 성과가 아니라 실제 시장과 유사한 주문 패턴으로 매칭 엔진에 현실적인 부하를 주는 것이며, 생성된 주문은 시간순으로 파일에 기록해 S3에 저장한다. 시연 및 주문 패턴 수집에 사용한다.

**리플레이 모드**: 기록된 페이퍼 트레이딩 주문 파일을 판단 로직 재실행 없이 그대로 다시 꺼내 재생해 부하를 발생시킨다. AI 트레이더는 실행마다 판단이 달라져 주문이 매번 달라지므로, 코드 변경과 주문 변화 중 무엇이 성능 차이의 원인인지 구분할 수 없다. 리플레이 모드는 입력 조건을 고정해 이 문제를 없애며, 따라서 모든 성능 측정은 리플레이 모드를 기준으로 수행한다.

## 1.2 시스템 구성

### 1.2.1 데이터 흐름 (Data Flow)
**주문 처리 흐름**
1. AI 트레이더(페이퍼 트레이딩 모드)나 리플레이 엔진이 접수 API로 주문을 제출한다
2. 접수 API가 주문을 검증한 뒤 Kafka의 orders 토픽에 발행한다
3. 매칭 엔진이 해당 토픽에서 주문을 소비해 체결을 수행하고, 결과를 executions 토픽에 발행한다
4. 기록기가 체결 결과를 DB(RDS/PostgreSQL)에 저장한다. 저장 대상은 페이퍼 트레이딩 이력, 리플레이 이력, 리플레이시 발생하는 체결 결과로 구분해 관리한다
5. 호가창의 현재 상태와 리플레이시 발생하는 주문 결과는 Redis(ElastiCache)에 반영해 조회 API와 트레이더·리플레이 엔진이 즉시 읽는다
6. 페이퍼 트레이딩이 생성한 주문 결과·체결 결과, 업비트에서 수집한 시세 원본 데이터(초/분/일/주/월/년 단위 시가·고가·저가·종가·거래량, 개별 체결 건의 시각·가격·수량·매수/매도 방향)는 S3에 저장한다

**시세 처리 흐름**
1. 사용자가 페이퍼 트레이딩 모드에서 트레이딩 기간(과거 시점)을 선택한다
2. 시세 수집기가 업비트로부터 선택한 기간의 20개 마켓 시세(초/분/일/주/월/년 단위 시가·고가·저가·종가·거래량, 개별 체결 건의 시각·가격·수량·매수/매도 방향)를 수신해 S3에 원본으로 저장한다
3. AI 트레이더가 시세 수집기(백엔드)가 제공하는 매니페스트/파일 API(HTTP, 풀 방식)를 통해 시세를 받는다(전달 분류는 아래 참고) — 접수 API를 거치지 않는다

**결정**: 시세는 이미 기간이 정해진 과거 데이터이고 요청당 소비자가 하나뿐이라(AI 트레이더 1개 세션), Kafka의 pub-sub·순서보장 이점이 크지 않다. 시세 수집기·AI 트레이더 사이에는 Kafka를 두지 않고, HTTP로 직접 요청/응답하는 풀(pull) 방식을 쓴다(Kafka는 `orders`/`executions` 등 실시간 다자간 이벤트 흐름에만 사용).

**시세 수집기 → AI 트레이더 데이터 전달 분류(매니페스트/파일 API)**
- 최초 1회 일괄 전달(batch 파일): 일/주/월/년 단위 시가·고가·저가·종가·거래량
- 이후 실시간 전달(stream 파일, 이벤트 타임스탬프 간격에 맞춰 순차 재생): 초/분 단위 시가·고가·저가·종가·거래량, 개별 체결 건의 시각·가격·수량·매수/매도 방향

### 1.2.2 설계 원칙
- Kafka 파티션 키는 마켓 이름으로 정한다. 동일 마켓 주문을 항상 같은 파티션에 넣어 순서를 보장한다(NFR-07)
- 한 마켓은 매칭 엔진 한 대만 담당한다. 복수 엔진이 같은 호가창을 다루면 경합으로 성능 저하와 순서 역전이 발생한다
- 호가창은 인메모리로만 유지하고 디스크에 즉시 쓰지 않는다(NFR-03 충족 목적). 장애 시에는 주문 기록을 리플레이해 복구한다(FR-08)
- 업비트 접속 수 제한으로 시세 수집기는 단일 인스턴스로 운영한다
- 트레이더는 판단 로직과 주문 생성 로직을 분리한다. 판단은 수 초 주기로 방향만 결정하고, 주문 생성은 그 방향에 따라 빠르게 처리한다. 이렇게 분리해뒀기 때문에 5종 봇 중 모멘텀 추종·평균회귀 봇의 판단부가 AWS Bedrock의 Claude를 호출하더라도, 그 응답 지연이 주문 생성 속도(부하량)에는 영향을 주지 않는다

| DB | RDS |
| 캐시(호가창 상태·리플레이 주문 결과) | ElastiCache(Redis) |
| 저장소(시세 원본·주문 기록 파일·주문·체결 결과) | S3 |
| 모니터링 | Amazon Managed Prometheus + Grafana, CloudWatch Logs |

> AI 트레이더, 리플레이 엔진, 백엔드(접수 API·매칭 엔진)는 각각 별도의 EKS 클러스터에서 실행한다(AI 트레이더·리플레이 엔진은 Kubernetes Job). 리플레이 엔진은 성능 측정의 부하 생성 주체이고 매칭 엔진은 측정 대상이므로, 같은 클러스터에서 자원을 공유하면 CPU·네트워크 경합으로 측정값이 왜곡될 수 있다 — 부하 생성기와 측정 대상의 인프라를 분리하는 것은 성능 테스트의 기본 원칙이다. AI 트레이더도 리플레이 성능 시험과 동시에 실행될 수 있어 같은 이유로 분리한다. 트레이딩 세션 단위로 시작·종료되는 워크로드라 상시 기동되는 EC2보다 Job 모델이 적합하며, IRSA(파드 단위 IAM 역할)로 Bedrock 접근 권한을 최소화한다.

### 1.2.4 역할 분담 (R&R)
- A 애플리케이션: FR-01, FR-13, FR-25
- B 매칭 도메인: FR-05~11
- C 인프라·검증: FR-14, FR-16~24, FR-26, FR-27

역할 구분 기준은 Kafka다. A는 주문을 Kafka에 넣는 데까지, B는 Kafka에서 꺼내 처리하고 다시 넣는 데까지, C는 그 기반과 트레이더·부하·지표를 담당한다. 서로의 코드는 직접 호출하지 않고, 사전에 정의한 규격으로만 통신한다.

## 1.3 기능 요구사항
**우선순위 기준**
- 필수: 미구현 시 프로젝트 목표 달성 불가
- 중요: 미구현 시 시험 결과의 신뢰성 저하
- 선택: 일정에 여유가 있을 경우 구현

### 1.3.1 주문 접수 (A)
**[필수] FR-01 주문 접수**

마켓명, 수량, 가격, 가격 단위의 유효성을 검증한 뒤 접수하고 주문 번호를 반환한다
- 검증: 정상 주문 → HTTP 202 + 주문 번호, Kafka에서 조회 가능
- 검증: 잘못된 주문 → HTTP 400 + 오류 코드, Kafka 미반영
- 검증: 컨슈머 랙이 기준치를 초과한 상태에서는 신규 요청을 HTTP 429로 즉시 거절(NFR-13)

**[중요] FR-02 중복 주문 방지**

네트워크 재시도로 동일 주문이 중복 도착해도 1회만 접수한다(멱등성)
- 검증: 동일 주문 번호로 2회 요청 시 응답은 동일하고 Kafka에는 1건만 반영

**[중요] FR-03 주문 취소 접수**

미체결 주문의 취소 요청을 접수한다
- 검증: 취소 시 잔여 수량이 호가창에서 제거되며, 전량 체결된 주문의 취소는 거절

**[필수] FR-04 Kafka 발행**

마켓명 기준으로 파티션을 결정해 발행한다. 동일 마켓 주문을 항상 같은 파티션에 넣어야 순서가 보장되므로(NFR-07), 파티션 배정 기준은 마켓명으로 고정한다
- 검증: 동일 마켓 주문 1,000건이 동일 파티션에 순서대로 적재

### 1.3.2 주문 매칭 (B)
**[필수] FR-05 호가창 관리**

마켓별 미체결 주문을 가격순으로 관리한다
- 검증: 매수는 고가순, 매도는 저가순 정렬

**[필수] FR-06 주문 매칭**

가격-시간 우선 원칙에 따라 매수·매도를 체결하며, 체결가는 선행 주문가를 따른다
- 검증: 사전 정의한 20개 시나리오의 체결 결과가 기대값과 전부 일치

**[필수] FR-07 부분 체결**

상대 수량이 부족하면 가능한 만큼만 체결하고 잔량은 호가창에 유지한다
- 검증: 매도 100주 대비 매수 300주 주문 시 100주 체결, 200주 잔량 유지

**[필수] FR-08 호가창 복구**

매칭 엔진 재시작 시 저장된 주문 기록을 리플레이해 호가창 상태를 복원한다
- 검증: 주문 1만 건 처리 후 강제 재시작 시, 복구된 마켓별 잔량이 재시작 직전과 일치

**[필수] FR-09 체결 결과 발행·저장**

체결 발생 시 결과를 Kafka에 발행하고, 페이퍼 트레이딩/리플레이 이력을 구분해 DB(RDS)에 저장한다
- 검증: 체결 결과의 매수·매도 주문 번호가 실제 체결 주문과 일치
- 검증: Kafka 발행 건수와 DB 저장 건수가 일치

**[중요] FR-10 취소 처리**

취소 요청을 받아 호가창에서 해당 주문을 제거한다
- 검증: 제거 후 조회 불가, 기체결 수량은 취소 대상에서 제외

**[중요] FR-11 마켓 재분배**

매칭 엔진 수 증감 시 20개 마켓을 재분배한다. 한 마켓은 항상 정확히 한 엔진만 담당해야 한다(1.2.2). 엔진 수가 바뀔 때마다 담당 마켓을 다시 나누지 않으면 이 원칙이 깨진다
- 검증: 2대→4대 확장 시 마켓이 중복 없이 분배되고, 한 마켓을 두 인스턴스가 동시 처리하는 구간이 없음

### 1.3.3 조회 및 시세 수집 (A, C)
**[필수] FR-12 호가창 조회**

마켓별 호가창을 조회한다
- 검증: 조회 결과가 매칭 엔진의 실제 상태와 일치, NFR-04 응답 시간 충족

**[선택] FR-13 거래 내역 조회**

최근 순으로 거래 내역을 조회한다
- 검증: 페이지 이동 시 누락·중복 없음

**[필수] FR-14 시세 수집 (C)**

페이퍼 트레이딩 모드에서 사용자가 트레이딩 기간(과거 시점)을 선택하면, 해당 기간에 대한 20개 마켓의 초/분/일/주/월/년 단위 시가·고가·저가·종가·거래량과 개별 체결 건의 시각·가격·수량·매수/매도 방향을 업비트로부터 수신해 원본 데이터를 S3에 저장한다. AI 트레이더는 Kafka가 아니라 시세 수집기의 매니페스트/파일 API(HTTP)를 통해 이 데이터를 받는다(FR-16 참고). 이 시세는 FR-16 트레이더 봇의 판단 입력으로 사용되므로, 수집이 실패하면 봇이 현실적인 주문을 만들지 못해 부하 생성 자체가 무의미해진다

**결정**: 시세를 별도로 Redis에 캐시하지 않는다 — 소비자가 AI 트레이더 하나뿐이고, 요청마다 시세 수집기가 S3/매니페스트 API로 바로 응답할 수 있어 별도 캐시 계층이 조회 성능에 실질적으로 도움이 되지 않는다. Redis(ElastiCache)는 매칭 엔진의 호가창 상태·리플레이 주문 결과(FR-08 등)에만 사용한다(1.2.1 참고)
- 검증: 선택한 기간의 데이터가 누락 없이 전량 S3에 저장됨

### 1.3.4 AI 트레이더 및 부하 생성 (C)
**[필수] FR-26 트레이딩 기간 선택**

페이퍼 트레이딩 모드 진입 시 사용자가 트레이딩할 기간(과거 시점)을 선택한다. 선택한 기간은 FR-14 시세 수집의 대상 범위를 결정한다
- 검증: 기간 선택 후 해당 기간의 시세만 수집됨
- 검증: 기간을 선택하지 않으면 페이퍼 트레이딩이 시작되지 않음

**[필수] FR-16 트레이더 봇**

5종 봇이 시세와 호가창을 참고해 주문을 생성한다: 마켓메이커(양방향 상시 호가), 모멘텀 추종(상승 추종 매수), 평균회귀(과열 시 매도), 노이즈(소량 무작위 주문), 대량 주문자(간헐적 대량 주문). 마켓메이커가 전체 주문의 50% 이상을 담당하며, 호가창을 채워 거래 성립 자체를 가능하게 하는 역할이다. 이 봇 없이는 매칭 엔진 성능 측정이 불가능하다.

AI 트레이더는 시세 수집기(백엔드)의 매니페스트/파일 API(HTTP, 풀 방식)를 통해 데이터를 두 단계로 받는다: 최초 1회 일괄 전달(batch 파일: 일/주/월/년 단위 시가·고가·저가·종가·거래량)과 이후 실시간 전달(stream 파일: 초/분 단위 시가·고가·저가·종가·거래량, 개별 체결 건의 시각·가격·수량·매수/매도 방향 — 이벤트 타임스탬프 간격에 맞춰 순차 재생)
- 검증: 5종 봇 동시 실행 시 호가창 양방향 주문이 유지됨
- 검증: 10분 실행 시 전체 주문의 20% 이상 체결

**[필수] FR-17 주문 기록**

페이퍼 트레이딩 모드에서 생성한 주문 전량을 파일로 기록해 S3에 저장한다. 이 파일은 FR-18 리플레이의 입력이 된다. 파일이 누락되면 리플레이 시 실제 페이퍼 트레이딩 모드와 다른 부하가 만들어져 성능 비교의 기준이 깨진다
- 검증: 시간순 복원 가능, 기록 건수와 접수 건수 일치

**[필수] FR-27 리플레이 선택 및 구간 지정**

리플레이 모드 진입 시 사용자가 실행할 리플레이와 그 리플레이 내에서 실행할 구간을 선택한다. 구간 선택이 끝나야 리플레이가 시작된다
- 검증: 리플레이 목록에서 선택한 리플레이만 재생됨
- 검증: 지정한 구간만 재생되고 구간 밖 데이터는 재생되지 않음

**[필수] FR-18 리플레이 엔진**

S3에 기록된 페이퍼 트레이딩 주문 파일을 지정 배속으로, 판단 로직 재실행 없이 그대로 재생해 부하를 발생시킨다. 이 과정에서 발생하는 주문 결과는 Redis에, 체결 결과는 DB에 저장한다. AI 트레이더는 실행마다 판단이 달라져 코드 변경과 주문 변화 중 무엇이 성능 차이의 원인인지 구분할 수 없다(1.1.3). 따라서 모든 성능 측정은 고정된 입력을 재생하는 이 기능을 기준으로 수행한다
- 검증: 동일 파일 재생 시 총 주문 수·마켓별 비율 동일
- 검증: 100배속 재생 시 초당 전송량이 목표치 대비 오차 5% 이내

**[중요] FR-19 리플레이 엔진 분산 실행**

단일 리플레이 엔진으로 부하가 부족할 경우 마켓 단위로 분산 실행한다. 리플레이 엔진 자체가 병목이 되면 측정치가 시스템이 아닌 리플레이 엔진 성능을 반영하게 되므로 필요하다
- 검증: 4대 확장 시 전송량이 1대 대비 약 4배, 리플레이 엔진 CPU 사용률 80% 이하

**[필수] FR-20 자동 확장**

Kafka 컨슈머 랙 증가 시 매칭 엔진을 자동 확장하고, 여유 발생 시 축소한다. 부하 생성기는 이론상 처리 한계(초당 1만 건, 1.4.1)를 넘는 부하를 발생시킨다. 엔진 수가 고정되어 있으면 랙이 계속 쌓여 NFR-13 거절만 반복될 뿐, 시스템이 부하에 실제로 대응하는지 확인할 수 없다
- 검증: 급격한 부하 증가 시 지정 시간 내 확장, 부하 종료 시 원상 축소

**[필수] FR-21 지표·로그 수집**

TPS(주문/체결), 컨슈머 랙, 응답 시간, 접속자 수, 서버 대수, 자원 사용률, 오류율을 수집한다. 전 서버 로그를 중앙 집계하고, 주문 단위로 접수~저장 구간별 소요 시간을 추적 가능하게 한다. 부하 시험(WBS 8.4)에서 목표치 미달이 확인되더라도, 이 지표가 없으면 접수·매칭·저장 중 어느 구간이 원인인지 특정할 수 없어 WBS 8.7 병목 개선이 불가능하다
- 검증: 전 지표가 대시보드에 표시됨
- 검증: 주문 번호 검색 시 구간별 소요 시간 조회 가능

### 1.3.5 인터페이스 규격 및 배포 전략 (전원, C)
**[필수] FR-22 규격 사전 확정**

API, Kafka 메시지, 주문 기록 파일 형식을 1주차에 문서화하고 저장소에서 버전 관리한다. A/B/C가 서로의 구현 완료를 기다리지 않고 병렬로 개발하려면(FR-23) 세 팀이 주고받는 인터페이스가 먼저 고정되어 있어야 한다
- 검증: 실제 응답과 규격 문서 간 자동 검사 수행
- 검증: 규격 위반 변경 시 배포 차단

**[필수] FR-23 독립 실행·검증**

각 담당 영역을 타 영역 구현 없이 실행·시험할 수 있어야 한다(병렬 개발 전제 조건)
- 검증: A는 매칭 엔진 없이, B는 접수 API 없이 각자 시험 통과

**[중요] FR-24 배포·환경 분리**

코드 푸시 시 자동 빌드·무중단 배포하며, 테스트 통과 시에만 병합을 허용하고 담당자별 환경을 분리한다. 4주라는 짧은 일정 안에서 WBS 8.7 병목 개선처럼 반복적인 배포가 필요하다. 담당자별 환경이 분리되어 있지 않으면 한 사람의 변경이 다른 두 사람의 시험을 방해해 병렬 개발이 무너진다
- 검증: 부하 상태에서 배포 시 오류율 0.1% 이하
- 검증: 테스트 실패 시 병합 차단

**[중요] FR-25 모니터링 화면**

마켓별 호가창, 거래 내역, 처리량 추이, 봇별 주문 현황을 시각화한다. 부하 시험 중에는 시스템 상태를 실시간으로 관찰해 이상 징후를 즉시 포착하는 용도로 사용하며, 데모데이 시연(WBS 9.3)에서는 처리량 변화를 눈으로 보여주는 용도로 사용한다
- 검증: 트레이더 실행 중 호가창 변화와 처리량 변화가 화면에 반영됨

## 1.4 비기능 요구사항

### 1.4.1 성능
- NFR-01 주문 접수 초당 1만 건 이상
- NFR-02 거래 성사 초당 1만 건 이상
- NFR-03 주문을 받고 거래 결과가 나올 때까지 p99 500밀리초 이하
- NFR-04 접수 응답 p99 100밀리초, 호가창 조회 p95 50밀리초 이하

**목표 설정 근거**
- 마켓이 20개이므로 매칭 엔진 확장은 20대에서 의미가 소멸한다
- 마켓당 초당 500건 처리를 가정하면 20개 마켓 기준 초당 1만 건이 이론상 처리 한계다
- 접수 성능이 매칭 성능을 넘어서도 의미가 없으므로 NFR-01과 NFR-02는 동일한 목표치로 설정한다
- 부하 생성기는 이 한계(초당 1만 건)를 초과하는 초당 3만 건까지 부하를 발생시킨다. 이는 목표 처리량이 아니라, 처리 한계 초과 시 시스템이 지연 없이 요청을 거절하는지(NFR-13), 컨슈머 랙 기준 자동 확장이 정상 동작하는지(FR-20)를 검증하기 위함이다

### 1.4.2 데이터 정합성
- NFR-07 같은 마켓 안에서 거래 순서 규칙을 어긴 사례 0건
- NFR-08 접수됐다고 응답한 주문이 사라진 사례 0건
- NFR-09 같은 주문이 두 번 거래된 사례 0건
- NFR-10 매수 총량과 매도 총량이 정확히 일치

### 1.4.3 가용성 및 확장성
- NFR-11 매칭 엔진 강제 종료 후 60초 이내 처리 재개 — Pod 재시작과 FR-08 호가창 복구에 걸리는 시간의 상한을 정해, 장애 1건이 CT 시험 전체를 무효화하지 않도록 한다
- NFR-12 서버 1대 장애 또는 Kafka 1대 정지 시에도 데이터 유실 없음 — Kafka 복제와 DB 트랜잭션만으로 단일 노드 장애를 흡수해야 NFR-08·NFR-09·NFR-10의 정합성 목표가 장애 상황에서도 유지된다
- NFR-13 처리 불가능한 부하 발생 시 지연 응답 대신 즉시 거절 — 지연 응답은 클라이언트 재시도를 유발해 부하를 가중시킨다. 컨슈머 랙이 기준치를 초과하면 HTTP 429로 즉시 거절한다
- NFR-14 컨슈머 랙이 기준치를 초과한 뒤 120초 이내 서버 증설 완료 — 확장이 지연될수록 컨슈머 랙이 계속 쌓여 NFR-03(p99 500ms)을 벗어나므로, KEDA 확장 소요 시간의 상한을 별도로 정한다
- NFR-15 매칭 엔진을 2배로 늘리면 처리량이 1.5배 이상 — 마켓 재분배 중 일시 정지가 발생하고 마켓당 처리 속도는 고정되어 있어 선형 확장은 되지 않는다

### 1.4.4 모니터링과 보안
- NFR-16 지표를 15초 이하 간격으로 모으고 15일 이상 보관 — 15초보다 성긴 간격은 급격한 컨슈머 랙 변화를 놓치고, 4주 일정 동안 반복되는 부하 시험(WBS 8.4) 결과를 서로 비교하려면 최소 2주 이상의 이력이 남아 있어야 한다
- NFR-17 처리량, 응답 시간, 컨슈머 랙, 서버 수, 접속자 수를 단일 화면에서 동일 시간축으로 확인 — 지표가 분산되어 있으면 부하 증가와 서버 확장, 지연 간의 상관관계를 파악하기 어렵다
- NFR-18 비밀번호나 접속 정보를 설정 파일에 그대로 적어두지 않고, 서버끼리 꼭 필요한 통신만 허용하며, 컨테이너를 관리자 권한으로 실행하지 않음 — 시험용 시스템이라도 쿠버네티스 클러스터와 저장소 접속 정보가 저장소(FR-22)와 CI 로그에 함께 노출되므로, 최소한의 보안 위생 없이는 실험 환경 자체가 침해될 수 있다
