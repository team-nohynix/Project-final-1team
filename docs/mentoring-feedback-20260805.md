시스템 아키텍처 다이어그램(전체 구조 + AI 트레이더 상세)을 발표하고 피드백을 받았다. 멘토는 발표 중간중간 특정 설계 선택 몇 가지에 대해 긍정 코멘트를 남겼고(1장), 동시에 여러 미해결 지점·보강 필요 사항을 지적했다(2장). 또한 "구성도를 잘 그리는 것 자체가 평가에서 비중이 크다"는 일반 조언도 있었는데, 이건 우리 구성도에 대한 평가가 아니라 **문서화 전반에 대한 일반론**이라 그렇게 구분해서 기록한다.

## 1. 멘토가 특정 선택에 대해 긍정 코멘트한 부분

각 항목은 멘토가 우리 설계의 해당 지점을 직접 짚어 말한 것만 기록한다 (일반론 제외).

- 정적 사이트를 CloudFront + OAC로만 접근 허용한 구성: "OAC로만 접근을 허용했다라는 컨셉은 되게 좋아요"
- 부하 목표를 "초당 3만 건"처럼 구체적 수치로 잡은 것: "3만 건이라는 수치를 정한 것은 되게 좋아요. 정확한 수치가 있는 게 조금 더 있어 보여요"
- AI 트레이더/리플레이를 Kubernetes Job으로 실행하는 발상: "잡 쓰고 이런 거 너무 괜찮아요" — 다만 곧바로 "트리거를 어떻게 받을 거냐"는 지적이 이어짐(2.6절, 무조건적인 긍정은 아니었음)
- 실제 부하 생성기(JMeter, k6 등) 대신 리플레이 엔진을 직접 구현해 테스트하는 방식: "이런 부하 테스트기는 많아요... 어쨌든 잘 만드셨어요. 저는 나쁘지 않다고 봐요" (테스트 방식에 국한된 코멘트)
- "대량 주문에도 버틸 수 있는 시스템을 만든다"는 시나리오 취지 자체: "이 시나리오는 되게 좋았어요" — 단, 제목 표현 방식은 별도로 지적함(2.3절)

## 2. 주요 피드백 및 액션 아이템

### 2.1 EKS 클러스터 4개 → 단일 클러스터 (✅ 반영 완료)

**피드백**: "EKS 클러스터를 4개 구현하는 건 바람직하지 않다." 역할별로 분리하고 싶으면 클러스터가 아니라 **같은 클러스터 안의 노드그룹으로 분리**하는 게 맞다. 클러스터를 나누면:
- 클러스터 간 통신에 인그레스/Gateway API가 필요해져서 오히려 병목이 생김(같은 클러스터 내라면 서비스 디스커버리로 끝날 일)
- 과금이 늘어남
- 클러스터 분리는 dev/staging/prod처럼 **환경이 다를 때** 하는 것이지, 같은 서비스의 역할만 다르다고 나누는 게 아님
- Node Affinity로 특정 노드에 강제 배치하는 건 GPU 노드처럼 하드웨어가 실제로 달라야 정당화됨 — 지금 케이스는 그 당위성이 불명확

**액션 아이템**: 오늘 논의를 통해 이미 **단일 클러스터 + 노드그룹(backend, taint) + Fargate Profile 3개(collector/ai-trader/replay, 네임스페이스 셀렉터)**로 재설계 완료. `architecture.md`·`infra-placement-design.md`에 반영됨. Terraform 리팩터링은 아직 미착수.

### 2.2 파드의 S3 접근 방식

**피드백**: 파드가 S3에 접근하려면 IAM Role이 필요하고(EC2가 Role을 쓰듯), 파드는 **IRSA**로 Role을 받는다(K8s ServiceAccount로 AWS 서비스를 쓸 수 있게 해주는 OIDC 연동 — "네이버 아이디로 가비아 로그인"과 같은 개념). 다만 엔드포인트 주소를 파드에 어떻게 심어둘지는 별개 문제:
- ConfigMap에 넣는 방법도 있지만, 멘토 추천 방식은 **파드 → ExternalName 타입 Service → Route53 Private Hosted Zone 레코드(`s3.cloud.local` 같은) → 실제 S3 엔드포인트** 순서로 연결하는 것. 엔드포인트가 바뀌어도 Route53 레코드만 갱신하면 되고 파드 재배포가 필요 없음
- VPC 내부 통신은 기본적으로 internal, VPC 바깥(S3 등 AWS 서비스 포함)과의 통신은 게이트웨이(IGW/NAT)를 거쳐야 함 — **VPC Endpoint(PrivateLink)를 쓰면 게이트웨이 없이 프라이빗하게 통신 가능**해서 비용 절감 + 보안 강화 두 가지 효과. "무조건 써야 한다"고 강조

**액션 아이템**: 현재 `infra/network/endpoints.tf`에 S3 Gateway Endpoint + Interface Endpoint 5종이 이미 구성돼 있음(VPC Endpoint 자체는 기 반영). ExternalName Service + Route53 Private Hosted Zone 패턴은 아직 미도입 — S3 접근이 필요한 파드(recorder, collector 등)에 도입 검토 필요.

### 2.3 프로젝트 제목·시나리오 프레이밍

**피드백**: 현재 제목("대량 주문에 강건한 쿠버네티스 실시간 거래 시스템")에 "쿠버네티스"·"부하검증"이 들어가는 건 어색하다 — 이것들은 **구현 수단이지 서비스의 목적이 아님**. 부하검증은 옵저버빌리티/모니터링 영역이지 핵심 가치가 아니라는 것.

- 제목 제안: **"대량 주문에 강건한 코인 거래 시스템"** (쿠버네티스는 "그걸 어떻게 구현했는가"의 답)
- 가상 고객사 시나리오 제안: "코인 거래소로부터 시스템 구축을 의뢰받았고, 고객이 초당 N건까지 버텨야 한다는 요구사항을 줬다"는 식으로 아키텍처 결정에 비즈니스 맥락을 부여하는 방식을 권장
- 부하 테스트(리플레이 엔진)는 "우리가 만든 시스템이 실제로 버티는지 검증한 방법"으로 시나리오와 분리해서 설명하는 게 깔끔하다고 언급

**액션 아이템**: 발표 자료·문서 제목 및 인트로 재구성 필요. `requirements.md` 목적 서술도 이 톤에 맞춰 다듬을지 검토.

### 2.4 "왜 쿠버네티스를 쓰는가" 당위성 보강

**피드백**: "모든 기술 선택엔 당위성이 있어야 한다." 오토스케일링 하나만으론 K8s를 쓸 이유로 부족함(EC2 오토스케일링으로도 확장은 됨). 문서에 추가로 넣어야 할 근거:
- 병렬화된 MSA 환경이라는 점
- 신속한 패치·배포가 필요하다는 점
- 컨테이너 기반 시스템으로 운영해야 하는 이유
- K8s + 오토스케일링이 주는 **가용성 향상**과 **비용 절감**(평소엔 축소 운영) 두 효과를 명시

**액션 아이템**: `architecture.md`나 `infra-placement-design.md`에 "왜 EKS인가" 절을 별도로 추가해 당위성을 명문화.

### 2.5 RDS 부하 처리 — 미해결 과제

**피드백**: 파드는 오토스케일링으로 무한정 늘릴 수 있지만 **RDS는 그렇게 늘어나지 않는다**. 프론트·백엔드가 부하를 버텨줘도 결국 DB가 못 받으면 거기서 정체된다(인터파크 대기열 비유 — 프론트가 버텨줘도 결국 DB 처리 속도가 병목). 명시적으로 "고민거리로 가져가라"고 남긴 미해결 이슈이며, 멘토가 구체적인 해법을 제시하지는 않았다.

**액션 아이템**: 다음 멘토링 전까지 RDS 병목 대응 방안 검토 필요.

### 2.6 Kubernetes Job 트리거 메커니즘 — 중간 계층 필요

**피드백**: **"Job 자체는 외부 트리거를 직접 받을 수 없다."** 프론트엔드에서 버튼을 눌러 신호를 보내는 것까지는 되는데, 그 신호를 받아서 실제로 Job 리소스를 생성해주는 **중간 계층이 필요**함 — 예: Lambda 함수(SQS나 API Gateway와 조합)가 트리거를 감지해서 Job 매니페스트를 생성/적용. 팀이 아직 이 부분의 정확한 동작 흐름을 확정하지 못한 상태였음.

**액션 아이템**: AI 트레이더/리플레이 엔진 Job을 실제로 어떻게 기동시킬지 설계 필요 — Lambda가 K8s API(또는 `kubectl apply` 상당)를 호출해 Job을 생성하는 구조로 구체화. SQS 큐잉이 필요한지(동시 세션 여러 개 처리 시 순서 보장/버퍼링 목적)도 함께 검토.

### 2.7 Terraform vs Helm 경계

**피드백**: Terraform으로는 **VPC~EKS 클러스터 생성까지(+ 클러스터 안의 Ingress/Gateway API 정도)**만 관리하고, 그 이상(클러스터 내부에 설치하는 컨트롤러·애플리케이션 등)은 **Helm**으로 넘기는 걸 권장. 전부 Terraform에 넣으면 코드가 무거워짐.

**액션 아이템**: 현재 `infra/irsa-alb-controller.tf` 등 ALB Controller의 IAM(IRSA) 부분은 Terraform 영역이라 문제없음 — 실제 ALB Controller 설치(Helm chart)는 Terraform 밖에서 진행하는 것으로 이미 방향이 맞음. KEDA, Cluster Autoscaler 등 나머지 애드온도 같은 원칙(IAM만 Terraform, 설치는 Helm) 유지.
