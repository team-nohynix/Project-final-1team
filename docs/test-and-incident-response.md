# 테스트 및 장애 대응 문서

## 문서 개요
이 문서는 Truss 프로젝트의 테스트 전략과, 개발·부하시험 과정에서 실제로 발생한 장애 사례 및 대응을 정리한 것이다. 요구사항의 검증 기준은 [docs/requirements.md](docs/requirements.md)를, 각 항목의 코드 근거는 [CLAUDE.md](../CLAUDE.md)를 함께 참고한다. 이 문서에 나오는 FR/NFR 번호는 `docs/requirements.md` 현재 버전의 번호를 그대로 따른다.

## 1. 테스트 전략

이 프로젝트는 처음부터 **"순수 로직은 단위테스트로, 실제 외부 시스템(Kafka/Redis/MySQL/S3/Bedrock)을 건드리는 코드는 로컬 인프라를 띄워 손으로 검증"**이라는 원칙을 6개 Go 모듈 전부에서 일관되게 지켰다.

- **단위 테스트 대상**: 결정적이고 실수하기 쉬운 순수 로직 — 가격 반올림, 원형 버퍼, 매칭 알고리즘, 배치 트리거, JSON 디코딩, 상태 전이 등. 표준 라이브러리 `testing`만 사용하고(외부 목킹 라이브러리 없음), 테스트는 같은 패키지에 두어(white-box) 비공개 헬퍼도 직접 테스트한다. Kafka publisher/Redis store/DB store처럼 실제 I/O가 필요한 의존성은 fake 인터페이스 구현체로 대체해 handler 로직만 따로 검증한다.
- **단위 테스트로 검증하지 않는 대상**: 실제 네트워크·AWS 호출이 본질인 코드(Upbit REST 호출, S3 업로드, 실제 Kafka/Redis 클라이언트, Bedrock 호출) — 이런 코드는 로컬 `infra/dev-kafka`/`dev-redis`/`dev-mysql`을 띄우고 `go run .` + `curl`/실제 `trader` 실행으로 검증한다. 이 방식으로만 발견 가능했던 실제 버그가 다수 있다(5절 참고) — 이것이 이 원칙을 유지하는 근거다.
- **결정성(determinism) 검증**: `matching/orderbook`은 동일 이벤트 시퀀스를 두 번 재생했을 때 최종 호가창 상태가 바이트 단위로 동일한지 검증하는 테스트를 별도로 둔다 — 매칭 엔진의 크래시 복구(FR-08)가 재생의 결정성에 의존하기 때문에, 이 가정이 깨지는 것을 조기에 잡기 위함이다.

## 4. 부하 테스트 및 스케일 테스트 결과

**FR-19 분산 리플레이 스케일 테스트 (2026-08-11)**: 로컬 단일 머신에서 `orderapi`+`matching`+Kafka+Redis 전체 스택을 대상으로 279,936건(20개 마켓)을 `-speed=500`으로 1/2/4/7 인스턴스 재생.

| 인스턴스 수 | 처리량(orders/sec) |
|---|---|
| 1 | 1,379 |
| 2 | 1,124 |
| 4 | 1,133 |
| 7 | 1,333 |

결과는 인스턴스 수에 비례해 늘지 않고 대체로 평탄했다(2~4대에서 오히려 소폭 하락). 이 기간 동안 `matching`의 백프레셔는 한 번도 트립되지 않아 매칭 엔진이 병목이 아니었음을 확인했고, 제출 실패 건수도 모든 구간에서 0건이었다 — 즉 `replayengine`의 샤딩 로직(런ID 그룹핑, 마켓 분할, 총 주문 수) 자체는 정확히 동작했다. **결론**: 병목은 로컬 테스트 환경 자체(단일 `orderapi` 프로세스, 모든 프로세스+Docker 컨테이너가 한 머신의 CPU/네트워크를 공유)에 있었을 가능성이 높고, 이 결과만으로는 "리플레이 엔진을 실제로 수평 확장하면 처리량이 NFR-01(초당 1만 건)에 가까워지는가"라는 원래 질문에 답할 수 없다 — 이는 `orderapi`/`matching`/Kafka가 실제로 독립된 자원을 가진 다중 인스턴스 AWS 배포에서만 확인 가능하다. 이 테스트는 "샤딩 메커니즘 자체는 정확하다"는 것의 확인으로만 취급한다.

## 5. 장애 사례 및 대응 (Incident Postmortems)

개발·부하시험 과정에서 실제로 발생했고 원인 분석·수정·재검증까지 완료된 사고들이다. 형식은 **증상 → 원인 → 조치 → 재발 방지/검증** 순서를 따른다.

### 5.1 매칭 엔진 메모리/스케일링

**① matching-engine 반복 OOMKilled — 미체결 주문 누적 (2026-08-19)**
- 증상: 부하시험을 반복할수록 매칭 엔진이 OOMKilled로 크래시루프에 빠짐.
- 원인: 부하시험 트래픽은 실제 양방향 시장처럼 자연스럽게 매수·매도가 교차하지 않아, 매칭되지 못한 미체결 주문이 인메모리 호가창에 무기한 쌓임(호가창은 TTL/크기 상한이 없음).
- 조치: 즉시 완화로 파드 메모리 한도를 1Gi→2Gi로 상향. 근본 대책으로 세션 종료 시 그 세션이 남긴 미체결 주문을 실제 CANCEL 이벤트로 자동 정리하는 기능 추가(상태 초기화가 아니라 정식 취소 이벤트를 발행해 기록 정합성을 유지하는 방식을 선택 — 상태를 그냥 지우면 `recorder`의 미체결 카운트가 영구히 틀어짐).
- 검증: 세션 4개 주문 접수 후 종료 → 4/4건 취소 발행 로그 확인, 잠시 후 전부 CANCELED로 반영됨을 확인. 다중 샤드(FR-19) 케이스도 별도 검증 — 그룹의 마지막 멤버가 해제될 때만 정리가 실행됨을 확인.

**② 세션 종료 정리의 스코프 누락 — 실제 186만 건 잔존 (2026-08-20)**
- 증상: ①의 자동 정리가 "동작 중"인데도 186만 건이 여전히 ACCEPTED/PARTIALLY_FILLED 상태로 남아 있음이 발견됨.
- 원인: 두 가지가 겹침 — (1) 자동 정리 기능 도입 이전에 쌓인 주문은 애초에 정리 대상이 된 적이 없었고, (2) CANCEL을 발행해도 `matching`이 아니라 **`recorder`**가 그 이벤트를 실제로 소비해야 DB 상태가 바뀌는데, `recorder`가 지연되거나 다운된 구간의 잔여물은 세션 범위 정리로는 절대 다시 훑이지 않음.
- 조치: 세션 종료 시 정리 범위를 "이번 세션 구간"에서 "현재 미체결인 모든 주문"으로 확대(세션 배타적 실행 보장 덕분에 안전 — 동시에 다른 런이 살아있을 수 없으므로 이 시점의 미체결 전량은 이번 런 아니면 과거 잔여물뿐임). 수동 관리자 트리거도 동기에서 비동기(202+폴링)로 변경 — 186만 건을 한 HTTP 요청 안에서 처리할 수 없기 때문.
- 검증: 단위 테스트로 비동기 동작(핸들러가 블로킹 전에 즉시 반환) 및 매칭 엔진 랙이 높을 때 정리를 보류하는 사전 점검 로직까지 확인. 실제 186만 건 백로그 대상 실행은 프로덕션 DB/Kafka 접근 권한이 있는 팀원 확인 대기 중.

**③ KEDA 스케일다운 후 재크래시 (2026-08-20, 2026-08-21)**
- 증상: 부하가 잦아들어 매칭 엔진이 1개로 축소된 뒤, 다음 버스트가 오면 그 1개 파드가 20개 마켓 물량을 혼자 받다가 스케일업 완료 전에 반복 OOMKilled.
- 원인: `minReplicaCount=1`이라 "혼자 다 받는 순간"이 구조적으로 발생. 크래시가 Kafka 컨슈머 그룹 리밸런스를 유발해 다른 파드들의 체결 발행까지 잠깐 실패하며 랙/백프레셔로 번짐. 이어서 랙이 0에 가까운 상태에서도 OOM이 재현됐는데, 컨슈머 랙 지표는 "아직 못 읽은 메시지 수"만 재서 "이미 다 읽었지만 상대가 없어 호가창에 쌓이기만 하는 미체결 주문"은 전혀 못 봤기 때문.
- 조치: `minReplicaCount`를 2로 올려 "혼자 다 받는 상황" 자체를 제거. KEDA `ScaledObject`에 컨슈머 랙과 별개로 호가창 크기(`matching_engine_book_size`) 트리거를 추가(둘 중 하나만 넘어도 스케일아웃, OR 조건).
- 검증: 코드/매니페스트 반영 완료. 임계값(500/20000)은 아직 실측 전 잠정값으로 다음 부하시험에서 조정 예정임을 명시.

### 5.2 데이터 정합성 / 기록기

**④ Kafka 메시지 소실 위험 — `ReadMessage`의 선(先) 커밋**
- 증상: 실제 실행 중 Kafka 토픽 메시지 수와 `SELECT count(*)` 결과가 2건 차이남(오류 로그는 전혀 없었음).
- 원인: `kafka-go`의 `ReadMessage`는 핸들러 실행 **전에** 오프셋을 커밋한다(라이브러리 소스로 확인) — DB 쓰기가 그 이후 실패해도 그 메시지는 영구히 유실됨.
- 조치: 세 리더(`orders`/`executions`/`assignments`) 모두 `FetchMessage`(자동 커밋 없음)로 교체하고, 핸들러 성공 후에만 명시적으로 `CommitMessages` 호출. 디코딩 자체가 실패한(영구히 재시도해도 소용없는) 메시지만 커밋하고 넘어가며, DB 쓰기 실패 등 일시적 오류는 커밋하지 않고 프로세스를 재시작시켜 마지막 성공 지점부터 재개하게 함.
- 검증: 실제 토픽 메시지 수와 DB 저장 건수 일치를 재확인.

**⑤ 대량 백로그 처리 중 MySQL 데드락 (2026-08-11)**
- 증상: 약 110만 건 백로그를 처리하던 중 기록기가 크래시 후 동일 지점에서 계속 재크래시(크래시루프).
- 원인: `orders` 리더와 `executions` 리더가 독립 트랜잭션으로 같은 `trade_order` 행을 동시에 갱신하며 실제 MySQL 데드락(에러 1213) 발생 — `SHOW ENGINE INNODB STATUS`로 `INSERT IGNORE`가 동시 `UPDATE`의 행 락을 기다리는 것을 직접 확인. 핸들러 실패 시 오프셋 미커밋+프로세스 재시작이라는 기존 설계가 오히려 같은 충돌을 반복 유발.
- 조치: 배치 함수 전체(트랜잭션 단위)를 감싸는 지수 백오프+지터 재시도(`withRetryOnDeadlock`) 추가, MySQL 에러 1213/1205만 재시도 대상으로 판별.
- 검증: 동일 백로그로 재실행 시 크래시루프 해소 확인. 다만 처리량 자체(특히 `execution` 삽입)는 여전히 느렸음을 정직하게 기록하고, 근본적인 락 경합 해소보다 워터마크를 보수적으로(5000/1000→2000/400) 낮추는 절충을 팀 결정으로 채택.

**⑥ 취소-체결 순서 역전으로 인한 상태 오염**
- 증상: 부분체결 후 취소된 주문이 뒤늦게 도착한 체결로 다시 미체결 취급되거나, 이미 전량체결된 주문에 대한 지연 취소가 상태를 덮어씀.
- 원인: `orders`(취소)와 `executions`(체결)를 완전히 독립된 두 컨슈머가 처리해 도착 순서가 실제 발생 순서와 다를 수 있음 — 이 자체는 드문 예외가 아니라 "부분체결 후 취소"가 정상적인 흐름이라 항상 발생 가능한 상황.
- 조치: 도착 순서가 아니라 **체결량 자체**를 진실의 기준으로 삼도록 SQL 로직 변경 — 이번 체결이 잔량을 0으로 만들면 기존 CANCELED 상태를 무조건 덮어써 FILLED로 교정하고, 그렇지 않으면 기존 CANCELED를 보존.
- 검증: 취소→지연 부분체결, 취소→지연 전량체결, 전량체결→지연 취소 세 시나리오 모두 실제 로컬 인프라로 재현해 기대한 최종 상태가 나옴을 확인.

**⑦ 매칭 엔진 스냅샷 완전 소실 시 전체 히스토리 재생 위험**
- 증상: 매칭 엔진이 한 번도 성공적으로 스냅샷을 저장하지 못한 채(비동기 큐가 계속 가득 차거나 파드가 SIGKILL로 즉시 종료) 크래시하면, 복구 로직이 오프셋 0부터 전체 히스토리를 재생 — 이미 처리한 체결을 다시 매칭해 `executions`에 중복 발행할 위험(NFR-09 위반) 및 성능 저하.
- 원인: `Recover()`의 기존 로직이 "스냅샷 없음 = 오프셋 0부터"로만 처리했음.
- 조치: 스냅샷보다 가벼운 워터마크(오프셋만 저장, 동기 저장)를 스냅샷 트리거와 같은 주기로 별도 기록. 전체 스냅샷이 없을 때 워터마크로 폴백 — 재생 범위를 "토픽 전체 역사"에서 "마지막 워터마크 이후"로 제한. 워터마크 조회 자체가 실패하는 경우는 애매하게 처리하지 않고 안전하게 오프셋 0으로 폴백(잘못 판단해 데이터를 놓치는 것보다 재생 비용을 감수하는 쪽을 택함).
- 검증: 단위 테스트로 워터마크 폴백/조회 실패 폴백/주기적 저장 세 경로 확인. 실제 크래시 시나리오는 아직 라이브 재현 전.

### 5.3 인증 / 네트워크

**⑧ Redis TLS 미설정으로 인한 절반만 동작하는 장애 (2026-08-11)**
- 증상: 실제 ElastiCache(TLS 필수) 대상 배포에서 매칭 엔진의 부하 추적·백프레셔는 정상 동작하는데 호가창 스냅샷 저장/복구만 실패.
- 원인: `matching/snapshotstore`가 `main.go`에서 이미 TLS/비밀번호로 올바르게 구성된 Redis 클라이언트를 재사용하지 않고, 주소 문자열만 받아 내부에서 **별도의 무인증 클라이언트**를 새로 만들고 있었음 — 로컬 무인증 Redis에서는 이 차이가 드러나지 않아 발견이 늦었음.
- 조치: `NewRedisStore`가 이미 구성된 클라이언트를 주입받도록 변경, `main.go`가 하나의 Redis 클라이언트를 만들어 스냅샷/부하추적/백프레셔 세 곳 모두에 공유하도록 리팩터링(구조적으로 이런 부류의 버그가 재발할 수 없게 함).
- 검증: 로컬 무인증 경로 재검증(회귀 없음 확인). 실제 TLS 환경 재검증은 인프라 접근 제약으로 대기 중.

### 5.4 인프라 / 배포

**⑨ 매칭 엔진 리밸런스 무한 루프 — 실제 MSK에서만 재현 (2026-08-12)**
- 증상: 실제 MSK 환경에서 매칭 엔진이 몇 초마다 컨슈머 그룹 제너레이션을 반복 갱신하며 전혀 진행하지 못함. 로컬 환경에서는 전혀 재현되지 않음.
- 원인: 물량 측정 로직이 20개 마켓을 순차적으로, 마켓마다 새 커넥션(`kafka.DialLeader`)으로 조회 — 실제 MSK의 IAM 인증(TLS+SigV4)은 매 dial마다 100~150ms가 들어 20개 순차 조회가 2~3초 걸림. 이 지연이 Kafka 코디네이터의 리밸런스 타임아웃과 충돌해 "멈춘 것"으로 판단되어 리밸런스가 재트리거되고, 재트리거된 리밸런스가 같은 지연을 다시 유발하는 악순환. 로컬 dev-kafka는 무인증+localhost라 이 비용 자체가 존재하지 않아 결함이 드러나지 않았음.
- 조치: 물량 측정을 마켓별 고루틴으로 병렬화.
- 검증: 실제 MSK 재배포 후 정상 동작 확인. `-race` 플래그는 이 환경에서 cgo 미지원으로 사용 불가해, 공유 가변 상태가 없는 동시성 구조임을 코드 리뷰로 확인.

**⑩ orderapi 파드 축출로 인한 순간 503 (2026-08-20)**
- 증상: `GET /v1/sessions/last-run`이 간헐적으로 503을 반환, 프론트엔드에 "세션 조회 실패" 노출.
- 원인: orderapi/매칭엔진/기록기 모두 평시 레플리카 1개이며, PodDisruptionBudget이 없어 Karpenter의 노드 통합(consolidation)이 그 유일한 파드를 "저활용"으로 판단해 자유롭게 축출 — 재스케줄(이미지 pull+시작+readiness) 30~40초 동안 ALB의 건강한 타겟이 0개가 됨.
- 조치: 세 Deployment에 `minAvailable: 1` PodDisruptionBudget 적용 — 자발적 축출(voluntary disruption)만 방지하며 노드 하드웨어 장애 같은 불가피한 경우는 여전히 막지 못함을 명시.
- 검증: 매니페스트 반영 완료.

**⑪ CI/CD 변경 감지 오탐 — 무관한 배포가 랙 급증 유발 (2026-08-20)**
- 증상: 대시보드 JSON 파일 하나만 수정한 push에도 `recorder`가 재배포되며, 100배속 부하시험 도중 랙이 급증.
- 원인: 변경 감지(`dorny/paths-filter`)의 diff 기준(base)이 명시돼 있지 않아 기본값(main과 prod의 merge-base) 사용 — 이 저장소의 `main`이 오래 방치돼 그 merge-base가 한참 과거였고, 그날 한 번이라도 `recorder`를 건드리면 그 이후 무관한 모든 push가 계속 "바뀜"으로 잡힘.
- 조치: diff 기준을 push 이벤트의 직전 커밋(`github.event.before`)으로 명시.
- 검증: 이후 무관한 변경에서 불필요한 재배포가 사라짐을 확인.

**⑫ CloudFront 라우팅 누락 — 기록기 조회 API가 정적 파일로 처리됨 (2026-08-13)**
- 증상: 기록기 조회 API(`/recorder-api/*`) 호출이 실패.
- 원인: CloudFront에 `/recorder-api/*` 전용 캐시 동작(behavior)이 없어 기본 동작(S3 정적 파일 서빙)으로 떨어져 정적 파일을 찾으려다 실패. 같은 시기에 ALB 보안그룹 인그레스도 8081(orderapi) 포트만 열려 있어 기록기의 8082 포트가 `Target.Timeout`으로 unhealthy였음.
- 조치: `/recorder-api/*` 전용 `ordered_cache_behavior` 추가(오리진 요청 정책 AllViewer, 캐시 비활성화), 보안그룹에 8082 인그레스 규칙 추가.
- 검증: 실제 배포 후 두 경로 모두 정상 응답 확인.

**⑬ GitHub OIDC `sub` 클레임 포맷 변경으로 CI/CD 전면 실패 (2026-08-18)**
- 증상: 어느 순간부터 CI/CD 파이프라인의 AWS 역할 assume이 전부 실패.
- 원인: GitHub가 OIDC 토큰의 `sub` 클레임 포맷을 owner/repo 각각에 불변 숫자 ID를 붙이는 방식으로 변경 — 최초 대응 시 repo ID만 추가하고 owner ID를 빠뜨림.
- 조치: 실제 실행에서 발급되는 OIDC 토큰을 디코딩하는 디버그 잡을 임시로 추가해 정확한 `sub` 값을 확인, 트러스트 정책에 올바른 값 반영. 만약을 대비해 예전 포맷도 함께 남겨둠.
- 검증: 디버그 잡으로 실제 토큰 클레임을 직접 확인하고 배포 재개.

**⑭ EKS 전체 재구축 리허설 중 발견된 순환 의존 (2026-08-24, 2026-08-25)**
- 증상: EKS 클러스터를 완전히 지웠다가 처음부터 다시 올리는 리허설 중 `terraform plan`/`apply` 자체가 진행되지 않음.
- 원인: (1) 아직 존재하지 않는 ALB를 태그로 찾는 데이터 소스가 결과 없음으로 즉시 에러 처리됨. (2) 모니터링 알람의 `for_each`가 apply 전에는 알 수 없는 값(`member_clusters`)에 의존해 계산 자체가 불가능.
- 조치: (1) 항상 성공하며 "찾음/못 찾음"만 알려주는 `data.external` + 리소스 개수(`count`) 조건부 생성으로 교체. (2) `for_each` 키를 apply 전에도 이미 알고 있는 설정값(`replication_group_id`/`num_cache_clusters`)으로 변경.
- 검증: 로컬 `terraform plan`으로 from-scratch 상태에서도 별도 재시도(`-target`) 없이 plan/apply가 끝까지 진행됨을 확인.

## 6. 자동 복구 메커니즘 vs 수동 개입이 필요한 상황

| 메커니즘 | 트리거 조건 | 자동/수동 | 관련 사고 |
|---|---|---|---|
| 세션 가드 Redis 키 TTL(30초) 자기치유 | 트레이더/리플레이 엔진 프로세스가 크래시하거나 SIGKILL됨 | 자동 | §5.3 미해결(신뢰 근거) |
| 백프레셔 플래그 TTL 자기치유 | 기록기/매칭 엔진 컨슈머 랙이 임계치 아래로 회복 | 자동 | §3 NFR-13 검증 |
| KEDA 스케일아웃/다운 | 컨슈머 랙 또는 호가창 크기가 임계치 초과/회복 | 자동 | §5.1 ③ |
| PodDisruptionBudget | Karpenter 등 자발적 파드 축출 시도 | 자동(단, 노드 하드웨어 장애 등 불가피한 축출은 방지 못함) | §5.4 ⑩ |
| 세션 종료 시 미체결 주문 자동 취소 | 트레이더/리플레이 엔진 세션 종료(정상/오류/중단 모두) | 자동 | §5.1 ①② |
| MySQL 데드락 재시도 | 배치 트랜잭션이 에러 1213/1205로 실패 | 자동(지수 백오프) | §5.2 ⑤ |
| 매칭 엔진 워터마크 폴백 복구 | 전체 스냅샷이 없는 상태로 크래시 | 자동(단, 호가창 상태 자체는 복구 안 됨 — 재생 범위만 제한) | §5.2 ⑦ |
| 186만 건 규모 잔존 주문 정리 | 운영자가 관리자 API를 수동 호출 | **수동** | §5.1 ② |
| 매칭 엔진 랙 중 대량 취소 발행 차단 | 자동 정리 시점에 매칭 엔진이 이미 랙 상태 | 자동 스킵 + 실행 결과 화면에 안내 메시지 기록(수동 확인 유도) | §5.1 ② |

## 7. 알려진 한계 / 후속 확인 필요 사항
- FR-19 스케일 테스트는 로컬 단일 머신 한계로 인해 실제 수평 확장 효과를 검증하지 못했다(4절) — 실제 다중 인스턴스 AWS 배포에서 재측정이 필요하다.
- §5.1 ②(186만 건 정리)와 §5.3 ⑧(Redis TLS)은 코드 수정과 로컬 회귀 검증까지는 끝났지만, 실제 프로덕션 규모/실제 TLS 환경 재검증은 접근 권한 제약으로 아직 완료되지 않았다.
- §5.2 ⑦(워터마크 폴백)은 단위 테스트로만 확인됐고, 실제 크래시 상황 재현 검증은 아직 하지 않았다.
- 이 문서에 정리된 사고는 실제 발생 순서·근거가 있는 것만 담았으며, 아직 발생하지 않았거나 재현되지 않은 잠재적 실패 시나리오(예: 완전한 AZ 장애, MSK 클러스터 자체 장애)에 대한 대응은 별도로 설계되어 있지 않다.
