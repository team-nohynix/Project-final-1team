# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is an **infrastructure load-testing project**, not a production trading system. The end goal: collect real historical market data from Upbit, feed it to a "trader" application that replays it as massive simulated trading traffic against an order-acceptance API + matching engine, and use that traffic to load-test the backend + infra. Seven independent Go modules live in this repo so far: `backend/` (market data collection + serving), `trader/` (data-replay + bot engine, produces FR-17 order-record files), `orderapi/` (order acceptance, role "A" — see below), `matching/` (order matching engine, role "B" — runs as any number of instances sharing a Kafka consumer group, FR-11 market rebalancing, see below), `replayengine/` (FR-18/19 replay engine — replays `trader`'s recorded order files with no judgment logic, see below), `recorder/` ("기록기" — consumes `orders`/`executions` and persists trade/execution history to RDS MySQL + S3, see below), and `frontend/` (a separate Vue/Vite app, see its own `frontend/README.md`, not yet wired to anything backend-side).

Per `requirements.md` 1.2.4, **role A (order acceptance) and role B (matching engine) are architecturally separate applications that only ever communicate via Kafka** (A publishes to the `orders` topic, B consumes it and publishes to `executions`) — never direct calls. `orderapi/` is role A, `matching/` is role B; neither imports the other, and both re-declare their own copies of small shared tables (20-market list, tick-size tiers) rather than sharing Go types across module boundaries.

`backend/` is the service that collects cryptocurrency market data from the Upbit exchange (REST + websocket APIs). Kafka wiring for this data was considered (a `backend/kafka/producer.go` wrapper existed early on) but **decided against and since removed** — see "Data flow" below for why. `backend/go.mod` no longer depends on `segmentio/kafka-go` as a result.

`.env`/`godotenv`-based config loading (`backend/config`) is active — `config.Load()` is called from `main.go` and reads `APP_ENV`, `S3_BUCKET`, `PORT`.

### Tests

All six modules have `_test.go` files now (table-driven, stdlib `testing` only — no external test/mock libraries). Convention: tests live beside the code they cover, same package (white-box, so unexported helpers like `order.tickTier` are reachable), `TestXxx` names, `t.Run` subtests for table cases. `go test` (and everything else that isn't `go build`/`go run`) automatically excludes `_test.go` files from the compiled binary — that's a Go toolchain guarantee based on the filename suffix, not something this project configures.

What's covered and why: pure/deterministic logic that's easy to get subtly wrong — `order.RoundToTick` (tick-size table + rounding), `bot.MarketState`'s circular buffer (wraparound indexing), `MarketMakerBot.Decide`, `dataset.BuildBatch`/`BuildStream` (Upbit field → normalized field mapping, event merge+sort), `dataset.localStorage` save/load round-trip, and `backend`'s `manifestHandler`/`fileHandler` (via an in-memory fake `dataset.Storage` in `server_test.go`, and — since `fileHandler`'s `r.PathValue()` only populates when matched through a real `http.ServeMux`, not on a bare handler call — a small mux built in the test with the same route pattern as `main.go`). `backend/collectjob_test.go` (added 2026-08-12, alongside the async `POST /v1/collect` redesign) covers the full accept→poll→complete flow by injecting a channel-gated fake in place of `collectAllMarkets` — the fake blocks until the test explicitly unblocks it, so the test can assert `IN_PROGRESS` deterministically before completing, with no reliance on goroutine-scheduling timing. `orderapi` follows the same handler-test pattern: `server_test.go`'s `fakePublisher` (implements `kafkaclient.Publisher`) stands in for Kafka, so `acceptOrderHandler`/`cancelOrderHandler` are tested (missing key, invalid market, success, idempotent retry doesn't re-publish, publish failure isn't cached so a retry can succeed, cancel-not-found, cancel-then-idempotent-no-op, cancel-already-filled) without a real broker; `validate/validate_test.go`, `idempotency/idempotency_test.go`, `order/order_test.go` cover the pure logic pieces in their own packages the same way `backend`/`trader` do. `matching` follows the same pure-logic-first pattern: `orderbook/orderbook_test.go` covers FR-06's matching scenarios (exact match, partial fill both directions, multi-level crossing, FIFO at one price level, price-gap no-match, cancel, price-string normalization, and a determinism check that replaying the same event log twice yields byte-identical book state — see Architecture below for why that matters) entirely in-memory, no Kafka/Redis; `engine/engine_test.go` covers the Kafka/Redis-facing orchestration (`Apply`, `Recover`, snapshot triggering) against fake `ExecutionPublisher`/`SnapshotStore` implementations, same style as `orderapi`'s `fakePublisher`. `kafkaclient` and `snapshotstore` (the real Kafka/Redis implementations) aren't unit-tested — same rationale as `dataset.s3Storage`/`backend/upbit` below — verified by hand instead (see the end-to-end run described in Architecture). `replayengine` mirrors `trader`'s own test split: `orderstore/local_test.go` is a save/load round-trip against a temp dir (mirrors `backend/dataset/local_storage_test.go`), `submitter_test.go` mirrors `trader/order/http_submitter_test.go` exactly (`httptest.Server`, 202/non-202, fresh-Idempotency-Key-per-call), `replay_test.go` covers `filterRange` (FR-27) and `replayMarket`'s ordering/context-cancellation with a fake `Submitter`. `recorder` follows the same pure-logic-first pattern as `matching`/`orderapi`: `events/decode_test.go` covers `orderEvent`/`executionMessage` JSON decoding (malformed input, unknown event type, CANCEL's mostly-empty shape); `store/apply_test.go` covers the orchestration in `apply.go` (`ApplyOrderEvent`/`ApplyExecutionEvent`/`ResolveMode`) against a fake `Store`, including the mode-mismatch and missing-order fallback paths (see Architecture below); `archive/batch_test.go` covers `Batcher`'s count-trigger/manual-flush/empty-flush-is-noop/buffer-reset behavior against a fake `archive.Store`. `server_test.go` (added 2026-08-12, alongside `query/`'s read-only HTTP API) covers `traceHandler`/`enginesHandler` against a fake `query.Querier`, same pattern as `orderapi`'s `fakePublisher`. `store/mysql.go`, `query/query.go`'s `MySQLQuerier`, `archive/local.go`/`s3.go`, and `kafka/*_reader.go` (the real MySQL/disk/S3/Kafka-touching code) aren't unit-tested — same rationale as `matching/kafkaclient`/`snapshotstore` below — verified by hand instead (see the end-to-end run described in Architecture, and the real bugs it caught that no unit test could have).

What's deliberately **not** covered, and why: anything whose real work is a live network/AWS call — `backend/upbit` (real Upbit REST calls), `dataset.s3Storage` (real S3), `collectMarket`/`collectAllMarkets`/`ensureMarketCollected` (wrap `upbit` calls, no injectable fetcher to substitute — would need a refactor to test meaningfully), `client.Fetch*`'s success path against a real backend. These stay verified by hand (spin up `go run .`, hit it with `curl`/`Invoke-RestMethod`/a real `trader` run) the same way they were before tests existed — see the git history in this repo for examples of that workflow (e.g. the concurrent batch+stream request that proved `ensureMarketCollected`'s dedup works). `bot.RealBedrockClient`/`NewBedrockClient` (the real Bedrock SDK call, added 2026-08-10) aren't tested either, same reasoning — the surrounding pure logic (`buildSnapshot`/`parseDecisions`) and the bots' own `Decide` (against a fake `BedrockClient`) are, see the `ai_bot.go`/`bedrock.go` bullets below.

### Local Kafka for development

```
cd infra/dev-kafka
docker compose up -d
```

Brings up a single-node KRaft-mode Kafka broker (`apache/kafka:3.7.0`) on `localhost:9092`, auto-creating topics (`KAFKA_AUTO_CREATE_TOPICS_ENABLE=true`). `orderapi/.env` and `matching/.env` hold `KAFKA_BROKER` for connecting to it (gitignored — copy/create locally, they're not committed) — `orderapi` publishes to `orders`, `matching` consumes `orders` and publishes to `executions` (`backend` never used Kafka in practice, and its unused `kafka/producer.go` wrapper has since been deleted — see "Data flow" below).

**`orders` needs exactly 20 partitions (one per market) for FR-11 to work** — auto-creation uses the broker's default partition count (1 on this dev broker), which is wrong for `matching`'s market-rebalancing design (see "Matching engine (role B)" under Architecture below): it needs a true 1-market=1-partition bijection, not "however many partitions auto-create happened to pick." Create it explicitly before starting `orderapi`/`matching` against a fresh broker: `kafka-topics.sh --create --topic orders --partitions 20 --replication-factor 1`. If it already exists with the wrong partition count, delete and recreate it (`--delete` then `--create`) — changing partition count on an existing topic changes what its offsets mean, so this is delete-and-recreate, not resize, and only safe when the existing data is disposable (true for local dev, not for a real deployment, which should just be created at 20 from the start).

**Client-side gotcha**: the broker allowing auto-created topics is not sufficient by itself — `segmentio/kafka-go`'s `kafka.Writer.AllowAutoTopicCreation` defaults to `false`, so a client that doesn't explicitly set it to `true` gets `[3] Unknown Topic Or Partition` against a brand-new topic even though the broker would happily create it. `orderapi/kafkaclient.go` and `matching/kafkaclient/producer.go` both set it explicitly (see Architecture below). Also note topic creation is asynchronous on the broker: the very first publish to a never-seen topic can still fail once even with the flag set — a retry (same or a different request) succeeds; this was actually observed live when `matching`'s `executions` topic was created for the first time (a burst of `Unknown Topic Or Partition` errors while replaying a backlog, self-resolving once the topic finished creating). This is part of why `orderapi`'s idempotency store never caches 5xx responses (see `orderapi/idempotency.go` below): it's what lets that retry actually work.

### Local Redis for development

```
cd infra/dev-redis
docker compose up -d
```

Single-node `redis:7-alpine` on `localhost:6379`, no auth/persistence config — purely a local stand-in for the ElastiCache Redis the design docs call for. `orderapi/.env` and `matching/.env` hold `REDIS_ADDR`. This is the **first real use of Redis anywhere in this codebase** — `matching` writes orderbook snapshots to it (`GET /v1/markets/{market}/orderbook`'s backing store) and `orderapi`'s new orderbook-query handler reads them back. See "Matching engine (role B)" under Architecture for the full design.

**Inspecting messages from Git Bash on Windows**: `docker exec dev-kafka-... /opt/kafka/bin/kafka-console-consumer.sh ...` gets its Linux path mangled by Git Bash's MSYS path conversion (`/opt/kafka/...` becomes a Windows path). Prefix with `MSYS_NO_PATHCONV=1` to stop that.

### Local MySQL for development

```
cd infra/dev-mysql
docker compose up -d
```

Single-node `mysql:8` on `localhost:3306`, no persistence config — same dead-simple style as `dev-kafka`/`dev-redis`, purely a local stand-in for the RDS MySQL the team decided to use (team decision 2026-08-07 — an earlier draft used PostgreSQL, migrated once `recorder` was already built; see Architecture below for what that migration actually touched). Schema isn't applied automatically: `cat recorder/schema.sql | docker exec -i dev-mysql-mysql-1 mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"` once per fresh container. See "Recorder (기록기)" under Architecture for the full design.

## Architecture

- **`backend/main.go`** — entrypoint. Starts an HTTP server (`net/http`, stdlib `ServeMux`, no router dependency) on `cfg.Port` (env `PORT`, default `8080`). Routes: `POST /v1/collect`, `GET /v1/collect/{jobId}`, `GET /v1/markets/data`, `GET /v1/markets/{market}/{kind}`. Does not currently call Kafka.
- **`backend/server.go`** — `collectHandler`: parses `{"date": "YYYY-MM-DD"}` from the request body, computes the KST `[date 00:00, date+1 00:00)` window. **Asynchronous since 2026-08-12** (previously called `collectAllMarkets` synchronously and returned 200 with the full per-market results once all 20 markets finished): now creates a `collectJob` (`collectjob.go`), spawns `collectAllMarkets` in a background goroutine, and returns 202 immediately with the job's `{jobId, date, range, status: "IN_PROGRESS"}` — no `results` yet. `GET /v1/collect/{jobId}` (`collectStatusHandler`) polls that job; once the goroutine finishes, `collectJobStore.complete` fills in `results` (same per-market shape as the old synchronous response — a market-level failure still shows up as that market's `status: "error"` rather than failing the whole job) and flips `status` to `"COMPLETED"`. 404 if the `jobId` is unknown. **Why**: a teammate reproduced a real 504 in the actual deployed environment — a full day's 20-market collection took 193s against Upbit's rate limits, and CloudFront's origin-response wait limit (180s, not configurable) can't be raised to cover it, so no synchronous-response redesign of the *backend* alone could fix this; the response pattern itself had to change. `collectHandler`'s `collect` parameter is injected (production wiring in `main.go` passes `collectAllMarkets`) specifically so `collectjob_test.go` can verify the full accept→poll→complete flow with a channel-gated fake instead of hitting real Upbit — deterministic (blocks on a channel the test controls, no reliance on goroutine scheduling timing), unlike `collectAllMarkets`/`collectMarket` themselves which still have no injectable fetcher (unchanged limitation, see Tests section below). **Frontend not yet updated to match** — `AITraderView.vue`'s collection call still expects the old synchronous 200-with-results shape; see `docs/frontend-backend-integration.md` §2.4/4.5 for the exact request/response shapes it needs to poll against instead. Verified live: a real `POST /v1/collect` returned its 202 in ~0.4s (vs. the old design's multi-minute wait), and polling `GET /v1/collect/{jobId}` correctly showed `IN_PROGRESS` then `COMPLETED` with populated `results`. Also `manifestHandler`: validates the `date` query param and returns `batchUrl`/`streamUrl` for all 20 `upbit.TargetMarkets` — purely mechanical URL generation, does **not** touch `dataset.Storage` or check whether the files actually exist (see Data flow below for why that's deliberate). Also `fileHandler` (`{kind}` is `batch` or `stream`): tries `dataset.Storage.LoadBatch`/`LoadStream` first; on `dataset.ErrNotFound` calls `ensureMarketCollected` (see `collector.go`) to collect just that one market on demand, then reads and serves it. 400 on bad `kind`/`date`, 404 on a market outside `upbit.TargetMarkets`, 500 on collection/read failure. (This on-demand single-market path is unaffected by the `POST /v1/collect` change above — it was already synchronous-but-fast, one market at a time, not the 20-market bulk path that hit the CloudFront timeout.)
- **`backend/collector.go`** — `collectAllMarkets` loops over `upbit.TargetMarkets`, calling `collectMarket` per market (fetches ticks + every candle granularity from `upbit`, builds batch/stream via `dataset.BuildBatch`/`BuildStream`, saves via the injected `dataset.Storage`). One market's error doesn't stop the others. Also `ensureMarketCollected`: wraps `collectMarket` in a `golang.org/x/sync/singleflight.Group` keyed on `market+start` so concurrent requests for the same market+date (e.g. `fileHandler` serving batch and stream at nearly the same time) collapse into a single `collectMarket` call instead of running it twice.
- **`backend/upbit/candles.go`** — REST client for Upbit's `/v1/candles/*` endpoints. `FetchCandlesInRange` paginates backwards in time (via the `to` cursor) to collect all candles in `[start, end)` for fine-grained units (seconds/minutes); `FetchRecentCandles` fetches the last N candles for coarse units (days/weeks/months) where a single page suffices. Both respect Upbit's ~10 req/sec rate limit with a 110ms sleep between paginated calls.
- **`backend/upbit/ticks.go`** — REST client for `/v1/trades/ticks` (individual trade executions). Also paginates backwards using the `cursor` (last page's `sequential_id`). Upbit only allows querying trade ticks for the last 7 days; `FetchTradeTicksForDate` enforces that and errors otherwise.
- **`backend/upbit/websocket.go`** — legacy real-time ticker client over Upbit's websocket API (`ConnectAndListen`), explicitly marked as legacy in a source comment. Not called from `main.go` currently; streams ticker updates onto a channel for a caller to consume.
- **`trader/`** — separate Go module (`module trader`, own `go.mod`), the data-replay + bot engine described in `docs/market-data-api.md`. Split into role-based sub-packages (import path `trader/<pkg>`) with a layered, cycle-free dependency graph: `client` and `bot` are leaves; `order` depends on `bot` (needs `bot.Decision`); `orderstore` depends on `order` (needs `order.RecordedOrder`); `replay` depends on `client`+`bot`+`order`; `main.go` (package `main`, module root) wires everything together, including `orderstore`. No package is named the same as a variable that holds one of its own values in scope (e.g. `main.go` binds the shared `*http.Client` to `httpClient`, not `client`) — that would shadow the package import within that scope.
  - **`trader/client/`** (`client.go`, `types.go`) — talks to the backend (and, via the same shared client, to `orderapi`). `NewHTTPClient` (5-minute timeout, to tolerate on-demand collection latency on a cache miss — see `backend`'s `ensureMarketCollected`), `FetchManifest`/`FetchBatch`/`FetchStream`. `types.go` re-declares the JSON shapes backend returns (`Manifest`, `BatchFile`, `StreamFile`, ...) rather than importing `backend/dataset` — the two modules are meant to only ever talk over HTTP+JSON, never share Go types at compile time.
    - **`MaxIdleConnsPerHost` bug, found via a real end-to-end run**: `NewHTTPClient`'s `Transport` explicitly sets `MaxIdleConnsPerHost: 100`/`MaxIdleConns: 200` (cloned from `http.DefaultTransport`, whose default is `MaxIdleConnsPerHost: 2`). Discovered by actually running `trader` at `-speed=100` against local `backend`+`orderapi`: with up to 62 goroutines (60 per-market bots + 2 global bots) sharing one client, the default pool size meant connections were constantly closed and reopened instead of reused, which exhausted Windows' outbound ephemeral port range within seconds (`connectex: Only one usage of each socket address`) — every order submission failed *client-side* after the first ~10, never even reaching `orderapi`. Fixed by sizing the idle-connection pool to comfortably cover the max concurrent goroutine count; re-verified afterward (see below) that a real run produces zero connection errors and orders land in Kafka continuously.
  - **`trader/bot/`** (`bot.go`, `marketmaker.go`, `noise.go`, `largeorder.go`, `ai_bot.go`) — judgment logic only (FR-16), no knowledge of HTTP or order wire format. `MarketState` (`bot.go`) is not just a single latest price — a fixed-size circular buffer (`PriceHistorySize`, currently 30) of recent prices behind a `sync.RWMutex`. `Price()` returns the most recent entry (fast path for the per-market algorithmic bots); `History()` returns the buffer oldest→newest (for the AI bots, which need a price *series* to reason about momentum/mean-reversion, not just a point value).
    - **Per-market bots (`Bot` interface)**: **`MarketMakerBot`/`NoiseBot`/`LargeOrderBot`** — plain rule-based algorithms, meant to run as one independent instance *per market* (60 total across 20 markets — see `replay.marketBots()`), each reading that market's own `MarketState`. Per-market is deliberate here: a market maker has to quote against one specific order book, it can't function "portfolio-wide".
    - **Global bots (`GlobalBot` interface, `ai_bot.go`)**: **`MomentumAIBot`/`MeanReversionAIBot`** are **not** per-market — decided deliberately, both for cost (2 Bedrock calls per judgment cycle instead of 40) and because "AI trader scanning the whole board and picking where to act" fits the concept better than 20 independent copies. `GlobalBot.Decide(ctx context.Context, states map[string]*MarketState) []GlobalDecision` receives *every* market's `MarketState` in one call and can return decisions tagged with whichever markets it wants to act on (`ctx` added 2026-08-10 alongside the real Bedrock wiring below — needed for the call's timeout/cancellation, unlike `Bot.Decide`'s pure per-market computation which never needed one).
    - **Real Bedrock wiring (2026-08-10, `bedrock.go`)**: both bots delegate to a shared `BedrockClient` interface (`Invoke(ctx, systemPrompt, states) ([]GlobalDecision, error)`) — same call shape, different `systemPrompt` (each bot's strategy description as plain-language instructions). `MomentumAIBot{Client}`/`MeanReversionAIBot{Client}` just forward to `Client.Invoke` and, on error, log and return `nil` — a Bedrock outage/misconfiguration (e.g. a local dev environment with no model access set up) costs that bot one judgment cycle's worth of decisions, nothing else; the rest of `trader` (market replay, the rule-based per-market bots, the other AI bot) is fully isolated, same "one failure doesn't stop the others" principle used everywhere else in this module.
      - **Structured input, not raw-history-to-summary-stats**: `buildSnapshot(states)` sends each market's `MarketState.History()` output as-is (oldest→newest, per-market JSON array) rather than pre-computing summary stats (% change, min/max, etc.) — `History()`'s circular buffer already exists specifically to give the trend-sensitive bots a *series*, not a point value (see `bot.go`'s own doc comment), and collapsing it to a few derived numbers before the model ever sees it would throw away exactly the shape information momentum/mean-reversion judgment needs. At `PriceHistorySize` (30) × ~20 markets, the raw series is well within a cheap model's comfortable context size, so there was no real token-cost reason to compress it either.
      - **Structured output via tool-use, not prompted free text**: `Invoke` forces the model's response through Bedrock's Converse API tool-use mechanism (`ToolChoice` pinned to a single `submit_trade_decisions` tool with a fixed JSON schema matching `GlobalDecision`), rather than asking for JSON in the prompt and parsing free text — deliberately, since a cheap model is more likely to wrap its answer in prose/markdown fences that break naive parsing, and tool-use puts that structure requirement at the API level instead. `parseDecisions` (pure, unit-tested) then validates each returned item (`market` non-empty, `side` is `BUY`/`SELL`, `price`/`quantity` > 0) and **skips only the invalid ones**, not the whole batch — a model occasionally returning one malformed entry among several good ones shouldn't cost the good ones too (same per-item-isolation principle as everywhere else in this repo).
      - **Test split**: `buildSnapshot`/`parseDecisions` (pure) and `MomentumAIBot.Decide`/`MeanReversionAIBot.Decide` (tested against a fake `BedrockClient`) are unit-tested; `RealBedrockClient`/`NewBedrockClient` (the actual SDK call) are **not** — same rationale as `backend/upbit`/`matching/kafkaclient`: real network/credential round-trip, verified by hand once real Bedrock model access exists. **Not yet hand-verified in this session** — written and reviewed against the AWS SDK v2 `bedrockruntime` package's actual types (confirmed by reading the installed module source, not just guessed from memory), but real Bedrock model access wasn't available to test against; needs a real end-to-end run once the team's infra side (model access enabled, credentials/IAM in place) is ready.

### Concurrent execution guard (세션 API, FR 없음 — 팀 결정 2026-08-06)

Team decision: **two or more `trader`/`replayengine` processes must never run at the same time** (two traders, or a trader and a replay engine) — nothing in `matching`'s orderbook or Kafka partitioning distinguishes which run an order came from, so concurrent runs would silently mix their orders into the same live orderbook.

**Real conflict with FR-19, found 2026-08-07, fixed same day**: `requirements.md`'s FR-19 requires distributing replay across *multiple concurrent* `replayengine` processes (one per shard) when a single instance can't generate enough load. But the original `RedisStore.Claim(ctx, owner)` did a `SETNX` on a single well-known key regardless of the `owner` argument — so shard 0's `Claim` succeeding meant shard 1's `Claim` unconditionally got a 409 (`ErrAlreadyActive`) and refused to start. FR-19's "run N replayengine instances at once" scenario was structurally impossible. See `docs/erd.md`'s changelog for the discovery writeup.

**Team decisions (2026-08-07) on the fix and the scale-out approach**:
- **Introduce an explicit `runId` — the guard's unit of exclusivity moves from "one process" to "one group of processes that share a runId."** Chosen over the simpler alternative (only shard 0 does the real `Claim`/`Heartbeat`/`Release`, other shards skip the guard entirely) because that alternative is silently unsafe: if shard 0 crashes before the others start, or someone runs a single shard standalone for debugging, the guard would be fully bypassed with no signal that anything was wrong.
- **Scale testing starts at 2 instances, then 4, then ~7, watching for where the real bottleneck shows up** (`replayengine` itself vs. `orderapi`/Kafka/`matching`) rather than committing upfront to a fixed target count. Back-of-envelope: one instance measured ~1,450 orders/sec aggregate at `-speed=500` (see `replayengine/`'s "Verified end-to-end" note below); NFR-01's target is 10,000/sec, so ~7 instances would close that gap by roughly linear extrapolation — well under the ~20-instance ceiling the current one-goroutine-per-market sharding scheme imposes (more than 20 shards means some get zero markets, since `i % shardCount == shardIndex` over a 20-element list).
  - **Actually run 2026-08-11 (single-machine only — real result, but doesn't answer the question this test was meant to answer)**: replayed one real day's worth of `trader`-recorded orders (279,936 orders, 20 markets) at `-speed=500` against a single local `orderapi`+`matching`+Kafka+Redis stack, at 1/2/4/7 instances. Result: **throughput did not scale with instance count** — 1,379 → 1,124 → 1,133 → 1,333 orders/sec (roughly flat, if anything slightly worse at 2–4 than at 1), zero submission failures at every instance count. Checked `matching`'s own backpressure log for the test window: it never once tripped (lag stayed near zero) — so `matching` had spare capacity the whole time, ruling it out as the bottleneck here. This means the flat throughput is being capped by something else entirely local to this test rig — most likely `orderapi` (still a single process throughout) or the fact that every `replayengine` instance, `orderapi`, `matching`, and both Docker containers were all competing for the same machine's CPU/network, not by any of `replayengine`'s own sharding logic (which worked correctly — session-guard `runId` grouping, per-shard market split, and total order count all came out exactly right at every instance count). **This local result cannot answer the real question** ("does horizontally scaling `replayengine` actually raise throughput toward NFR-01's 10,000/sec target") — that requires `orderapi`/`matching`/Kafka to actually have independent, unshared capacity to absorb more concurrent load, which only a real multi-instance AWS deployment can provide. Treat this run as confirmation that the *sharding mechanism itself* is correct, not as a capacity number.
- **No `matching`-style FR-11 dynamic rebalancing for `replayengine` — decided against, not just deferred.** `replayengine` runs as a one-shot K8s `Job` per `-date` (unlike `matching`'s always-on service), so `-shard-count`/`-shard-index` only ever need to be decided once, at launch — there's no "instance joins/leaves mid-run" scenario to rebalance around the way `matching`'s FR-11 has. This is the same "no coordination needed" property already documented under `replayengine/main.go` below, just now explicitly confirmed as a reason *not* to build FR-11-style machinery here, rather than an oversight.

**Design, chosen over per-order enforcement for performance**: enforcement happens **once, at process startup** (`trader`/`replayengine` call `POST /v1/sessions` before doing any real work) — not on every `POST /v1/orders`. A per-order check would add a Redis round-trip to NFR-01's 10,000 orders/sec hot path and make Redis a hard dependency for order acceptance, where today it isn't (accepting an order touches only the in-memory idempotency store and Kafka). Gating only at session-start costs one Redis operation per whole run, not per order — no throughput impact. This also means `POST /v1/orders` itself is completely unaware of sessions and unchanged; the guard only stops a *second run from starting*, not a caller bypassing the session API directly (out of scope — `orderapi` isn't a public-facing API, only `trader`/`replayengine` call it in practice).

- **`orderapi/session/session.go`, group model (implemented 2026-08-07)**: `Claim(ctx, owner, runID)` — if `runID` is empty (e.g. `trader`, which never shards), the server generates one and the call behaves exactly like the old single-process design (a "group of one"). If `runID` is non-empty and multiple callers present the *same* one (`replayengine` shards, via a new `-run-id` CLI flag that the launcher assigns identically to every shard of one logical run), they all join the same group instead of conflicting; a *different* `runID`/owner while a group is active still gets 409, preserving the original exclusivity guarantee. Redis keys: `orderapi:session:active` holds the active group's `runID` (this key alone is what makes exclusivity correct, as before); `orderapi:session:members:{runID}` is a Set of member IDs, TTL-refreshed alongside `active` on every heartbeat — a group stays alive as long as *any* member is still heartbeating, not tied to one specific member. `orderapi:session:meta` is unchanged (best-effort `{owner, claimedAt}` for conflict messages). The opaque `sessionId` returned to callers is `"{runID}{sep}{memberID}"` — a composite that lets `Heartbeat`/`Release` recover which group a given call belongs to without a second lookup.
  - **`claimScript` (new Lua script)**: atomically handles all three claim outcomes — no active group → create one; active group's `runID` matches mine → join (refresh TTL); otherwise → conflict. Combining "check" and "act" in one script (same principle `heartbeatScript`/`releaseScript` already used) avoids a TOCTOU race between a plain `GET` and a follow-up `SETNX`/`EXPIRE` (e.g. two claims racing right as a group's TTL expires).
  - **`releaseScript` (rewritten)**: removes just the calling member from the group's Set; only clears the group's `active`/`meta`/`members` keys if that removal left the Set empty (i.e. this was the *last* member) — a non-last release leaves the group fully intact for the remaining members. This preserves the pre-existing "clean release frees the lock immediately, no need to wait out the TTL" UX for the common single-member case, while correctly not tearing down a multi-member group out from under still-running shards.
  - **Known accepted limitation**: a member that crashes (never calls `Release`) stays a phantom entry in the group's Set forever — it's never proactively pruned. This doesn't threaten correctness (the group's `active`/`members` keys still expire via TTL once nobody heartbeats them, same self-healing guarantee as before), it just means a group that had a partial crash won't get the "instant free-up on last clean release" optimization — the last surviving member's clean `Release` will see a non-empty Set (the crashed phantom) and leave the group's keys to expire via TTL (≤30s) instead of deleting them immediately. Accepted as consistent with this system's existing "TTL is the correctness backstop, immediate release is just a nice-to-have" philosophy — not worth a proper per-member liveness scan for an internal load-testing tool.
  - **Real bug found live, fixed same session**: the first version used `"#"` as the `sessionId` composite separator. `trader/session`/`replayengine/session`'s `Heartbeat`/`Release` build URLs by raw string concatenation (`BaseURL+"/v1/sessions/"+sessionID+"/heartbeat"`, no URL-encoding) — and `#` is the URL *fragment* delimiter, so `curl`/`net/http` silently truncate everything from `#` onward before the request ever leaves the client (a `PUT .../run_A#sess_x/heartbeat` request actually reached the server as `PUT /v1/sessions/run_A`, matching no registered route for that method → confusing 404/405s). Switched the separator to `"."`, which needs no encoding in a URL path segment and can never collide with `newSessionID()`'s hex-only output. Verified live end-to-end afterward (`infra/dev-redis`): two members joining one `runId` group, a third `runId` correctly rejected with 409 while the group was active, heartbeat succeeding, a non-last `Release` leaving the group's `active`/`members` keys intact (confirmed via `redis-cli`), the group's keys fully clearing only once the *last* member released, and a new, different `runId` successfully claiming immediately afterward.
- **Self-healing on crash**: if a `trader`/`replayengine` process dies without calling `Release`, the Redis key's TTL (30s) expires on its own and the next `Claim` succeeds — same self-healing philosophy as `matching/kafkaclient`'s consumer-group session timeout and `orderapi/idempotency`'s never-cache-5xx rule. Verified live (see above).
- **Client side** (`trader/session/session.go`, `replayengine/session/session.go` — independently declared per-module, same rationale as everywhere else in this repo): `Client.Claim` fails fast with a wrapped `ErrAlreadyActive` if `orderapi` returns 409, and `main.go`/`run()` in both modules returns an error immediately in that case rather than starting any replay work. `RunHeartbeat` runs a background ticker at `ttlSeconds/3` (the server returns its own TTL in the claim response so both sides can never disagree about the interval) until the run's context is cancelled; `main.go` releases the session in a `defer` after the heartbeat goroutine stops.
  - **Asymmetric `runId` support, deliberately** (2026-08-07): `trader/session.Client.Claim(ctx, owner)` kept its original 2-argument signature unchanged — `trader` never shards, so there's nothing for it to group with, and its request body simply never sends a `runId` (server treats the omission as "solo group of one," same as before this feature existed). `replayengine/session.Client.Claim(ctx, owner, runID)` gained the extra parameter, fed from a new `replayengine/main.go` flag: `-run-id` (default `""` — a lone shard still runs exactly as before). To actually distribute one replay run across N shards, whatever launches the N processes (a shell loop for manual testing, or eventually the K8s Job template from the launcher design above) must generate one shared ID and pass the identical `-run-id` value to every shard — the shards don't discover each other or negotiate an ID among themselves, matching this repo's existing "no coordination needed" philosophy for FR-19's market sharding.
- **`trader/main.go` and `replayengine/main.go` were both refactored from `main()` directly to a `main() { if err := run(); err != nil { log.Fatal(err) } }` / `func run() error` split** specifically to make the session `Release` `defer` reliable — `log.Fatal` calls `os.Exit` immediately and skips deferred functions, so any `log.Fatal` inside the old flat `main()` after a successful claim would have leaked the session lock for a full TTL (30s) instead of releasing it immediately. Every other line of logic in both `main()`s (flags, manifest fetch, replay loops, order-record flush) is otherwise unchanged, just moved into `run()`.

### AI 트레이더 실행 결과 조회 (FR 없음 — 팀 결정 2026-08-13, 프론트 "실행 결과" 화면 지원)

Team decided the frontend's AI-trader/replay result screen needs exactly 4 fields: 실행 상태(running/completed/failed), 주문 접수/체결/미체결 수, 시작·종료 시각(+실행 시간), 오류 메시지 — see `docs/frontend-backend-integration.md` §3.5 for the full frontend-facing writeup. Two new read endpoints support this, both reusing guarantees the system already had rather than adding new bookkeeping:

- **`orderapi/session`'s `RunRecord`, deliberately separate from the exclusivity lock's own ephemeral keys** — the existing `active`/`meta`/`members` Redis keys (see "Concurrent execution guard" above) exist only to answer "is a run active *right now*," and get deleted the instant the last member releases (or expire via TTL on a crash) — there is nothing left to query once a run ends, which is exactly when a result screen needs to show something. `Store` gained `LastRun(ctx) (RunRecord, bool, error)`; a new Redis key `orderapi:session:lastrun` (no TTL, never auto-deleted) holds `{RunID, Owner, Status, StartedAt, EndedAt, Message}` and is written at two points: `Claim` writes an initial `{Status: "IN_PROGRESS", StartedAt: now}` record the moment a *new* group is created (`claimScript`'s "created new" outcome, not "joined existing" — a shard joining an already-running group shouldn't reset the start time), and `Release` overwrites it with the final `{Status, EndedAt, Message}` only when the *last* member of the group releases (`releaseScript`'s "group now empty" outcome — same event that already tore down the exclusivity keys). Both `claimScript`/`releaseScript` were extended to return a richer signal (1 vs 2, previously just success/fail) so the Go code can tell "created" from "joined" and "last member" from "one of several" without a second round-trip.
- **`Release`'s signature grew an `outcome RunOutcome{Status, Message string}` parameter**, and `DELETE /v1/sessions/{sessionId}` now accepts an optional JSON body `{"status":"COMPLETED"|"FAILED","message":"..."}` (`sessionhandlers.go`'s `releaseSessionHandler`) — an empty/absent body defaults to `COMPLETED`, so this is backward-compatible with any caller that was already hitting this endpoint with no body. `trader/session.Client.Release`/`replayengine/session.Client.Release` both grew matching `status, message string` parameters and now send that body (same independent-redeclaration pattern as the rest of `session.go`'s wire shapes) — `RunStatusCompleted`/`RunStatusFailed` are exported string constants on `orderapi/session`, but `trader`/`replayengine` don't import them (module independence — they use the literal strings `"COMPLETED"`/`"FAILED"` directly, same rationale as everywhere else two modules need to agree on a wire value without sharing a Go type).
- **`trader/main.go`'s and `replayengine/main.go`'s `run()` both changed to a named return (`func run() (err error)`)** specifically so their existing deferred release closure can observe the function's *final* outcome (an unnamed return can't be read from a `defer`) — the closure now computes `status := "COMPLETED"; if err != nil { status = "FAILED"; message = err.Error() }` and passes it to `Release`. Both also gained a `resultMessage` var, set on the success path when there's something worth summarizing (`trader`: which markets failed, if any, even though a few per-market failures don't fail the whole run per existing policy; `replayengine`: how many markets replayed/skipped and which shard) — this is *not* an error, just a human-readable note carried into `RunRecord.Message` alongside a `COMPLETED` status.
- **`recorder/query`'s new `OrderSummary(ctx, mode string, from, to time.Time) (OrderSummary, error)`** (`MySQLQuerier`, real SQL: `SELECT COUNT(*), COALESCE(SUM(status='FILLED'),0), COALESCE(SUM(status IN ('ACCEPTED','PARTIALLY_FILLED')),0) FROM trade_order WHERE mode=? AND submitted_at >= ? AND submitted_at < ?`) — the `COALESCE` wrapping matters: MySQL's `SUM(CASE...)` returns `NULL`, not `0`, when zero rows match, which would otherwise fail the `Scan` into `*int64` on an empty time window. Exposed as `GET /v1/orders/summary?mode=...&from=...&to=...` (`server.go`'s `orderSummaryHandler`, wired in `main.go`) — `mode`/`from` are required (400 `INVALID_MODE`/`MISSING_FROM` otherwise), `to` is optional and defaults to "now" when omitted (for polling a still-`IN_PROGRESS` run's running total). **Why `[from,to)` is precise enough to trust without a `runId` filter on `trade_order` itself**: `orderapi/session`'s exclusivity guard (see "Concurrent execution guard" above) already guarantees only one trader/replayengine run-group is ever active system-wide, so no other run's orders can land inside `[startedAt, endedAt)` — the frontend is expected to pass exactly the `startedAt`/`endedAt` from `GET /v1/sessions/last-run` (below) as `from`/`to`.
- **New `GET /v1/sessions/last-run` (`orderapi/sessionhandlers.go`'s `lastRunHandler`, wired in `main.go`)** — returns the `RunRecord` above (RFC3339-formatted timestamps, `endedAt`/`message` `omitempty` so an in-progress run's response omits them entirely rather than sending empty strings), 404 `NO_RUN_YET` if `orderapi` has never seen a completed claim. This is the frontend's single source for "실행 상태"/시작·종료 시각/오류 메시지; 실행 시간 is left for the frontend to compute as `endedAt - startedAt` rather than precomputed server-side (same "don't compute what the caller can trivially derive" restraint used elsewhere in this API).
- **Verified live end-to-end against real local Kafka/Redis/MySQL** (fresh `infra/dev-kafka`/`infra/dev-redis` + a disposable local MySQL on port 3307, same "native `mysqld` already owns 3306 on this dev machine" workaround as prior MySQL-verification passes — see `recorder/`'s own "verified live" notes above): `GET /v1/sessions/last-run` → 404 before any claim; claim → immediately shows `IN_PROGRESS` with `startedAt`; `DELETE .../{id}` with `{"status":"COMPLETED","message":"..."}` → `last-run` flips to `COMPLETED` with matching `endedAt`/`message` (Korean text round-tripped correctly through Redis JSON — an initial "garbled" reading turned out to be a Windows shell console-encoding artifact from typing Korean literals inline in a bash command, not a real bug, confirmed by re-sending the same body from a UTF-8 file); a `FAILED` release and a no-body release (defaults to `COMPLETED`) both confirmed correct. Submitted real orders through `orderapi` in both `PAPER_TRADING` and `REPLAY` mode, then confirmed `GET /v1/orders/summary` correctly split counts by `mode` (3 vs 1), correctly defaulted `to` to "now" when omitted, returned `{0,0,0}` (not an error) for a time window with zero matching rows, returned 400 for missing `mode`/`from`, and — after flipping one order's `status` to `FILLED` directly in MySQL to simulate a real fill — correctly moved it from `unfilled` to `filled` in the aggregate.

### Session-end unresolved-order cleanup (FR 없음 — 팀 결정 2026-08-19, 부하테스트 반복으로 인한 matching OOMKilled 사고 대응)

**Incident**: repeated load-test runs left a growing number of never-matched resting orders in `matching`'s in-memory orderbook (load-test traffic doesn't naturally cross bid/ask the way organic two-sided market activity does, so a large share of submitted orders just sit there forever unless explicitly canceled). Across enough runs this grew `matching`'s heap past its pod memory limit → OOMKilled → CrashLoopBackOff, which in turn 502'd anything depending on `matching` being reachable. Immediate mitigation was raising the pod memory limit (1Gi → 2Gi, `infra/k8s`). This section is the follow-up: automatically cancel a run's own leftover unresolved orders the moment that run ends, so backlog stops compounding across runs.

**Rejected approach: wiping matching's in-memory/Redis state directly.** Tempting because it sounds simpler, but it's actually worse on both fronts:
- **Harder to build**: `matching` has no "reset" primitive at all — it's a pure Kafka-event consumer (NEW/CANCEL) with no HTTP admin surface (aside from `/metrics`), so a wipe would mean inventing a new message type or endpoint from scratch. Cancellation, by contrast, is an existing, already-tested code path — `matching` already handles "cancel an order not currently in the book" as a safe no-op, so no new matching-engine code was needed at all.
- **Corrupts the load-test's own measurement data**: a raw wipe never publishes anything to Kafka, so `recorder`'s `trade_order` rows for those orders stay `ACCEPTED`/`PARTIALLY_FILLED` forever — permanently wrong "미체결" counts for that run's own results, which defeats the point of a project whose purpose *is* measuring load-test outcomes accurately. Publishing real CANCEL events (which `recorder` already handles, including the existing fill-vs-cancel-ordering and idempotency guards) keeps the historical record honest.

**Design — reuses `OrderSummary`'s mode+time-window precision instead of adding a session-ID column.** The first sketch of this feature proposed a `trade_order.session_id` migration plus threading that ID through `POST /v1/orders` on every request — rejected for two reasons: (1) it reverses the team's earlier, deliberate `docs/erd.md` decision *against* a `REPLAY_SESSION`/session-tracking column (same "~1 month project, don't need durable run bookkeeping" reasoning as before); (2) looking up "my current active session" per order would mean a Redis round-trip on `POST /v1/orders`'s hot path — exactly the NFR-01 (10,000 orders/sec) cost the session guard was designed from day one to avoid (see "Concurrent execution guard" above: session checks happen once at process start, never per-order). Instead, this reuses the same trick `OrderSummary` already established: `mode` + `[startedAt, endedAt)` uniquely identifies "this run's orders" *without* any new column, because the session guard already guarantees no other run's orders can land in that window.

- **`recorder/query`'s new `UnresolvedOrders(ctx, mode string, from, to time.Time) ([]UnresolvedOrder, error)`** (`MySQLQuerier`: `SELECT order_id, market_code FROM trade_order WHERE mode=? AND submitted_at >= ? AND submitted_at < ? AND status IN ('ACCEPTED','PARTIALLY_FILLED')`) — `UnresolvedOrder{OrderID, Market}`; `Market` is included specifically because `kafkaclient.Publisher.PublishCancel` needs it for the Kafka partition key. Exposed as `GET /v1/orders/unresolved?mode=&from=&to=` (`unresolvedOrdersHandler`, `server.go`) — same required/optional param rules as `orderSummaryHandler` (they now share a `parseModeFromTo` helper).
- **`orderapi/session.Store.Release` signature grew a return value**: `Release(ctx, sessionID, outcome) (record RunRecord, finalized bool, err error)` — `finalized` tells the caller whether *this* release was the group's last member (mirrors the existing `releaseScript` n==2 signal, previously only used internally to decide whether to write `LastRun`), and `record` is the just-finalized `RunRecord` (avoids a second Redis round-trip to re-fetch `Owner`/`StartedAt`/`EndedAt`).
- **`orderapi/sessioncleanup.go`'s `cleanupUnresolvedOrders`** — called from `releaseSessionHandler` in a background goroutine (fire-and-forget: the client already got its `204` for the release itself, which already succeeded regardless of cleanup's outcome) only when `finalized == true`. Maps `RunRecord.Owner` → `mode` via the same `trader`→`PAPER_TRADING`/`replayengine`→`REPLAY` convention already used for `X-Order-Mode` (`modeForOwner`), calls `GET /v1/orders/unresolved` on `recorder` for `[StartedAt, EndedAt)`, then `PublishCancel`s each returned order. Fails open at every step (empty `RECORDER_URL`, unknown owner, zero `StartedAt`, recorder unreachable, individual publish failure) — logs and moves on, never blocks or fails the session release itself, matching this codebase's established "best-effort side effect, not a correctness-critical path" pattern (same philosophy as `matching/kafkaclient/assignment_producer.go`'s fire-and-forget audit publishes).
- **New `RECORDER_URL` config** (`orderapi/config.go`) — optional, empty means the cleanup step is skipped entirely (same "don't force local dev to configure a feature it isn't using" pattern as `JOB_TRIGGER_QUEUE_URL`/`ORDER_RECORDS_BUCKET`).
- **Startup/per-cleanup visibility logging added 2026-08-20, after a real incident this exact silence caused.** The original implementation skipped silently when `RECORDER_URL` was empty — no log anywhere, in `main.go` or in `cleanupUnresolvedOrders` itself — unlike its sibling optional config `JOB_TRIGGER_QUEUE_URL`, which already logged its enabled/disabled state at startup. When a prod deploy manifest omitted `RECORDER_URL` for real, this meant zero signal that session-end cleanup was silently inert; the gap was only found once orphaned unresolved orders had already piled up. Fixed by making `main.go` log which state it's in at startup (`"recorder 연동 활성화"` / `"RECORDER_URL이 없어... 비활성화"`, matching `JOB_TRIGGER_QUEUE_URL`'s existing pattern) and by making `cleanupUnresolvedOrders` itself log a skip line (with the `runId`) every time a session ends while it's unset — so both "is this feature on at all" and "did this specific session's cleanup get skipped" are visible from logs alone, not just inferred after the fact from missing side effects.
- **Verified live end-to-end** against real local Kafka/Redis/MySQL: claimed a session, accepted 4 orders (stayed `ACCEPTED`, no matching engine running to fill them), released the session → log showed `미종결 주문 4/4건 취소 발행` → confirmed all 4 flipped to `CANCELED` with a real `canceled_at` in `trade_order` moments later (via `recorder`'s own Kafka consumption of the CANCEL events, independent of `matching`). Also verified the multi-member (FR-19 shard) case: claimed 2 members under one `runId`, accepted an order, released the *first* member — confirmed no cleanup log at all (group not finalized) — then released the *second* (last) member — confirmed cleanup fired then and only then, correctly canceling that group's order.

### Stop button — mid-run graceful stop (FR 없음 — 팀 결정 2026-08-20, "중지 버튼이 없다" 실사용 피드백 대응)

**Gap**: `trader`/`replayengine` only ever stopped by running to completion or being hard-killed (`kubectl delete job`) — the frontend's "초기화" button just reset the *result screen's* local state without touching the actual running process, so a real run kept consuming resources and submitting orders in the background regardless of what the screen showed. A hard kill would also skip the session-end unresolved-order cleanup entirely (see above) — `Release` is only called from the process's own `defer`, which a `SIGKILL` never lets run — so a "stop" built as a K8s Job deletion would silently *reintroduce* the exact orphaned-order problem that cleanup feature exists to prevent.

**Design — piggyback on the existing heartbeat round-trip rather than building a new polling path or touching K8s.** `trader`'s and `replayengine`'s `run()` already run a background heartbeat every `ttlSeconds/3` (~10s) against `orderapi`'s session API, and both already build a `context.WithCancel` that every market-replay goroutine and (for `trader`) the global AI bots already select on `ctx.Done()` for — this was all pre-existing plumbing from the session guard and per-market pacing loops, not new. So "stop" just means: let a stop request ride along in the *next* heartbeat response, and have the heartbeat loop call the same `cancel()` that a natural end-of-run already calls.
- **`orderapi/session.Store.Heartbeat` signature grew a return value**: `Heartbeat(ctx, sessionID) (stopRequested bool, err error)`. `RedisStore.Heartbeat` does its existing atomic TTL-refresh script, then a plain `GET`/`EXISTS` on a new `orderapi:session:stop:{runID}` key — this second check is deliberately *not* folded into the same Lua script, since the stop flag is a pure signal that doesn't participate in the group's exclusivity correctness (unlike `activeKey`/`membersKey`) and a `Heartbeat` calls this every ~10s regardless, so there's no TOCTOU window worth closing with atomicity. A read failure on the stop key fails open (returns `false`, doesn't fail the heartbeat itself) — same "don't let an auxiliary signal block the load-bearing operation" philosophy as `RedisChecker`'s backpressure read-error handling.
- **New `Store.RequestStop(ctx, runID) error`** — `SET`s `orderapi:session:stop:{runID}` (TTL matches the session's own, so an orphaned flag self-heals the same way every other key in this package does) only if `activeKey` currently equals `runID`; otherwise `ErrNotActive`. Exposed as `POST /v1/sessions/{runId}/stop` (`stopRunHandler`, `sessionhandlers.go`) — deliberately keyed by `runId`, not the opaque per-member `sessionId` `Claim` returns, because the *frontend* is the caller here and it only ever sees `runId` (from `GET /v1/sessions/last-run`) — the internal `sessionId` never leaves the `trader`/`replayengine` process. 404 `NO_ACTIVE_RUN` if there's nothing active to stop; retrying is safe (idempotent — a second call just re-sets the same flag).
- **`heartbeatSessionHandler` changed from a bare `204` to `200 + {"stopRequested": bool}`** (`heartbeatResponse`) — `trader/session.Client.Heartbeat`/`replayengine/session.Client.Heartbeat` (independently redeclared, same module-independence rationale as everywhere else) now parse and return this. `session.RunHeartbeat` in both modules gained an `onStopRequested func()` parameter, called exactly once (guarded by a local bool so a stop isn't re-triggered every subsequent heartbeat tick) the first time a response comes back with the flag set.
- **`trader/main.go`/`replayengine/main.go`'s `run()` — the `context.WithCancel` that market-replay goroutines already select on had to move earlier**, to right after the session `Claim` and before the heartbeat goroutine starts, so the heartbeat's `onStopRequested` callback has a `cancel` to call. (`replayengine/main.go` previously used a bare `context.Background()` here — never cancelable at all pre-2026-08-20, since nothing needed to cancel it early before this feature; `trader/main.go` already had a cancelable context, just created too late to hand to the heartbeat goroutine, so only its *position* moved.) A package-level `stopped bool`, set by the same callback, is read (race-free — set only before `heartbeatWG.Wait()` returns, read only after) by the deferred session-release closure to report a third outcome, `orderapi/session.RunStatusStopped = "STOPPED"`, distinct from `COMPLETED`/`FAILED` so the frontend's result screen can tell "user stopped it" apart from "it crashed." Per-market replay errors that are actually just `context.Canceled` (i.e., cut short by the stop, not a real failure) are filtered out of `trader/main.go`'s `failed` list via `errors.Is` — a deliberate stop shouldn't make every in-flight market show up as a failure.
- **Order records / DB writes already in flight are not wiped, deliberately — reuses the existing session-end cleanup, doesn't bypass it.** A teammate initially asked for a "flush everything" button (discard whatever `matching`/`recorder` haven't finished processing yet, since waiting for it felt slow) — rejected for the same reason the original cleanup design rejected a raw state wipe (see above): it would silently break FR-09's "Kafka 발행 건수 = DB 저장 건수" and permanently corrupt that run's own measured results, which is the one thing this project is actually trying to produce correctly. The agreed compromise: stop only *submits no more new orders* — everything already published to Kafka drains normally, and whatever's left `ACCEPTED`/`PARTIALLY_FILLED` once the session actually releases gets swept up by the existing session-end unresolved-order cleanup (real `CANCEL` events, not deletion) exactly as it would after a natural completion. Already-`FILLED` orders are never touched either way.
- **Not solved by this change, tracked separately**: the *reason* draining felt slow that day wasn't a real write backlog at all — see the `idx_trade_order_submitted_at`/`idx_execution_executed_at` index bullets under `recorder`'s schema section below, found the same day. A stop button doesn't need to wait on that fix to be correct, but it's why "stop" alone didn't feel fast enough on its own that day.
- **Verified**: `go build`/`vet`/`test` clean across `orderapi`/`trader`/`replayengine` (existing `sessionhandlers_test.go` extended with `TestHeartbeatSessionStopRequested`/`TestStopRunSuccess`/`TestStopRunNoActiveRun`, using the same `fakeSessionStore` pattern already established for this file). Not yet hand-verified against a real running `trader`/`replayengine` process end-to-end (no live infra available in this pass) — the individual pieces (heartbeat round-trip shape, context-cancellation propagation into `ReplayMarket`/`runGlobalBot`/`replayMarket`) were each already independently live-verified for their original purposes (session guard, per-market pacing) before this feature reused them, but the *new* wiring connecting them hasn't been run against a real broker/Redis yet.

### Trader/simulator launch via K8s Job (implemented 2026-08-11, superseding the earlier browser→Lambda-direct design)

**The design in this section changed for real, not just on paper — the infra teammate built a different (better) trigger flow than the original 2026-08-06 plan, and this doc was out of date until now.** The old plan (below, kept crossed out for history) was browser → Lambda directly. The actual `infra/job-trigger.tf`/`infra/irsa.tf`/`infra/k8s/job-trigger-rbac.yaml` build: **browser → `orderapi` → SQS (`team1-sqs-job-trigger`) → Lambda(`team1-lambda-job-trigger`, VPC-attached) → EKS API → K8s `Job`**. `orderapi` (`sa-ingest-api`) only has `sqs:SendMessage` — no K8s RBAC at all; the Lambda is the *only* identity with `create`/`get`/`list`/`watch`/`delete` on `jobs.batch`, scoped to just the `ai-trader`/`replay` namespaces (`infra/k8s/job-trigger-rbac.yaml`). This is strictly narrower blast-radius than the original plan, which would have had `orderapi` talk to K8s indirectly via Lambda anyway but didn't have this queue decoupling — the queue also gives free retry/DLQ semantics (`maxReceiveCount=3`, 14-day DLQ retention) that a direct Lambda Function URL call wouldn't have had.

**What was implemented this session, all three pieces the infra side left for "application code"**:

### RDS admission control via recorder consumer lag (NFR-13, implemented and live-verified 2026-08-07)

**Design**: extends the same "429 on consumer lag" shape the `acceptOrderHandler` `TODO` already anticipated (see `orderapi`'s `server.go` bullet above) — originally scoped to `matching`'s lag — to cover `recorder`'s lag against RDS instead, since `recorder`→MySQL is the actual bottleneck under sustained load, not `matching`. Flow: `recorder/backpressure.Watcher` periodically checks `recorder`'s own consumer lag on the `orders`/`executions` topics; over a threshold, it sets a Redis key; `orderapi`'s `acceptOrderHandler` checks that key and returns 429 while it's set, until `recorder` drains its backlog and the watcher clears it. Built alongside the `recorder` RDS-write batching above (same 2026-08-07 work) so the same RDS spec absorbs more throughput before ever needing to reject anything.

- **`recorder/backpressure/watcher.go`** — `Watcher.Run` polls a set of `LagSource` functions (`recorder/kafka.OrderReader.Lag`/`ExecutionReader.Lag`, added as thin wrappers around `kafka.Reader.Stats().Lag`) every `CheckInterval` and writes the max through a `FlagSetter`. **Hysteresis, not a single threshold**: turns on at `HighWatermark` (2000, lowered from 5000 — see "Watermark tuning + a real deadlock bug" below), only turns back off at a lower `LowWatermark` (400, lowered from 1000) — a single shared threshold would flap the flag (and therefore `orderapi`'s 429/202 behavior) every time lag oscillates near it. `nextState`/`maxLag` are pure functions, unit-tested with fake `LagSource`s — the real Redis-backed `RedisFlag` (`redis_flag.go`) is hand-verified only, same rationale as `matching/kafkaclient`/`snapshotstore`.
  - **Watermark tuning + a real deadlock bug found doing it (2026-08-11)**: ran a real FR-19 scale test first (`trader` collected+replayed a real day of 20-market Upbit data, `replayengine` replayed the resulting 279,936 recorded orders at 1/2/4/7 instances back-to-back), which left a ~1.1M-message backlog on `orders`/`executions`. Pointing `recorder` at that backlog to measure its real drain rate surfaced a genuine bug: `orders`-reader (`InsertOrdersBatch`/`CancelOrdersBatch`) and `executions`-reader (`ApplyExecutionsBatch`/`updateFill`) run as independent goroutines with independent transactions against the same `trade_order` table, and under this backlog they hit real MySQL deadlocks (error 1213) — confirmed via `SHOW ENGINE INNODB STATUS`, showing an `INSERT IGNORE` waiting on a row lock held by a concurrent `UPDATE` for the same `order_id`. Since a handler failure doesn't commit its offset and `main.go` calls `log.Fatalf` (see the `ReadMessage` auto-commit bug below for why), the whole process exited — and on restart, hit the *same* collision pattern again immediately, effectively crash-looping rather than making progress.
    - **Fix: `store/mysql.go` gained `withRetryOnDeadlock`** — wraps each of the three batch functions' entire transaction body (not just one statement, since a rolled-back transaction can't be resumed — the whole `BeginTx...Commit` has to re-run from scratch) and retries only on MySQL error 1213 (deadlock) or 1205 (lock wait timeout), identified via `errors.As` into `*mysql.MySQLError` — exponential backoff + jitter, same shape as `trader/order/retry.go`'s `RetryingSubmitter` and for the same reason (jitter avoids both readers' retries re-colliding at the exact same instant). `isRetryableMySQLError`/`withRetryOnDeadlock` are pure (fake `*mysql.MySQLError` values, no real DB) and unit-tested in `store/mysql_test.go` — the surrounding real-DB code stays hand-verified-only per this file's existing convention.
    - **Verified live**: after the fix, `recorder` no longer crash-looped against the same backlog — it stayed up and kept making progress. It did **not** fully solve throughput, though: `execution` rows still landed at only a few per second under this same backlog (vs. `trade_order` cruising at ~1,400/sec), because the underlying row-lock *contention* between the two readers (not just occasional deadlock aborts) is still there — the fix stops the crash, not the slowdown. Discussed with the user whether to dig into the contention itself (e.g. consistent lock-acquisition ordering across both batch functions) versus treating this backlog as an artificial worst case (four back-to-back load-test runs dumping 1.1M messages at once, raced through by both readers at max concurrency — not obviously representative of steady real-world arrival rates) and just being more conservative with the watermark instead. **Decided: conservative watermark for now, deeper contention fix deferred** — `HighWatermark`/`LowWatermark` lowered from 5000/1000 to 2000/400 so backpressure trips earlier, before as large a concurrent backlog can build up, rather than trying to pin down an exact safe ceiling from this one extreme, hard-to-generalize test.
    - **`matching`'s own lag watermark (5000/1000) was deliberately left unchanged** — the same FR-19 test run showed `matching`'s own consumer-lag flag never tripped once across all four instance-count scenarios, meaning its current watermarks have real headroom in the load actually exercised. Not raised either, since the test only proved "enough headroom for this load," not where the real ceiling is.
  - **`kafka.Reader.Lag()`/`ReadLag()` return -1/an error for consumer-group readers** (confirmed in `segmentio/kafka-go@v0.4.51`'s source) — `recorder`'s readers all use `GroupID`, so neither method works here. `Stats().Lag` is a *different* internal counter (`r.stats.lag`), updated unconditionally inside the low-level fetch path on every batch read regardless of group-mode — confirmed safe to use by reading the library source before relying on it, not just from the doc comment.
  - **Fail-open, not fail-closed**: `RedisFlag.SetActive` writes the key with a 15s TTL when active, deletes it when not — if `recorder` crashes while the flag is set, it self-heals off after the TTL rather than rejecting orders forever (same self-healing philosophy as the session guard's TTL and `matching/kafkaclient`'s consumer-group session timeout). `orderapi`'s `RedisChecker` also treats a Redis *read* error as "not active" (logs and fails open) rather than blocking admission on a Redis hiccup.
- **`orderapi/backpressure/checker.go`/`redis_checker.go`** — `Checker` interface (existence of the Redis key = active, value content unchecked) so `acceptOrderHandler` can be tested with a fake (`fakeChecker` in `server_test.go`), same pattern as `kafkaclient.Publisher`/`session.Store`. `acceptOrderHandler` checks it **after** the idempotency-cache-hit check but **before** validation — a cached-response replay is not new load and must succeed regardless of current backpressure; a genuinely new request gets checked before any other work. Returns 429 `CONSUMER_LAG_EXCEEDED` via `writeError` (never `writeErrorAndCache`) — same non-caching rule as the `Decided` bullets below.
- **Verified live end-to-end** (`infra/dev-kafka`/`infra/dev-redis` + a disposable local MySQL, with `HighWatermark`/`LowWatermark`/`CheckInterval` temporarily lowered to make the test fast and deterministic, then reverted): produced a 50,000-message backlog on `orders` with `recorder` already running, then polled both the Redis flag and `orderapi`'s actual `POST /v1/orders` response every second. The flag came on and `orderapi` returned 429 for 42 consecutive seconds while the backlog drained (13,000 → 50,000 rows committed), then the instant the backlog fully drained the flag cleared and `orderapi` immediately started returning 202 again — confirmed for 18 more seconds straight. Confirms the whole chain (lag measurement → hysteresis → Redis → `orderapi` read → 429/202) end to end, not just each piece in isolation.

**Decided**:
- **A rejected (429) order is not queued anywhere and is not retried by the server** — it never reaches the `orders` topic at all, so it never becomes a `TRADE_ORDER` row, never appears in FR-17's record file (`RecordingSubmitter` only records a `Submit` that returns success), and leaves no trace beyond a log line and a rejection-count metric. This was explicitly discussed and accepted, not an oversight: for `trader`, a *transient* 429 gets retried client-side now (see below) so it's not simply dropped; for `replayengine`, dropping the order is *preferred* over retrying (see next point).
- **`trader` gets 429 retry logic (implemented 2026-08-07, `trader/order/retry.go`'s `RetryingSubmitter` — see `trader/order/` above for the full design); `replayengine` deliberately does not.** `replayengine`'s entire reason to exist (FR-18) is submitting the *same* recorded order sequence in the *same* relative order/timing on every run, so that comparing metrics across two runs (e.g. before/after an infra change) is a fair comparison. Retrying a 429'd order after a real-time-dependent backoff would make the actual Kafka arrival order/timing depend on whatever congestion happened to occur during that specific run — nondeterministic, and specifically undermines the before/after comparison this project's whole measurement methodology rests on. So `replayengine` keeps today's behavior unchanged: a 429 (like any other `Submit` failure) is logged and skipped, `replayMarket` moves on to the next recorded order. The team's framing: the resulting rejection count/rate becomes a first-class **infra capacity signal** surfaced via monitoring — "how much load did the system actually reject under condition X" is itself a useful measurement for this load-testing project, not a defect to hide.
- **`trader`'s retry reuses the same `Idempotency-Key` across attempts, not a fresh one per attempt** — `Order.IdempotencyKey` is now generated once in `NewOrder` rather than inside `HTTPOrderSubmitter.Submit`, specifically so `RetryingSubmitter` calling `Submit` several times with the same `Order` value sends the same key every time (avoids a scenario where an earlier attempt actually succeeded server-side but the caller didn't see a clean 202, which could otherwise double-accept the order).
- **The 429 must not be cached in `orderapi/idempotency.Store`.** `idempotency.go`'s existing rule is "never cache a 5xx, because Kafka publish failures are transient and must stay retryable under the same key" (see `orderapi/` bullets above) — a lag-based 429 is transient in exactly the same sense (the condition clears once `recorder` catches up), so it needs the same treatment: if it's accidentally routed through `writeErrorAndCache` (used today for deterministic 4xx like `INVALID_MARKET`), a retry with the same key would keep getting the stale cached 429 forever, even long after the lag condition clears.

### `matching`'s own consumer-lag-based 429 (NFR-13, matching's own lag — implemented and live-verified 2026-08-10)

**Distinct bottleneck from the recorder version above**: the recorder-lag 429 catches `recorder`→MySQL falling behind. This one catches `matching` itself falling behind on the `orders` topic — NEW/CANCEL piling up because matching can't keep up, a different failure mode with a different signal. Both flags feed the same `acceptOrderHandler` gate; `orderapi` treats "either one is active" as "reject," since a caller doesn't need to know which subsystem is behind, only that it should back off.

- **`matching/kafkaclient/consumer.go`'s `GroupConsumer` gained a `readers map[int]*kafka.Reader` + `readersMu sync.Mutex`** — `consumePartition` registers its `*kafka.Reader` into this map right after creating it and deregisters it (via `defer`) when the partition is released (rebalanced away or the read loop errors out). This registry exists purely so `Lag()` (new method) can sum `r.Lag()` across whatever partitions *this instance* currently holds — necessary because unlike `recorder` (effectively one process, fixed partition set from Kafka's own group assignment), `matching` runs multiple instances that dynamically acquire/release partitions under FR-11, so "this instance's total lag" isn't a fixed thing to wire up once, it has to reflect whatever the rebalancer currently gave it.
  - **`Reader.Lag()` works here, unlike `recorder`'s readers** — `matching`'s per-partition readers use `GroupID: ""` (group-less; `kafka.ConsumerGroup` is only used for membership/rebalancing, actual reads bypass it — see the `kafkaclient/` bullet above), so `Reader.Lag()` returns a real value directly. `recorder`'s readers, by contrast, use a real `GroupID` and had to fall back to `Stats().Lag` instead (see the recorder section above) — same underlying kafka-go quirk, opposite fix, because the two modules' consumer setups differ.
- **`matching/backpressure/`** (new package, mirrors `recorder/backpressure`'s `Watcher`/`LagSource`/`FlagSetter`/hysteresis design almost verbatim — `nextState`/`maxLag` unit-tested the same way) — the one deliberate difference is `redis_flag.go`'s `RedisFlag.SetActive`: **it only ever `SET`s (refreshing the TTL) when active; it does nothing when inactive, never an explicit `DEL`.** This matters because `matching` runs multiple instances sharing one Redis key (one global "is matching behind" signal, not per-instance) — if one instance's `SetActive(ctx, false)` explicitly deleted the key the moment *its own* lag recovered, it could wipe out a flag that a different, still-overloaded instance legitimately set moments earlier. Since nobody explicitly clears the key, it only ever disappears by 15s TTL expiry once *every* instance has stopped refreshing it (i.e., nobody currently thinks they're behind) — self-healing, same TTL philosophy as the session guard, just applied to a multi-writer key instead of a single-owner one.
- **`matching/main.go`** wires `backpressure.Watcher{Sources: []backpressure.LagSource{consumer.Lag}, Flag: &backpressure.RedisFlag{Client: redisClient, Key: "backpressure:matching_lag"}, ...}`, started via `go matchingWatcher.Run(ctx)`, reusing the `redisClient` already created for `rebalance.NewLoadTracker`. Same watermarks/interval as `recorder`'s (5000/1000/5s) — equally a placeholder pending real load-test numbers.
- **`orderapi/backpressure/composite.go`'s `MultiChecker`** (new) — a `[]Checker` that implements `Checker` itself: returns `(true, nil)` the instant any sub-checker reports active, regardless of whether other sub-checkers errored; if none are active, returns `(false, firstErr)` so the fail-open behavior in `acceptOrderHandler` (log the error, treat as not-active) still applies. `orderapi/main.go` now wires `lagChecker := backpressure.MultiChecker{&backpressure.RedisChecker{Key: "backpressure:recorder_lag"}, &backpressure.RedisChecker{Key: "backpressure:matching_lag"}}` in place of the single `RedisChecker` from the recorder-only design above. `acceptOrderHandler`'s 429 message was generalized from "기록기가 처리 지연 중입니다" to "시스템이 처리 지연 중입니다" since the cause can now be either subsystem and the client's correct response (retry later) is identical either way.
- **Verified live** (`infra/dev-kafka`/`infra/dev-redis`, with `matching`'s watermarks/interval temporarily lowered to 500/100/300ms to make the test tractable at local-single-broker scale, then reverted to the real 5000/1000/5s before finishing): produced a 60,000-message backlog directly on `orders` while `matching` was stopped, then started it. The flag turned on within one check tick at a measured lag of 17,908 (confirming `GroupConsumer.Lag()` correctly sums real per-partition `Reader.Lag()` across all 20 partitions this instance held), then turned back off once the backlog fully drained — and, confirming the asymmetric-flag design, the Redis key's TTL was observed counting down un-refreshed (8s → 3s → gone) rather than being deleted immediately. Separately verified `orderapi`'s read side against a real running `orderapi` with each flag set independently by hand: baseline (no flags) → 202; `backpressure:recorder_lag` alone → 429; `backpressure:matching_lag` alone → 429; cleared → the same `Idempotency-Key` retried successfully (confirming the 429 isn't cached, same as the recorder-only design).

- **`matching/`** — separate Go module (`module matching`, own `go.mod`), the order-matching engine: role **B** per `requirements.md` 1.2.4. Implements FR-05 (orderbook management), FR-06 (price-time-priority matching), FR-07 (partial fills), FR-08 (restart recovery), FR-09's Kafka-publish half (DB storage is a separate "기록기" component, see `recorder/` below — `matching` is explicitly not responsible for RDS), FR-10 (cancel), FR-11 (market rebalancing across multiple instances, see below), and FR-12 (orderbook query, jointly with `orderapi`'s new handler above). Runs as any number of instances sharing one Kafka consumer group — a single instance still works unmodified (it just gets all 20 partitions assigned to itself).
  - **`orderbook/`** (`orderbook.go`, `match.go`) — pure logic, no Kafka/Redis dependency, fully unit-tested. `OrderBook` holds bid/ask `priceLevel`s (`map[normalizedPrice]*priceLevel`, each a `container/list.List` FIFO queue — **not** a slice, because `Cancel` (FR-10) needs O(1) removal from the middle of a queue, which a slice can't give cheaply) plus a separately-maintained sorted-price-slice per side for O(1) best-price lookup (bids descending, asks ascending — FR-05's own verification bar); `map[orderID]*list.Element` gives O(1) cancel-by-ID. `Apply` (`match.go`) walks the opposite side's best price while it crosses the incoming order, filling FIFO at the **resting** order's price (FR-06) and leaving any unfilled remainder as a new resting order (FR-07); it always re-reads the current best price after a level empties out rather than iterating a stale slice index, so level removal mid-loop can't skip or misread the next level.
    - **Prices/quantities are `github.com/shopspring/decimal`, never `float64`** — at NFR-01/02's target throughput, float summation drift across thousands of fills would risk violating NFR-10's *exact* buy/sell-total-match requirement. Kafka messages carry price/quantity as strings specifically to avoid a float round-trip (same reasoning as `trader/order`'s formatted-precision serialization); `orderbook.normalizePrice` (`.Truncate(8)`, matching the finest Upbit tick tier) is applied before any price is used as a map key, so e.g. `"100"` and `"100.00000000"` land in the same price level instead of silently splitting into two.
    - **Time priority uses the Kafka offset, not a timestamp** — at 10,000 orders/sec (NFR-01), same-millisecond collisions are expected, but offsets are a strict total order within a market's partition. This is also exactly the number `engine`'s recovery checkpoint uses (see below), so it does double duty rather than inventing a second sequence concept.
    - `orderbook_test.go` covers FR-06's matching scenarios table-driven (see Tests above) plus a determinism check: replaying the same event sequence twice must produce byte-identical final book state. This isn't incidental — `engine`'s recovery design (below) is only correct if replay is deterministic, so the test exists to catch anything that would quietly break that assumption (e.g. accidentally keying off map iteration order or wall-clock time).
  - **`engine/`** (`engine.go`) — the per-market orchestration layer sitting on top of `orderbook`, Kafka/Redis-agnostic itself (depends only on its own `ExecutionPublisher`/`SnapshotStore` interfaces, implemented for real by `kafkaclient`/`snapshotstore`). `Apply(ctx, OrderEvent)` applies one `orders`-topic event to the book and publishes any resulting executions (FR-09's Kafka half) or removes a cancelled order (FR-10); **the event's offset is only recorded as "safely processed" after every resulting execution publish has succeeded** — if a publish fails partway through, `Apply` returns an error before advancing that bookkeeping, so a later snapshot can never checkpoint past a fill that was never actually published. `Recover(ctx)` (FR-08) loads the last snapshot for a market (if any) and restores its individual resting orders via `orderbook.Restore` (bypasses matching — these orders already survived their matching decision once, replaying them through `Apply` again would be wrong), returning the offset consumption should resume from.
    - **Recovery is checkpoint-bounded, not "always replay from the beginning"** — this was a deliberate correction from an earlier draft of the design. `docs/requirements.md` 1.2.2's "재시작 시 주문 기록을 리플레이해 복구" literally means replaying the `orders` topic from scratch, but doing that unconditionally means recovery time grows with *total historical topic volume since the topic was created*, not "time since last snapshot" — at NFR-01's target throughput this blows straight through NFR-11's 60-second recovery budget once a test session has been running a while. So `engine` periodically (event-count or wall-clock, whichever comes first — `snapshotEvery`/`snapshotInterval` in `matching/main.go`) snapshots each market's full resting-order list *plus the offset it reflects*, and `Recover` resumes from `snapshot.Offset + 1` instead of offset 0. This still satisfies the doc's "replay to recover" mechanism — it just bounds what gets replayed. Verified live: after replaying a ~75k-message backlog accumulated over this session's testing, killing and restarting `matching` resumed every market from its own recent snapshot offset (tens of thousands in), not from zero.
    - This same mechanism is also what makes Kafka's at-least-once redelivery safe (NFR-09, no double-execution) "for free" — since state is deterministically re-derived from the event log rather than trusted from a committed consumer offset, redelivering an already-processed message just recomputes the same result; nothing depends on offset-commit bookkeeping being exactly-once.
    - **Snapshot writes are async, off the matching hot path** — `SnapshotStore.Save` must return immediately; `snapshotstore.RedisStore` does this via a buffered channel + one background goroutine per store (not per market), and drops (logs, doesn't block) a snapshot if that queue is ever full rather than stalling the caller. Observed live under a large backlog-replay burst: the queue does fill up periodically ("스냅샷 큐가 가득 차서 이번 스냅샷은 건너뜀") — expected, self-healing backpressure, not a bug; a later snapshot for that market catches up once the burst subsides.
    - **`SnapshotStore.Handoff(ctx, Snapshot) error`** (FR-11) — a second, synchronous save path alongside `Save`. `Save`'s async/lossy queue is fine for occasional crash recovery, but is wrong for a *routine* market handoff (every rebalance, not just rare crashes): the lag between "last successfully async-saved offset" and "actual last-applied offset" would make the incoming instance's `Recover()` replay-and-republish already-published executions on essentially every handoff. `Engine.Handoff(ctx)` calls this directly, bypassing the queue — only called by `matching/kafkaclient` right after a market's per-partition goroutine has fully stopped reading (see below), never while `Apply` could still be running concurrently. `snapshotstore.RedisStore.Handoff` reuses the same `writeNow` primitive the async worker already used internally.
    - **`Engine.lastOffset`'s zero value is `-1`, not `0`** — found live while verifying FR-11 with two real instances: a market with zero orders ever (so `Apply` never ran) still got `Handoff`'d when its partition was reassigned, and if the zero-value int64 default (`0`) were used, the resulting snapshot would read `{"offset":0,...}` — indistinguishable from "offset 0 was actually processed." The next owner's `Recover()` would then resume from `snapshot.Offset+1 = 1`, permanently skipping whatever message eventually lands at the partition's real offset 0. `-1` means "nothing processed yet," so `Recover` correctly computes `resumeFrom = -1+1 = 0`. Regression test: `engine_test.go`'s `TestEngineHandoffWithNoEventsDoesNotSkipOffsetZero`.
    - **`SnapshotStore.SaveWatermark`/`LoadWatermark` — a lightweight fallback checkpoint, added 2026-08-20 after a real production incident.** Root cause chain observed live: a market accumulates a large resting-order backlog (load-test traffic doesn't naturally cross bid/ask — see the OOM incident under "Session-end unresolved-order cleanup" above) → the pod holding it gets OOMKilled (`SIGKILL`, which skips `Handoff`'s synchronous save entirely) → if that market's async `Save` (the 64-deep lossy queue) never once successfully landed before the crash, `Recover()`'s old logic (`if !ok { return 0, nil }`) had the next owner resume from **offset 0** — replaying the market's *entire* history on the `orders` partition (potentially days, since nothing in this repo sets a Kafka topic `retention.ms` override — see the "Kafka topic retention" note below) back through real `Apply()` (not `Restore()`), which **re-matches orders that already matched hours earlier and re-publishes duplicate executions to `executions`** — a correctness bug (violates NFR-09's no-double-execution guarantee) on top of the obvious performance/memory cost of the full replay, and the likely reason a single OOM incident could spiral into an all-night crash loop (the replay itself re-balloons memory before the next snapshot has a chance to land).
      - **Fix**: `SnapshotStore` gained `SaveWatermark(ctx, market, offset) error` / `LoadWatermark(ctx, market) (offset int64, ok bool, err error)` — a second, much lighter checkpoint (`orderbook:{market}:watermark`, just an int64) written **synchronously** (no queue, unlike `Save`) at the same cadence as the periodic snapshot trigger (`Engine.snapshot()`, alongside the existing `Save` call — failure here is logged and otherwise ignored, matching the "auxiliary signal, fail open" pattern used throughout this codebase). `Engine.Recover()` now falls back to it when the full snapshot is missing: resume from `watermark+1` instead of unconditionally `0`. This bounds the replay window to "since the last successful watermark" (at most `snapshotEvery`/`snapshotInterval` — the same 50-events/100ms cadence the full snapshot already used) instead of the entire topic history, which reduces this failure mode to the *same*, already-accepted risk level as an ordinary async-snapshot-lagged crash recovery ("가끔 있는 크래시에서는 감내할 지연" — see the `Save`/`Handoff` split note above) rather than a catastrophic full-history replay. The resting-order *state* itself is still unrecoverable in this path (the book starts empty) — that loss is inherent once the full snapshot is genuinely gone, not something this fix claims to solve.
      - **A `LoadWatermark` error (as opposed to a clean "not found") deliberately falls back to offset 0, not to the watermark path** — an ambiguous failure can't distinguish "no watermark" from "watermark lookup broke," and guessing wrong the *other* way (treating an unreadable watermark as if it existed) would silently skip a genuinely-first-time market's unprocessed messages — an unrecoverable, silent data-loss direction judged worse than the already-known, bounded cost of a possible full replay.
      - **Real ElastiCache config confirmed relevant, not a red herring**: the cluster runs `default.redis7` with `volatile-lru` eviction (only evicts keys that carry a TTL) and 3.3GB `maxmemory`. Both `Save`'s (`writeNow`) and the new `SaveWatermark`'s `Set` calls use TTL `0` (never expires), so Redis-side *eviction* of an existing snapshot/watermark key was ruled out as the mechanism (a `volatile-lru` policy never touches non-TTL'd keys). The live failure mode is therefore "a snapshot/watermark that never successfully wrote even once" (most likely: the pod OOMs before its first successful periodic `Save`/`SaveWatermark` cycle, or Redis's own `maxmemory` is hit and rejects writes outright once full — `volatile-lru` with no evictable keys left just refuses new `SET`s rather than silently dropping an old one), not "a key that existed and later vanished."
      - **Kafka topic retention, flagged as a related but separate finding**: nothing in this repo (`infra/msk.tf`, `infra/k8s/backend/kafka-admin-job.yaml`, or `infra/dev-kafka`) sets a `retention.ms` override for `orders`/`executions`/`assignments` — all three run on whatever MSK Serverless's fixed default retention is (not per-topic configurable on MSK Serverless). This means the worst-case replay window this bug could trigger was bounded only by that default retention (days), not by a single day's traffic — worth a deliberate team decision on an explicit shorter retention if the team wants to bound this further, independent of the code fix above.
      - Regression tests: `engine_test.go`'s `TestEngineRecoverNoSnapshotButWatermarkResumesFromWatermark` (fallback engages, book starts empty), `TestEngineRecoverWatermarkLoadErrorFallsBackToZero` (ambiguous failure doesn't misfire), `TestEngineSnapshotAlsoSavesWatermark` (periodic trigger actually writes both). `go build`/`vet`/`test` clean across `matching`. Not yet hand-verified against a real broker/Redis in this pass (no live infra available) — the individual pieces (`Save`/`Handoff`'s existing async/sync split, `Recover`'s snapshot-priority logic) were already independently live-verified for their original purposes; only the new watermark fallback path itself hasn't been run against a real crash scenario yet.
  - **`kafkaclient/`** (`consumer.go`, `producer.go`) — `GroupConsumer` (`consumer.go`) replaces the old Phase-1-only `OrderReader`. It uses `kafka.ConsumerGroup` (with `matching/rebalance.LoadAwareBalancer` as its `GroupBalancer`) purely for group membership/leader-election/generation-fencing — actual message consumption never goes through the group's own commit/offset machinery. On each new generation, `Run` calls `gen.Start` once per assigned partition; each spawned goroutine (`consumePartition`) maps its partition index to a market name (same `TargetMarkets`-ordered scheme as `orderapi`'s `marketPartitioner`), calls the injected `MarketLifecycle.Acquire(market)` to get a fresh `Engine` and its `Recover`-derived resume offset, then subscribes directly via a **group-less** `kafka.Reader{Partition: N, GroupID: ""}` (`Partition` and `GroupID` are mutually exclusive in `segmentio/kafka-go`) seeked with `SetOffset(resumeFrom)` — Kafka's own committed-offset tracking is never trusted, exactly like Phase 1. When the generation ends (`ctx.Done()`, i.e. this partition is being reassigned), the goroutine stops reading and calls `MarketLifecycle.Release(market)` — which the real implementation (`matching/main.go`'s `marketRegistry`) wires to `Engine.Handoff` — *before* returning; `Generation.Start`'s documented guarantee ("the consumer group will wait for all functions launched by Start to exit before the group can move on") is exactly what makes this "old owner fully stops and confirms its state before the new owner's `Acquire` runs" ordering hold across process boundaries, without any hand-rolled lock. This hybrid (group for membership, direct `Reader` for reads) was validated beforehand with a disposable spike against real local Kafka: zero duplicate `(partition, offset)` processing across both a join-triggered and a force-kill-triggered rebalance, at the cost of a real, now-documented trade-off — the whole group briefly pauses (session-timeout-bounded on a hard kill, ~tens of seconds) during a rebalance. `ExecutionProducer` publishes to `executions` keyed by market via `&kafka.Hash{}` (this topic isn't consumer-group-partitioned by anything yet, so the 1-market=1-partition bijection doesn't matter here the way it does for `orders`) and `AllowAutoTopicCreation: true`. Both topics' message shapes are **provisional** (FR-22 doc doesn't exist yet, same situation as `orderapi`).

  - **`rebalance/`** (`assign.go`, `loadtracker.go`, `balancer.go`) — pure-logic FR-11 package, no Kafka/Redis dependency in its core algorithm (fully unit-tested, same philosophy as `orderbook/`). `Assign(loads []Load, members []string) map[string]string` is LPT (Longest-Processing-Time-First) greedy: sort markets by load descending, repeatedly assign each to whichever member currently has the least total assigned load; ties break first by load-then-count (**not** load alone — see below) and finally by market name for full determinism, since `AssignGroups` only runs on whichever instance Kafka elects group leader, and a different leader on the next rebalance must compute the identical assignment from the identical input. **Found live, fixed**: the original tie-break compared `totals[m] < totals[least]` only — when all loads are equal (most commonly the all-zero cold-start case, before any throughput has been measured), `totals` never changes, so the comparison always resolved to the first member in sorted order and every market piled onto one instance instead of splitting evenly. Fixed by adding assignment-count as a secondary tie-break, so equal (including zero) loads now round-robin by count as intended. Regression test: `assign_test.go`'s `TestAssignZeroLoadSplitsEvenlyByCount`. `LoadTracker.Loads` measures each partition's recent throughput by diffing the broker's current `kafka.Conn.ReadLastOffset()` against a previous `{offset, timestamp}` reading persisted in Redis (keyed per market, survives leader changes) — no instance ever self-reports load, the broker is the sole source of truth. `LoadAwareBalancer` implements `kafka.GroupBalancer`, calling `Loads` + `Assign` inside `AssignGroups` and falling back to all-zero loads (i.e. even-by-count, thanks to the tie-break fix above) if the measurement call itself fails, so a transient Redis/Kafka hiccup during rebalance never stalls the whole group.
    - **Real self-inflicted rebalance loop found live on real MSK, fixed 2026-08-12**: a teammate reported `matching` stuck cycling through consumer-group generations every few seconds, every partition failing "복구 실패: generation has ended" in a loop (pod stayed `Running`, never actually made progress). Root cause: `Loads()` originally measured all 20 markets **sequentially** in a single `for` loop, and each iteration's `readLastOffset` dialed a **brand-new** connection to the broker (`kafka.DialLeader`) — against real MSK with `AWS_MSK_IAM`, every single dial pays a fresh TLS handshake plus a SigV4-signed SASL exchange (~100–150ms each), so 20 sequential dials cost ~2–3s. Since `Loads()` runs synchronously inside `AssignGroups` (`balancer.go`), which the elected group leader must finish before `SyncGroup` completes, this multi-second stall collided with Kafka's own rebalance-timing expectations — the coordinator concluded the rebalance had stalled and re-triggered it, which re-entered `Loads()` and repeated the same multi-second sequential-dial stall, forever. **Invisible locally** specifically because local `dev-kafka` runs with `KAFKA_USE_IAM_AUTH=false` (nil dialer, plaintext `kafka.DialLeader`, no TLS/SASL) *and* on `localhost` (near-zero RTT) — neither the auth handshake cost nor the network latency that made the sequential design expensive in production exists in local dev, so the design flaw had no way to surface there. Fixed by parallelizing `Loads()` — one goroutine per market (`measureLoad`, a new helper factoring out the per-market read-offset/read-prior-reading/save-reading sequence), writing into a pre-sized, index-aligned `[]Load` so result ordering is unaffected by goroutine completion order, with a mutex-guarded `firstErr` preserving the original "any single market's failure aborts the whole call" semantics. `go build`/`vet`/`test` clean; re-verified against real local Kafka/Redis (no `-race` available in this environment — no `gcc` for cgo — but the concurrency shape has no shared mutable state beyond distinct slice indices and the mutex-guarded error, so it's low-risk by inspection). Rebuilt and re-pushed `matching-latest` to ECR.

  - **DB engine is MySQL, not PostgreSQL** (team decision 2026-08-07) — `recorder` was originally built against Postgres and migrated once the team settled on MySQL. `store/mysql.go` (`database/sql` + `go-sql-driver/mysql`) replaced `store/postgres.go` (`jackc/pgx/v5`); nothing else in the codebase changed, because `store.Store` is an interface and every other package (`apply.go`, `events`, `archive`, `kafka`, `main.go`) only ever depended on that interface, never on the Postgres-specific type — the exact benefit this split was designed for.
    - **MySQL has no `UPDATE ... RETURNING`** (Postgres does) — `updateFill` can't lock+read+compute+write in one statement anymore. Fixed shape: `UPDATE trade_order SET remaining_quantity = remaining_quantity - ?, status = CASE ... END WHERE order_id = ?` (still does the arithmetic in SQL, no Go-side `decimal` needed) checked via `RowsAffected()` for "order not found" (0 rows, not an error), then a separate `SELECT mode FROM trade_order WHERE order_id = ?` in the **same transaction** — safe because the `UPDATE` already holds that row's lock until commit, so no other transaction can change it between the two statements.
    - **`id`/code columns are `VARCHAR(N)`, not `TEXT`** — MySQL can't use `TEXT`/`BLOB` columns as a primary key or in most indexes without an explicit prefix length; Postgres's `TEXT` has no such restriction. `price`/`quantity`/`remaining_quantity` are `DECIMAL(24,8)` — MySQL's bare `DECIMAL` (no precision given) silently defaults to `DECIMAL(10,0)` (**zero** fractional digits), which would have truncated every crypto quantity to a whole number; `24,8` matches `matching/orderbook.normalizePrice`'s `.Truncate(8)` precision. Timestamp columns are `DATETIME(3)`, not `TIMESTAMPTZ` — this project always handles time as explicit UTC (never relies on session-timezone conversion), so `TIMESTAMP`'s automatic timezone behavior and 2038 range limit are both unwanted; `(3)` keeps the millisecond precision the rest of the system already produces (`orderapi`'s `nowISO()` etc.), since plain `DATETIME` truncates to whole seconds.
    - **Real bug found live**: passing this project's ISO-8601 timestamp strings (`"2026-08-07T02:02:34.995Z"`) directly as a bind parameter for a `DATETIME` column fails — `Error 1292: Incorrect datetime value` — because MySQL's own `DATETIME` literal syntax uses a space (not `T`) and has no trailing `Z`, and the Go MySQL driver won't reinterpret an arbitrary string for you. Fixed by parsing the string into a `time.Time` (`store/mysql.go`'s `parseTimestamp`, layout `"2006-01-02T15:04:05.000Z"`) before binding — `go-sql-driver/mysql` (with `DATABASE_URL`'s `parseTime=true`) formats a real `time.Time` correctly on its own.
  - **Much simpler consumer design than `matching`'s FR-11 machinery, deliberately** — `matching`'s `GroupConsumer`/custom partition balancer/`Handoff` exist specifically to protect *per-market in-memory orderbook state* across rebalances. `recorder` has no such state (every message is an independent DB write), so `kafka/orders_reader.go`/`kafka/executions_reader.go`/`kafka/assignments_reader.go` just use a plain `kafka.NewReader(kafka.ReaderConfig{GroupID: "recorder-orders"/"recorder-executions"/"recorder-assignments"})` and trust Kafka's own partition assignment. Each topic gets its own consumer group so a burst on one doesn't affect another's partition assignment.
  - **Real, load-bearing bug found only by running this against a real broker (not caught by any unit test)**: `kafka.Reader.ReadMessage()` — the obvious, convenient method — commits the message's offset **immediately upon fetch, before the caller's handler even runs** (confirmed by reading `segmentio/kafka-go@v0.4.51`'s source: `ReadMessage` = `FetchMessage` + an unconditional `CommitMessages` call, executed before `ReadMessage` returns to the caller). Using it here would mean any DB-write failure after that point causes **silent, permanent message loss** — directly violating FR-09's own verification criterion ("Kafka 발행 건수와 DB 저장 건수가 일치"). All three readers use `FetchMessage` (does not auto-commit) followed by an explicit `CommitMessages` **only after** the handler succeeds. Decode failures (message itself is malformed — retrying can never fix this) are logged and committed-past; handler failures (e.g. a transient DB error — retrying via process restart might fix this) are **not** committed and instead returned as an error, which stops that reader and (via `main.go`'s `log.Fatalf` on `Run`'s return) restarts the whole process, resuming from the last good commit. This was caught live: a first pass silently dropped 2 real executions with zero error output, discovered only by cross-checking the Kafka topic's message count against `SELECT count(*) FROM execution`.
  - **RDS write batching (`orders_reader.go`/`executions_reader.go`, added 2026-08-07 — part of the "RDS admission control via recorder consumer lag" design above)** — `Run`'s callback shape changed from "one message in, one DB call" to "buffer up to `batchSize` (200) messages or `batchFlushInterval` (2s), whichever first, then hand the whole batch to `handleBatch` in one call." Implemented with a `context.WithTimeout(ctx, batchFlushInterval)` wrapped around each `FetchMessage` call — a `context.DeadlineExceeded` on that inner context (distinguished from the outer `ctx` actually being cancelled, checked first) means "no new message arrived within the flush window," which triggers the time-based flush even during a quiet period. Offsets for the whole batch are committed together, once, only after `handleBatch` succeeds — same "never advance past unprocessed work" principle as before, just applied to N messages instead of 1: a batch failure commits nothing, so a process restart replays the entire batch. `assignments_reader.go` was deliberately left unbatched — that topic's volume (rebalance events only) doesn't justify it.
    - **Offset-ordering subtlety, handled**: a decode failure (malformed message) is still skipped-and-committed immediately as before, but now **only after first flushing whatever's already buffered**. Committing the malformed message's (higher) offset before an unflushed batch of (lower) offsets would permanently skip those lower offsets on restart — Kafka offset commits within a partition must stay monotonic with what's actually been processed. Verified live: a malformed message injected between two valid ones didn't lose either valid message.
    - `main.go`'s wiring changed to match: the S3 archive `Batcher.Add` calls (a separate, independent batching concern, unaffected by this) now loop over the batch's individual events, while the RDS write is one call per batch (`store.ApplyOrderEvents`/`store.ApplyExecutionEvents`) instead of one call per event.

Pure, unit-tested (`decode_test.go`).
  - **`store/`** (`store.go`, `apply.go`, `mysql.go`) — `Store` interface (`InsertOrdersBatch`/`CancelOrdersBatch`/`ApplyExecutionsBatch`/`AssignMarket`/`ReleaseMarket`, batch-shaped since 2026-08-07 — see above) exists so `apply.go`'s orchestration can be tested with a fake (`apply_test.go`), same pattern as `kafkaclient.Publisher`/`engine.SnapshotStore` elsewhere. The old single-item methods (`InsertOrder`/`CancelOrder`/`ApplyExecution`) were removed rather than kept alongside the batch versions — a batch of size 1 behaves identically, so there was nothing left for the old methods to do that the new ones couldn't. `MySQLStore` (real implementation, mostly hand-verified — except `isRetryableMySQLError`/`withRetryOnDeadlock`, pure logic added 2026-08-11 and unit-tested with fake `*mysql.MySQLError` values, see "Watermark tuning + a real deadlock bug" under the RDS admission control section below) does the actual work: `InsertOrdersBatch` builds one multi-row `INSERT IGNORE` for the whole batch (still tolerates at-least-once redelivery — `IGNORE` applies per-row, so one duplicate doesn't fail the rest); `CancelOrdersBatch` wraps N per-order `UPDATE`s in one transaction (can't merge into one multi-row statement — each cancels a different `order_id` with its own `canceled_at` — but batching the *commit* is still the main win, since each commit has its own overhead independent of statement count); `ApplyExecutionsBatch` wraps N calls to `updateFill` (unchanged per-item logic — each execution can touch a different order pair) plus one multi-row `INSERT` for all the batch's `execution` rows, all in a single transaction/commit. Going from N transactions (and N commits) to 1 transaction per batch is the single biggest lever here — MySQL's commit overhead doesn't scale with statement count the way per-statement round-trip cost does.
    - **`ResolveMode(buyMode, buyFound, sellMode, sellFound) (mode string, mismatched bool)`** (`apply.go`, pure, unit-tested) — decides `EXECUTION.mode` from both sides' `TRADE_ORDER.mode`. If both sides were found and differ, the buy side wins and `mismatched=true` (logged loudly, not guessed silently) — thanks to `orderapi/session`'s "Concurrent execution guard," `PAPER_TRADING` and `REPLAY` traffic can never be live at the same instant system-wide, so this should only happen when a *stale resting order from a previous, already-ended session* gets crossed by a new session's order. If only one side was found, its mode is used. If **neither** side was found (a real, observed race — see below), `mode` is `""`, stored as SQL `NULL` (see next point).
    - **Missing-order handling is a first-class case, not an edge case** — `orders` and `executions` are consumed by two fully independent readers with no ordering coordination between them, so an execution can genuinely arrive at the recorder before the recorder has processed the NEW event for one or both of the orders it references (observed live, every time, on a from-scratch catch-up run: `orders`/`executions` don't fall behind evenly). `ApplyExecutionsBatch` **always inserts the execution row regardless** (skipping only the missing side's `remaining_quantity`/`status` update) — this is what FR-09's "always equal counts" criterion actually requires, and is why `execution.buy_order_id`/`sell_order_id` are **plain columns, not foreign keys**, and `execution.mode` is **nullable**. Both were caught as real constraint-violation crashes during local verification (an initial schema draft had a `REFERENCES trade_order(order_id)` FK and `mode ... NOT NULL` — directly contradicting this documented design) and fixed in `schema.sql`.
    - **Fill-vs-cancel ordering, resolved 2026-08-07** (found live while verifying the batching work — pre-existing since the single-item `ApplyExecution`/`updateFill`, not introduced by batching, batching's larger buffering window just made it easy to trigger). Root cause: `orders` and `executions` are consumed by two fully independent readers with no cross-topic ordering, so a `CANCEL` and an `EXECUTION` for the *same order* can reach the recorder in either relative order regardless of which one actually happened first — and this isn't a rare edge case, because "partially fill, then cancel the remainder" (FR-07 + FR-10) is a completely normal, expected trading flow. Two concrete failure directions were found: (1) a *legitimate* partial-fill-then-cancel, where the cancel is applied first (recorder-arrival-order) and the trailing partial fill must NOT undo it; (2) a *stale* cancel for an order matching had already fully filled (possible at the time because `orderapi`'s `order.Store` didn't yet learn about fills either, so it couldn't reject the cancel request — this was fixed the same way, on `orderapi`'s side, on 2026-08-10, see the `order.Store` fill-tracking bullet above) arriving either before or after the fill that actually completes the order.
      - **The fix distinguishes the two by using the fill amount itself as the source of truth, not arrival order.** `updateFill`'s `status` `CASE` now checks "did *this* fill bring `remaining_quantity` to zero" **first** — if so, `FILLED` wins unconditionally, even overriding an existing `CANCELED` (a completing fill is definitive proof the order really was filled, so it corrects an earlier stale cancel) — and only when the fill *doesn't* complete the order does it fall back to preserving an existing `CANCELED` (protecting the legitimate partial-fill-then-cancel case from being undone by a late partial fill). The same `UPDATE` also clears `canceled_at` back to `NULL` whenever it flips to `FILLED` this way, so a corrected row doesn't keep a stale cancellation timestamp. Symmetrically, `CancelOrdersBatch`'s guard grew from `status <> 'CANCELED'` to `status NOT IN ('CANCELED', 'FILLED')`, so a stale cancel can never clobber a genuinely `FILLED` order either, in either arrival order.
      - **Deliberately not fixed via a "validate in `matching` first" approach** — `matching` already treats a cancel for an order no longer in its book as a safe no-op, but that decision never reaches `recorder`: they're independent consumers of the same `orders` topic (module-independence principle), with no signal path from `matching`'s book state to `recorder` today. Building one would be a much larger change for no extra correctness benefit — the SQL-level fix above is arrival-order-independent on its own, without needing timestamps or cross-service signaling.
      - Verified live (`infra/dev-kafka` + a disposable local MySQL): cancel-then-trailing-partial-fill correctly stayed `CANCELED` with an accurately-reduced `remaining_quantity`; cancel-then-trailing-completing-fill correctly flipped to `FILLED` with `canceled_at` cleared; a completing-fill-then-late-cancel correctly left the row `FILLED` and untouched by the stale cancel.
    - **FR-11 assignment audit (`AssignMarket`/`ReleaseMarket`, added 2026-08-07)** — `matching/kafkaclient/assignment_producer.go` publishes an `ASSIGNED`/`RELEASED` event to a new `assignments` topic every time `matching/main.go`'s `marketRegistry.Acquire`/`Release` runs (fire-and-forget: publish failure is logged, never blocks the real Acquire/Release, since the real correctness guarantee already lives in Redis/`Handoff`, not here — this is audit-only). `recorder` consumes it into `MATCHING_ENGINE_ASSIGNMENT` (`docs/erd.md`, previously unpopulated — see erd.md's changelog). **`AssignMarket` closes any still-open (`released_at IS NULL`) row for that market before inserting the new one, rather than trusting a matching `RELEASED` event to have already closed it** — found live: force-killing a `matching` instance mid-test (no graceful shutdown, so `Release`/`PublishReleased` never runs for its markets) left old rows permanently open, so a market briefly showed *two* "currently open" assignments — exactly the situation this table exists to catch, except the false positive was `recorder`'s own gap, not a real FR-11 violation. Safe to self-close on every `AssignMarket` because Kafka's own `Generation.Start` contract (`matching`'s design, see below) already guarantees a new `ASSIGNED` for a market never arrives while the old owner could still be running. Verified live afterward: force-killing an instance and letting the group rebalance left exactly one open row per market, zero exceptions, across all 20 markets.
  - **`archive/`** (`archive.go`, `batch.go`, `local.go`, `s3.go`) — raw order/execution archival to S3 (bucket `team1-truss-trade-results`, already exists in AWS) or local disk (`ARCHIVE_BUCKET` empty), (recorder's raw archival path, separate from its MySQL writes). `Batcher` (pure, unit-tested in `batch_test.go`) buffers records per kind (`"orders"`/`"executions"`, separate `Batcher` instances so one doesn't delay the other) and flushes as **one new object per batch** — never a single ever-growing per-day file — once either `archiveFlushEvery` (500) records or `archiveFlushInterval` (30s) is reached, whichever first (same dual-trigger shape as `matching/engine.Engine.shouldSnapshot()`). Object keys (`{kind}/{YYYYMMDDTHHMMSSZ}_{unixNano}.json`) are always unique, so unlike `backend/dataset`'s `HeadObject`-before-`PutObject` idempotency check, no such check is needed here — a batch is never legitimately re-flushed under the same key. Accepted lossiness: a crash loses only the currently-unflushed buffer, same as `matching/snapshotstore.RedisStore.Save`'s accepted async-loss tradeoff — MySQL (via `store/`) is the durable, authoritative write; this is best-effort raw archival on top.

### Data flow

Upbit REST/websocket (`upbit` package) → Go structs (`Candle`, `TradeTick`, `UpbitTicker`) → **JSON files persisted to AWS S3** → served to the trader app on request. **Decided: this path does not use Kafka** — an earlier `backend/kafka/producer.go` wrapper was built to carry Upbit data onto a Kafka topic (per an earlier draft in `docs/requirements.md`), but market data here is historical/finite/already-`ts`-sorted and has exactly one consumer per request, none of which benefit from Kafka's pub-sub/backpressure/ordered-live-stream strengths — so it was deleted rather than left unused. (Kafka remains the right tool for the *separate* live order flow — `orders`/`executions` topics — which `orderapi/` and `matching/` now implement for real.)

The trader app is **pull-based and now exists** (`trader/`, see below): it does not receive data automatically at startup. It requests simulation data for a period from the backend, and the backend responds with the JSON file(s) covering that period (read from S3). See [docs/market-data-api.md](docs/market-data-api.md) for the full spec and sequence diagram; summary: `POST /v1/collect` triggers collection, `GET /v1/markets/data?date=...` returns a manifest of URLs for all 40 files (20 markets × batch/stream), the trader fetches them individually/in parallel via `GET /v1/markets/{market}/{batch|stream}` — backend proxies file bytes, no S3 presigned URLs, so the trader never needs S3 credentials — and per-market replay pacing (walking `events` by `ts` gaps) happens entirely client-side in memory, decoupled from the HTTP download.

**Decided and implemented**: the on-demand-generation trigger (hybrid design above) belongs to the per-file GET handler, not the manifest — the manifest stays cheap/fast (no existence checks, no `dataset.Storage` access at all) and `GET /v1/markets/{market}/{batch|stream}` (`fileHandler`) checks whether its file exists and triggers `collectMarket` for just that one market if not. Since `collectMarket` produces both batch and stream together in one call, concurrent batch+stream requests for the same market+date are deduped via `ensureMarketCollected`'s `singleflight.Group` (see `collector.go`) rather than running `collectMarket` twice — verified by firing concurrent batch/stream requests for an uncollected date and confirming the collection log line appeared exactly once.

### Output JSON file format (finalized design, not yet implemented)

Collected data is persisted as JSON, split into two files per requested period because the trader app consumes them differently:

- **Batch file** — day/week/month/year candles. Delivered as one lump snapshot; the trader app doesn't need it in time order.
- **Stream file** — second/minute candles + individual trade ticks, merged into a **single array sorted ascending by `ts`**. The trader app walks this array in order and paces its outgoing traffic by the gap between consecutive `ts` values, so all the merge/sort work happens at generation time, not in the trader app.

Field names are normalized across both files (see mapping table below) instead of reusing Upbit's raw field names, so the trader app has one consistent shape regardless of candle unit.

**Batch file**
```json
{
  "market": "KRW-BTC",
  "range": { "start": "2026-07-29T00:00:00+09:00", "end": "2026-07-30T00:00:00+09:00" },
  "candles": {
    "days":   [ { "ts": 1785283200000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 } ],
    "weeks":  [ ... ],
    "months": [ ... ],
    "years":  [ ... ]
  }
}
```

**Stream file**
```json
{
  "market": "KRW-BTC",
  "range": { "start": "2026-07-29T00:00:00+09:00", "end": "2026-07-30T00:00:00+09:00" },
  "events": [
    { "type": "trade_tick",    "ts": 1785283200123, "price": 0, "volume": 0, "side": "BUY" },
    { "type": "candle_second", "ts": 1785283201000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 },
    { "type": "candle_minute", "ts": 1785283260000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 }
  ]
}
```

**Field name mapping (Upbit raw → normalized JSON)** — kept explicit because `trade_price` means a different thing in each source struct: candle close vs. tick execution price.

Candle (all units — seconds/minutes/days/weeks/months/years):

| Upbit field | JSON field | Meaning |
|---|---|---|
| `timestamp` | `ts` | Candle time, UTC epoch ms |
| `opening_price` | `open` | Open |
| `high_price` | `high` | High |
| `low_price` | `low` | Low |
| `trade_price` | `close` | Close (**not** the same meaning as tick's `trade_price`) |
| `candle_acc_trade_volume` | `volume` | Volume for the candle period |

Trade tick:

| Upbit field | JSON field | Meaning |
|---|---|---|
| `timestamp` | `ts` | Execution time, UTC epoch ms |
| `trade_price` | `price` | Execution price (**not** the same meaning as candle's `trade_price`) |
| `trade_volume` | `volume` | Execution volume |
| `ask_bid` | `side` | `"BUY"` / `"SELL"` — remapped from Upbit's `"BID"`/`"ASK"` for clarity (BID→BUY, ASK→SELL) |

Storage target is **AWS S3** (not local disk) for prod. The bucket exists (see the Infra section below) and `dataset.s3Storage` is a real implementation (`aws-sdk-go-v2`, `HeadObject`-then-`PutObject` idempotency check, region hardcoded to `ap-northeast-2`) — verified end-to-end against an EC2 instance profile. Dev writes to local disk via `dataset.localStorage` instead; `APP_ENV` in `backend/config` selects between the two.

### Multi-market collection (implemented)

`upbit.TargetMarkets` (`backend/upbit/markets.go`) lists the ~20 target markets/coins; `collectAllMarkets` (`backend/collector.go`) loops over all of them for every request. Decisions so far:

- **One batch file + one stream file per market** (not one shared file for all markets) — keeps re-collection/re-generation of one coin from touching the others, and maps directly onto the S3 key layout below.
- On the trader-app side, the intended design is **one goroutine per market**, each independently walking its own stream file's `events` array in `ts` order and pacing sends by the gap between consecutive `ts` values — this is what actually produces the "many coins trading concurrently" load pattern, not just a speed optimization. Goroutines should share a single HTTP client / Kafka producer rather than each opening their own connection, and errors in one market's goroutine must not abort the others (isolate per-goroutine, collect via `WaitGroup`/`errgroup`).

### S3 storage design (decided so far, not yet implemented)

- **Key layout**: `s3://{bucket}/{market}/{start}_{end}_batch.json` and `.../{start}_{end}_stream.json` — period encoded in the filename, market as a path prefix.
- **Idempotency, not overwrite**: re-requesting the same market+period is not expected in normal use, but as a safety check, the backend should `HeadObject` before generating — if the file already exists, serve it as-is instead of regenerating/re-uploading.
- **No lifecycle policy**: this project's premise is re-running the *same* simulation dataset against evolving infra to measure improvement, and the project timeline is ~1 month, so objects must not expire or auto-transition to a cheaper storage class.
- **Access scope**: only the backend talks to the **market-data** bucket (`team1-truss-market-data`, IAM policy scoped to the backend) — the trader app never gets credentials for it, only the backend's request/response API. **This does not extend to order records (FR-17)** — see the "Order records" subsection right below; that's a deliberate, separate decision for a separate bucket.
- **Auth (dev vs. prod)**: final deployment target is AWS (EC2 or EKS), but local development also needs to work. The AWS SDK's default credential chain handles this without code branching — env vars/shared profile locally, IAM role automatically in AWS (EC2 instance profile, or **IRSA** for EKS — IRSA is a cluster/infra setup task: OIDC provider + IAM role trust policy + ServiceAccount annotation, not application code). The same env-var-driven pattern should extend to the planned dev-local-DB vs. prod-RDS split — connection target read from an env var (`.env` locally via the already-added `godotenv` dep, ConfigMap/Secret in EKS), not hardcoded or branched on environment in code.

### Order records (FR-17, implemented in `trader/`)

`requirements.md` FR-17: every order generated during paper trading must be recorded to a file, time-ordered, saved to S3 — that file becomes FR-18 (replay)'s input later. **Decided**: unlike market data, this goes to a **separate S3 bucket from `team1-truss-market-data`**, and **the trader writes to it directly** (not via the backend) — this is a deliberate exception to the "only backend talks to S3" rule above, made specifically for order records.

- **New bucket needed, not yet created**: proposed name `team1-truss-order-records` (same `team1-truss-*` convention as the market-data bucket), region `ap-northeast-2`. Whoever is doing infra work needs to provision it plus an IAM policy granting the trader `PutObject` (and eventually `GetObject`/`ListBucket` once FR-18/replay reads these back) — analogous to `infra/iam.tf`'s `team1_ec2_role`/`team1_ec2_s3_policy` but as its **own** role (e.g. `team1_trader_role`), not reusing backend's, so the two stay scoped independently.
- **Until the bucket exists**: `trader/main.go`'s `-order-bucket` flag defaults to empty, which selects `orderstore.NewLocalFileStorage("orders")` (writes to a local `orders/` dir) instead of `orderstore.NewS3Storage`. Pass `-order-bucket=team1-truss-order-records` once the bucket and IAM are ready — everything else (recording, flush timing, file shape) is identical either way, only `orderstore.Storage`'s implementation changes.
- **How recording happens**: `order.Order` gained a `TS int64` field (`time.Now().UnixMilli()`, set in `NewOrder`) — not part of the real order-acceptance API's request shape, only used for the record. `order.RecordingSubmitter` (`trader/order/record.go`) wraps any `OrderSubmitter` and records only orders whose underlying `Submit` succeeded — matching FR-17's verification criterion "기록 건수와 접수 건수 일치" (recorded count == accepted count). `order.InMemoryRecorder` buffers per-market in memory (mutex-protected, since multiple bot goroutines record concurrently) and **sorts by `TS` in `Snapshot`**, not at insert time — concurrent goroutines' `Record` calls can interleave slightly out of `TS` order under scheduling, the same reason `dataset.BuildStream` sorts its merged events rather than trusting insertion order.
  - **`InMemoryRecorder.mu` design — decided, revisit only if measured as a bottleneck**: up to ~62 goroutines (3 algorithmic bots × 20 markets + 2 global bots) can call `Record` concurrently on the *same* shared `InMemoryRecorder`, all serialized through one `sync.Mutex`. A lock-free alternative was discussed — give each producer goroutine its own local buffer (no shared state, no lock during the run) and k-way-merge them by `TS` at the end — which is a legitimate, commonly-used pattern for exactly this contention shape. **Decided to keep the current shared-mutex design for now**: a real end-to-end run (20 markets, up to ~118k recorded orders in one market) completed in ~1-2s with no observed slowdown, and the final sort step is needed either way (sorting one unsorted list vs. merging several pre-sorted ones — similar cost at this scale), so the extra plumbing (per-goroutine buffers + a merge routine) isn't earning its complexity yet. If lock contention is ever actually measured as a bottleneck (e.g. order volume scales up much further), switch `InMemoryRecorder` to the per-goroutine-buffer + merge design then, not preemptively.
- **`replay`/`bot` packages are untouched** — they only ever see the `OrderSubmitter` interface, so wrapping it in `RecordingSubmitter` is invisible to them. This is the same "decouple judgment from mechanics" pattern used throughout `trader/`.
- **Flush timing — end of the whole run, not per-market**: `main.go` only writes records out after *both* `wg.Wait()` (all markets' `ReplayMarket` goroutines done) *and* `globalWG.Wait()` (the global AI bots done). The global bots run until every market finishes, not just one — flushing a market's records as soon as its own `ReplayMarket` ends could miss orders the global bots place for that market afterward. Same reasoning as market-data collection producing one complete file rather than streaming incrementally.
- **File shape** (`trader/orderstore`, key layout `{market}/{start}_{end}_orders.json`, same convention as the market-data bucket):
  ```json
  { "market": "KRW-BTC", "range": { "start": "...", "end": "..." }, "orders": [ { "ts": 1785283200123, "side": "BUY", "price": "90000000", "quantity": "0.01" } ] }
  ```

### Upload/generation timing — hybrid (decided)

Simulation data is served via **both** pre-generated files and on-demand generation: some batch/stream files may be created ahead of time, but the trader app can also request a market+period that doesn't exist yet, triggering on-the-fly collection from Upbit → S3 upload → serve. The `HeadObject`-based idempotency check above is what makes this work either way. `POST /v1/collect` (see Architecture above) is the on-demand-collection trigger; it always runs across all 20 `upbit.TargetMarkets` for the requested date rather than accepting a single market — there's no per-market request shape yet. The trader-app-facing "give me the file(s) for this period" read/serve API is still not designed.

## Kafka/Redis authentication (added 2026-08-10, Kafka mechanism replaced 2026-08-11)

**Context**: until this point, every Kafka client (`segmentio/kafka-go`) across `orderapi`/`matching`/`recorder` and every Redis client (`go-redis/v9`) connected with zero auth — fine for local `infra/dev-kafka`/`infra/dev-redis`, but a real gap once MSK/ElastiCache enter the picture. Team decided both should support real auth, optionally — env vars empty means unauthenticated (unchanged local behavior), filled in means authenticated (MSK/ElastiCache).

**Kafka: AWS_MSK_IAM (not SASL/SCRAM) — reversed 2026-08-11, once the actual MSK Terraform (`infra/msk.tf`) turned out to provision MSK *Serverless*.** The 2026-08-10 pass chose SCRAM specifically because the pinned `segmentio/kafka-go@v0.4.51` module appeared to have no AWS_MSK_IAM mechanism (see below for why that check was incomplete). That choice broke once the infra side's actual Terraform was read: **AWS's own MSK Serverless docs state "MSK Serverless requires IAM access control for all clusters. Apache Kafka access control lists (ACLs) are not supported"** — i.e. SASL/SCRAM isn't an option on MSK Serverless at all, full stop, not a tradeoff. The team chose to fix this in the app (switch to IAM) rather than ask infra to move MSK Serverless→Provisioned just to keep the already-built SCRAM code, since Serverless has real operational upside (no broker capacity planning) for a load-testing project.
- **The 2026-08-10 "kafka-go has no AWS_MSK_IAM mechanism" finding was wrong, not just outdated** — it only checked the *main* `segmentio/kafka-go` module tree. AWS_MSK_IAM support ships as **separate Go submodules**, `github.com/segmentio/kafka-go/sasl/aws_msk_iam` and `.../aws_msk_iam_v2` (published back in Feb 2023, `go get`-able independently), which a main-module-only search simply doesn't surface. `aws_msk_iam_v2` is AWS SDK v2-based (`aws_msk_iam_v2.NewMechanism(awsCfg) *Mechanism`, implementing `sasl.Mechanism` directly) — the same SDK v2 this repo already uses for S3/Bedrock, so no hand-rolled protocol code and no new credential-plumbing pattern, unlike what the 2026-08-10 "too risky to hand-roll" concern assumed.
- `orderapi/kafkaclient/auth.go`, `matching/kafkaclient/auth.go`, `recorder/kafka/auth.go` — each module independently declares `newDialer`/`newTransport` (or `NewDialer`/`NewTransport`, exported in `matching/kafkaclient` since `matching/rebalance.LoadTracker` also needs one for its own direct `kafka.DialLeader` call) — same module-independence principle as everywhere else in this repo. Every producer/consumer/reader constructor across all three modules takes a single `useIAM bool` now (replacing the old `saslUsername, saslPassword string` pair) plus a `ctx context.Context` (needed for `config.LoadDefaultConfig(ctx)`). `useIAM=false` returns `nil` (no error) — same as before, so `kafka.ReaderConfig.Dialer`/`kafka.Writer.Transport` fall back to their unauthenticated default and the empty-env-var local-dev path is unchanged. `useIAM=true` builds `aws_msk_iam_v2.NewMechanism(awsCfg)` from the AWS SDK v2 default credential chain (no explicit region — the SDK already resolves `AWS_REGION`/EC2 IMDS/EKS IRSA on its own, same as the Bedrock/S3 code) and bundles it with `&tls.Config{}` (MSK requires TLS for any SASL mechanism, same as the old SCRAM setup).
- **The `kafka.RoundTripper`-interface-not-`*kafka.Transport` nil-pointer fix from 2026-08-10 (see git history) carried over unchanged** — `newTransport`/`NewTransport` still return the `kafka.RoundTripper` interface type, so `return nil, nil` on the `useIAM=false` path is still a genuine nil interface, not a non-nil interface wrapping a nil pointer. This bug class was specific to the return type, not to which SASL mechanism fills the non-nil case, so replacing SCRAM with IAM inside the same function shape didn't reintroduce it.
- **Verified live**: rebuilt and ran `go build`/`go vet`/`go test` clean across `orderapi`/`matching`/`recorder` after the swap, then re-ran the *unauthenticated* path against the real local `infra/dev-kafka`/`infra/dev-redis` stack (`KAFKA_USE_IAM_AUTH` unset, exactly today's `.env` files) — `orderapi` started without a panic and a real `POST /v1/orders` produced a real 202 with the order actually published to Kafka, confirming the empty-env-var path is still byte-for-byte the old unauthenticated behavior. **The `useIAM=true` path itself is not yet hand-verified against a real MSK cluster** — same "written and reviewed against the real SDK/library source, but no live target to test against yet" caveat as `trader/bot.RealBedrockClient` — needs a real end-to-end run once the team's MSK Serverless cluster and IAM policy (`kafka-cluster:Connect`/`*Topic`/`*Group` actions scoped to the cluster ARN, via EKS IRSA) are actually in place.
- **`KAFKA_SASL_USERNAME`/`KAFKA_SASL_PASSWORD` are gone, replaced by `KAFKA_USE_IAM_AUTH`** (`"true"`/anything-else, default false/unauthenticated) — a single boolean instead of a username/password pair, since IAM auth needs no secret of its own (the identity comes from the SDK's credential chain, i.e. EKS IRSA in prod).

**Redis: `Password` field on `redis.Options`** — `go-redis/v9` already supports this natively, so `orderapi`/`matching`/`recorder` just needed a `RedisPassword` config field threaded through to `redis.NewClient(&redis.Options{Addr: ..., Password: cfg.RedisPassword})`. Empty string is `go-redis`'s own documented "no auth" value, so no `nil`-vs-empty-interface pitfall here (unlike the Kafka `Transport` case) — no bug found, no extra verification needed beyond the existing test suite.

**Redis TLS, added 2026-08-11 — a second, independent gap found reading `infra/elasticache.tf`.** The actual ElastiCache Terraform sets `transit_encryption_enabled = true` with **no `auth_token`** configured — i.e. "TLS is required, no password is set," a combination `RedisPassword`'s empty/non-empty toggle alone can't express (empty password there had always meant "no auth *and* no TLS," which would now be wrong for this cluster). Added a separate `RedisTLSEnabled bool` (env var `REDIS_TLS_ENABLED`, default false) to all three modules' `Config`; when true, `redis.Options.TLSConfig = &tls.Config{}` is set alongside whatever `RedisPassword` is (independently — the two toggles are orthogonal, matching the real ElastiCache config instead of assuming they always move together). Not separately live-verified (standing up a TLS-terminating Redis locally was out of scope for this pass) — same risk profile as the original SCRAM+TLS bundling note used to have: standard `crypto/tls` default behavior, not custom protocol code.

**Current env vars** (all optional, all empty/false-by-default = unchanged local behavior): `KAFKA_USE_IAM_AUTH` (all three Kafka-touching modules), `REDIS_PASSWORD`/`REDIS_TLS_ENABLED` (all three Redis-touching modules). Full reference: [`docs/deployment-env-vars.md`](../docs/deployment-env-vars.md) (needs updating to match — still describes the old `KAFKA_SASL_USERNAME`/`PASSWORD` pair as of this writing). AWS-side setup (MSK IAM policy, ElastiCache in-transit encryption) documented in [`docs/aws-infra-handoff.md`](../docs/aws-infra-handoff.md) (also needs updating).

**Real bug found live (2026-08-11, reported by a teammate testing against real ElastiCache): `matching` had a second, independent Redis client that never got the TLS/password wiring.** `matching/main.go`'s `redisClient` (used by `rebalance.LoadTracker`/`backpressure.Watcher`) was correctly built from `cfg.RedisPassword`/`cfg.RedisTLSEnabled`, but `matching/snapshotstore.NewRedisStore` took a bare `addr string` and built its *own* `redis.NewClient(&redis.Options{Addr: addr})` internally — no password, no TLS, ever. Against local `dev-redis` (no auth) this was invisible; against real ElastiCache (`transit_encryption_enabled=true`) it meant the orderbook-snapshot path (FR-08/FR-11's `Save`/`Load`/`Handoff`) tried a plaintext connection to a TLS-only endpoint and failed, while the *rest* of `matching` (load tracking, backpressure) connected fine — a confusing "half-working" failure mode that's exactly why it wasn't caught by this session's own local regression testing (which never had TLS turned on). **`recorder` was checked at the same time and does not have this bug** — it only ever builds one `redis.Client` (`main.go`), already correctly wired for `RedisPassword`/`RedisTLSEnabled`; if `recorder` was also seen erroring against real ElastiCache, the cause is more likely `REDIS_TLS_ENABLED` not actually being set to `true` in that deployment's env, not a second code defect (nothing else in `recorder` constructs a Redis client independently — verified via a repo-wide `redis.NewClient` search, only one hit).
- **Fix**: `snapshotstore.NewRedisStore` now takes an already-constructed `*redis.Client` instead of an address string — same pattern `orderapi/session.NewRedisStore(client *redis.Client, ttl)` already used, which `matching/snapshotstore` should have matched from the start. `matching/main.go` now builds the one `redisOpts`/`redisClient` first and passes it to *all three* Redis-touching pieces (`snapshotstore.NewRedisStore`, `rebalance.NewLoadTracker`, `backpressure.RedisFlag`) — one client, one connection pool, one place where auth/TLS config can drift from reality, structurally ruling out this bug class recurring.
- **Verified**: `go build`/`vet`/`test` clean; re-ran the *unauthenticated* path against real local `dev-kafka`/`dev-redis` — `matching` started, took over all 20 partitions, resumed from real prior offsets stored in Redis, and kept snapshotting (the periodic "스냅샷 큐가 가득 차서" log lines are expected backpressure, not an error) — confirming the shared-client refactor didn't change local behavior. Rebuilt and re-pushed `team1-truss:matching-latest` to ECR with the fix. The `useIAM=true`/`RedisTLSEnabled=true` path itself still isn't hand-verified against real MSK/ElastiCache for the same access-limitation reason as above — this fix removes a real defect that *would* have blocked that eventual verification, it doesn't complete it.

## Conventions

- Comments and log/print messages in this codebase are written in Korean; match that style when editing existing files in `backend/upbit`, `backend/dataset`, and `orderapi/`.
- **Inter-app connection config (URLs, and later DB/cache endpoints+credentials) is always env vars via `.env`/`godotenv`; CLI flags are only for per-run simulation parameters — decided, revised from an earlier CLI-flag-based design.** `trader` originally took `-backend`/`-orderapi` as flags, but that doesn't scale once secrets enter the picture: an RDS/Redis endpoint is fine either way, but a password passed as a CLI flag shows up in `ps`/shell history on shared systems, so it can't go there — and splitting "URLs as flags, passwords as env vars" would just be two config systems to remember. So all three modules now load connection config the same way: `backend/config.go`'s `Load()`, `orderapi/config.go`'s `LoadConfig()`, and `trader/config.go`'s `LoadConfig()` each read `.env` via `godotenv` (missing `.env` is logged, not fatal — expected in prod where real env vars are injected directly).

  **Required (`log.Fatal` if unset) vs. default-and-continue — decided.** A var that legitimately differs per environment, where a wrong silent value fails *later and confusingly* instead of *immediately and clearly*, must be required: `backend`'s `S3_BUCKET` (prod only — wrong value means data silently goes to local disk instead of S3), `orderapi`'s `KAFKA_BROKER`, `trader`'s `BACKEND_URL`/`ORDERAPI_URL` — all of these defaulting to `localhost` outside local dev would mean the process starts "successfully" and only fails once it actually tries to connect, deep inside a library, instead of at startup with a clear message. A var that's effectively the same across environments and fails obviously if wrong keeps a default: `PORT` (everywhere — a wrong bind port just fails the health check immediately) and `orderapi`'s `ORDERS_TOPIC` (the topic name is a fixed convention per the docs, not something that varies by deployment). `backend`'s `APP_ENV` is unconditionally required (no valid default exists for "which environment am I"). Each module's local `.env` (gitignored, one per module: `backend/.env`, `orderapi/.env`, `trader/.env`) supplies the required vars for local dev — there is no hardcoded `localhost` fallback to lean on anymore.

  `trader/main.go`'s `-date`/`-speed`/`-order-bucket` stay CLI flags — these are simulation run parameters you genuinely want to vary per invocation (e.g. looping over dates in a shell script), not connection targets, so the flag/env-var split tracks "what changes per run" vs. "what the service connects to", not module boundaries.
- **Date boundaries are KST (UTC+9), not UTC — decided.** Every `date=YYYY-MM-DD` the API accepts (`POST /v1/collect`, `GET /v1/markets/data`, `GET /v1/markets/{market}/{kind}`) means that KST calendar day, not the UTC one — a request for `2026-07-27` collects `2026-07-27T00:00:00+09:00` through the instant before `2026-07-28T00:00:00+09:00`. Upbit is a Korean exchange, and the team decided this reads more naturally than UTC-shifted-by-9-hours days. `upbit.KST` (`backend/upbit/ticks.go`) is the shared `*time.Location`, built via `time.FixedZone("KST", 9*60*60)` rather than `time.LoadLocation("Asia/Seoul")` — Korea has no DST so the fixed offset is always correct, and `FixedZone` has no dependency on the OS/container having the IANA tzdata database installed (`LoadLocation` would fail on minimal images like Alpine without the `tzdata` package). `backend/server.go`'s `parseDate` helper is the one place all three handlers parse the incoming date string, via `time.ParseInLocation(..., upbit.KST)`.
  - **Two traps this hit while switching from UTC, worth knowing about**: (1) `upbit.FetchTradeTicksForDate` used to hardcode `time.UTC` when reconstructing its day boundary from `date.Year()/Month()/Day()` — discarding whatever `Location` the caller actually passed in. Fixed by using `date.Location()` instead of a hardcoded zone, so the function works correctly regardless of which zone callers use. (2) Its `daysAgo` calculation used `time.Now().UTC().Truncate(24 * time.Hour)` to find "today's start" — **`time.Time.Truncate` ignores `Location` entirely** (it rounds down against the absolute time since Go's zero time, which is UTC-aligned), so swapping in `.In(kst)` before `Truncate` would silently keep truncating to UTC midnight, not KST midnight. Fixed by reconstructing "today" the same way as `startOfDay` — `time.Date(now.Year(), now.Month(), now.Day(), 0, 0, 0, 0, loc)` — never `Truncate` for a timezone-aware day boundary.
  - `dataset`'s `formatFileTime` (file/S3 key timestamps, `local_storage.go`) and `toRange` (the JSON `range.start`/`range.end` fields, `build.go`) both display in KST too, for the same reason as the date boundaries — a file for `2026-07-27` should visibly read `20260727...`, not a UTC-shifted `20260726T150000...`. `formatFileTime`'s layout dropped the trailing `Z` (that specifically denotes UTC in ISO 8601 and would be wrong now); `toRange` still uses `time.RFC3339`, which renders the `+09:00` offset instead of `Z` — still fully valid, unambiguous RFC3339.
  - `upbit/candles.go`'s `FetchCandlesInRange`/`FetchRecentCandles` needed **no changes** — they only ever compare absolute `time.Time` instants (cursor-based pagination), never reconstruct a calendar day from `Year()/Month()/Day()`, so they're correct regardless of which `Location` the `start`/`end` they're given came from. `trader/` also needed no changes — it only ever passes the `date` string through to the backend as-is.
  - Verified end-to-end against real Upbit data: requesting `date=2026-08-02` produced a stream whose first event's `ts` converts to exactly `2026-08-02T00:00:00+09:00` and last event's `ts` to `2026-08-02T23:59:59+09:00`.
